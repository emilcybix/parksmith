# Architecture

## Boundaries

- `src/game`: deterministic game state, clock, economy, content definitions, construction rules. No React or Pixi imports.
- `src/rendering`: Pixi scene graph, camera, coordinate transforms, input, visual synchronization.
- `src/ui`: React HUD and panels. Zustand carries low-frequency UI snapshots and player intent, never per-frame entity state.
- `src/app`: application lifecycle that wires the three layers together.

## Data flow

Player input → construction controller → pure game-world mutation → change event → Pixi redraw + Zustand HUD snapshot. The fixed-step clock advances simulation independently of rendering. Pixi renders on animation frames, reading moving entities directly from their simulation records; in the classic renderer guest and staff positions are therefore stepped at the 100 ms fixed step and are **not** interpolated between steps, which is visible as stutter at 2× and 4× speed (PA-018 in the plan; only coaster trains are interpolated there, through `coasterTrain.ts`). The voxel renderer, the default, does interpolate figures, ride parts and trains, by `SimulationClock.stepFraction` (see Renderers).

## World model

The logical grid (the map's size, 32×32 in Phase 24 step 1; see Biomes and maps) stores terrain plus optional occupancy. Static definitions describe costs, footprints, appearance, and future simulation values. Runtime placed objects store only identity, definition ID, anchor, rotation, and mutable operating state. Rotation is a quarter turn that swaps a footprint's width and depth and nothing else — cost, stats, and behavior are orientation-free — and every consumer reads the rotated rectangle through `footprintSize` or `objectFootprint` rather than the raw definition, so placement, occupancy, guest access, scenery influence, rendering, and the overview can never disagree about which tiles a building covers. Path topology is represented by a versioned cardinal network. Reverse destination maps are shared by all guests traveling toward the same access tile and are invalidated only when paths change.

Guests live in a dedicated fixed-step simulation as compact records containing position, route cursor, needs, preference, destination, and current thought. Decisions occur on state transitions; needs update at one-second intervals. Rendering reads these records without publishing per-frame positions through React. Since Phase 29 a guest also carries `nausea`, `warmth`, `souvenirs` (a bitmask) and an `activity` (the pause of a `pausing` guest, the seat of a `walkingToBench` or `resting` one, or the pose-only flourish of a `wandering` one). The rules the guest, ride and shop simulations share live in `guests/life.ts` (pure: no RNG, no clock), so a ride completing or a stall serving can settle a stomach, warm a guest or hand over a keepsake mid-step. Benches and admirable scenery are derived destination lists rebuilt with the ride and service ones; bench seats are reserved by the guests themselves and the seat table is rebuilt from them every step. Where a guest is sick the guest simulation queues the cell and the session turns it into a sick litter pile in the same tick (`drainSickCells` → `OperationsSimulation.addSick`), so the queue is never saved. `GAME_CONFIG.guestLife.enabled` switches all of it off bit for bit. Since Phase 30 a guest also carries `thoughtObjectId`, the building a complaint thought is about, written only through `setThought` (see Guest inspector and complaint links (Phase 30)); a guest whose hunger, thirst or toilet need is at `guestLife.lifeNeedCeiling` skips every life activity (set at the leave thresholds, so it is a safety net), and a guest walking to a bench counts as moving for the crowd penalty.

Ride definitions remain immutable catalog data. `RideSimulation` owns runtime instances keyed by placed-object ID: open state, manual price, queue/rider IDs, dispatch and cycle clocks, revenue, operating expenses, throughput samples, and satisfaction totals. It mutates compact guest states only at explicit queue, boarding, completion, closure, or removal events. The React inspector receives a throttled serializable snapshot rather than the mutable runtime instance.

Food, drink, and toilet definitions use the same immutable catalog. `ShopSimulation` owns service instances keyed by placed-object ID: open state, price, FIFO queue, active customer, service clock, customers served, revenue, and satisfaction. It rechecks affordability at service start and completion, releases stale guests on closure/removal, and changes only the need matching the service type. Guest destination access remains path-network driven, while React receives throttled service snapshots for its contextual inspector.

## Sessions and scenarios

A `ParkSession` owns one world plus every simulation wired to it and runs the whole fixed-step pipeline; `GameApp` holds the current session and swaps in a fresh one when a park starts or restarts, so no cash, guests, queues, timers, or transactions can leak between parks. Sessions play under a `ParkRuleset` compiled once at start (base rules, which since Phase 16 include the new-park keys `themeAffinity` and `researchCostScale`, and since Phase 14 `crowdFeedback` → biome → scenario overrides → **permanent profile bonuses (Phase 22)** → selected Pulse Cards → safety clamps; see Game modes and profile) — global configuration is never mutated. Pulse Cards are immutable data: run-scoped rule multipliers plus display copy, each carrying at least one player-positive and one player-negative modifier. The world and each simulation consume their slice of the compiled ruleset (construction costs, guest budgets and needs, price tolerance, ride operating cost and dispatch, service speed and relief, staff wages and speed). The card collection lives in the versioned profile owned by `ProfileManager` (discovered cards; Scenario mode drafts into it, seeded and duplicate-protected) and, inside **The Map (Phase 23)**, in the run's own deck (see The Map (runs)); the hand-made Park Tour and `TourManager` are retired. A park's loadout is locked into its session at construction, and unrecognized ids in stored profiles are dropped rather than trusted. A session in mode `run` is one **stage** of a run on a generated map (`ParkSession.run`, `advanceRun`). Scenario definitions are immutable data (seeded map setup, starting cash, deadline, one typed objective, an optional constraint carried by the ruleset); `ScenarioSimulation` evaluates reach/earn/sustain objectives and the deadline against typed simulation and management metrics, never UI text, and latches the first success or failure with numeric evidence. Sandbox is simply a session without a scenario. The Sandbox alone carries the First Day progression (`src/game/onboarding`, `OnboardingTracker`): ten steps as data, each completed by a pure function of a read-only snapshot of simulation metrics (`collectOnboardingInput`), evaluated every 10th tick, sticky once latched, skippable and dismissible, and never able to refuse a build. It reads nothing about rides or the park being open.

### Park capacity (Phase 11, PA-009)

`GuestSimulation.capacityView()` returns the organic guest ceiling with its parts (`ceiling`, `rideSeats`, `rating`,
`crowdMultiplier`, `hardMaximum`, and `blocked`: park closed, after hours, too few paths or no reachable open ride). It
is a pure read: like `organicGuestPotential()`, now a one-line wrapper over it, it first syncs the navigation graph and
destination list (derived caches the determinism harness ignores), and the private helper it shares with
`updateArrivals` keeps the arithmetic in one place and in the same operation order. GameApp publishes the view as
`UiState.guestCapacity` (a new object only when a number changed) and steps `src/app/capacityNotice.ts`, a pure tracker
driven by world ticks: `atCapacity` turns on after 10 simulated seconds at or above a non-zero ceiling, off below
`ceiling − max(2, ceil(ceiling × 0.1))` or when the ceiling rises past the count, and `fire` raises one `important`
toast after 60 s, re-armed only by leaving capacity. It is reset on every session swap and is **never saved**: it is
not a Management notification because `pendingNotifications`, `lastNotificationAt` and `activeNotificationSeverities`
are saved state, and a new notification kind would change the saved state of any park that reaches it. The copy (Pulse
label, Overview KPI and section, toast, `max N guests` above the ceiling) is `src/ui/capacityModel.ts`.

## Persistence

Parks are saved to IndexedDB (Phase 12, steps 1 and 2) and the profile (Phase 22: scenario records, unlocks, bonuses, the legacy Park Tour slice and the card collection; Phase 23 adds run statistics)
is JSON in localStorage under `parksmith-profile` (see Game modes and profile). The current save schema is **13** (the optional crowd field of a congestion-feedback park, see Crowd flow and neighborhoods (Phase 14); schema 12 added the one-shot ledger and run format 2, see Card pool (Phase 25) and The Map (runs); schema 11 added the run state of The Map; schema 10 added game mode and park grant, see Game modes and profile). Step 1 is the typed serialization boundary below;
step 2 is the store, autosave and the save/load UI (next section but one). Step 3 is snapshot undo
(see Construction undo) and interrupted-session recovery (last bullet of the storage section).

**One state module.** Every owner's state type lives in `src/game/save/state.ts`, which the owners
import as types only, and each of `GameWorld`, `GuestSimulation`, `RideSimulation`, `ShopSimulation`,
`OperationsSimulation`, `ScenerySimulation`, `ProgressionSimulation`, `ManagementSimulation`,
`ScenarioSimulation` and `SimulationClock` implements `Serializable<State>`. A save is plain data
only: objects, arrays, finite numbers, strings, booleans and null; no `undefined`, `-0`, `NaN`, `Map`,
`Set`, class instance or function (enforced by `plainData.ts` and a walk over a full 1,000-guest
save). Maps become arrays of entries in iteration order, because Map order is simulation-relevant
(guests in spawn order drive RNG draws; ride, service, bin and litter order drive float sums and tie
breaks), and `GameWorld.paths` is saved in insertion order for the same reason. Every float
accumulator is saved as the exact double, never a rounded snapshot. `serialize()` is pure (it never
steps, syncs, drains events, calls `snapshot()` or draws from the RNG) and deep-copies;
`restore()` validates the whole state before changing anything (`SaveError('invalid-state')` naming
the owner and path), then resets and applies in place, keeping container identity.

**What is saved, derived and left out.** Saved: everything that influences the future, including
the guest RNG state and every id generator. Derived and invalidated on restore, never saved: both
`PathNetwork`s, the guest destination caches, scenery sources and snapshot (the score field itself
is saved bit-exact, sparsely), management's connectivity cache, bin capacity, the occupancy grid.
Version counters (`version`, `pathVersion`, every `routeVersion`) are saved verbatim and the caches
keyed by them are reset to "never synced", so a restored stale route is still stale. Left out on
purpose: construction undo (cleared on restore), UI selection, renderer state, the profile, the
clock accumulator and perf counters. The clock and the view rotation live in the envelope
(`ParkSave.app`), not in the park state (`app.tourNodeId` stays in the format for older builds and is always written null since Phase 23).

**Sessions.** `ParkSession.serialize()` returns a `ParkSaveV4` (schema 4; schema 1 lacked `onboarding`, schema 2 lacked `calendar` and schema 3 lacked `weather`, the opening-hours fields and `rules.wetWeatherMultiplier`, migrated by `SAVE_MIGRATIONS[0]`, `[1]` and `[2]`, see the frozen fixtures in `src/game/save/fixtures`; `SAVE_CONTENT_VERSION` was 2 because an old park continues under the arrival curve and the weather, was 3 from Phase 16, see Content, themes and research scale, and is 4 since Phase 14, see Crowd flow and neighborhoods): scenario id, ordered card ids, seed,
the compiled ruleset (stored, so a card or scenario rebalance cannot change a park in progress) and
one state per owner. `onboarding` (the First Day tracker, `src/game/onboarding`) exists in a Sandbox park and is `null` in a scenario park, mirroring `scenario`; the migration marks existing sandbox parks as dismissed. `calendar` (`src/game/calendar`, Phase 20) is the park clock: the day number and the time of day are a PURE function of `world.tick` plus a tiny saved anchor (`dayLengthSeconds`, `anchorTick`, `anchorUnits` in 1e-6 day, `timeLock`), so there is no accumulator to drift, pausing and the 2x/4x speeds need no special case, and a sandbox day-length change re-anchors at the current tick so the clock stays continuous. Tick 0 is day 1, 06:00; migration 2->3 gives old parks the default 720 s day anchored at tick 0 (their age). The setters are refused in a scenario park. Gameplay (step 2) must read the RAW `clockFraction`, never the `effectiveFraction` the look and HUD use, so a fixed look cannot starve the park. Undo rewinds the calendar with the park but the two settings (day length, fixed time) survive it, like the First Day dismissals (`ParkCalendar.adoptSettings` in `GameApp.restoreSnapshot`); a setting change is an unsaved change through `GameApp.saveVersion()` (the version the save manager compares: a counter above the world version), not an undo snapshot. `ParkSession.fromState(state)` always builds a FRESH session (constructor
options `rules`, `seed`, `seedScenarioContent: false`) and restores owners in `RESTORE_ORDER`
(world, scenery, calendar, weather, rides, shops, guests, operations, progression, management, onboarding, scenario) after
`checkSessionConsistency` has checked what spans owners on the plain data (queue and rider ids
against guests and guest states, id generators against referenced ids, progression and management
counters against the runtime). A failed load discards the half-built session, so the live park is
never at risk, and every failure is a `SaveError` with a stable `code`. `sessionFromSave(raw)`
(`src/game/session/fromSave.ts`; `ParkSession.fromSave` until Phase 34) adds the migration entry point (`migrateSave`
in `src/game/save/migrate.ts`: version check, plain-data check, ordered chain of
single-step migrations; `too-new` and `no-migration-path` are surfaced, never silently dropped). Since Phase 34 the
chain and the load-side envelope checks are in `migrate.ts`, which only the lazy load path imports; `version.ts` keeps
the envelope types, `SaveError`, `createParkSave` and `contentDriftOf` (see Bundle and chunks under Renderers).
`restoreState` restores in place into a session of the same scenario and ruleset (the future
snapshot-undo path). A save is only legal between steps and after `ParkSession.syncWithWorld()`
for any world edit, because `serialize()` deliberately does not sync (a sync at save time would
apply edits at a different moment than the never-saved run does and change scenery float history). **Schema 6 (Phase 28)** adds the optional `colours` array on a placed object: migration 5 to 6 adds nothing (no record means defaults), restore normalises a bad record instead of refusing the save. **Schema 7 (Phase 28 step 2)** adds the park-level `world.gateColours` and the ruleset field `recolourCostMultiplier` (`ParkSaveV7`; `ParkSaveV6`, `V5` and `V4` are kept as deprecated aliases): migration 6 to 7 adds `recolourCostMultiplier: 1` and drops a hand-edited `gateColours`; see Colour customisation. **Schema 8 (Phase 24)** adds the top-level `map` key (the land: map id, biome id, entrance, ground rows, remaining props; `ParkSaveV8`, with `V7` and older as deprecated aliases) and, only when a biome changes them, `rules.hungerRateMultiplier` / `rules.thirstRateMultiplier`: migration 7 to 8 appends the frozen Meadow map (old saves are the Meadow Garden); see Biomes and maps. **Schema 13 (Phase 14)** adds the optional top-level `crowd` key (the rolling crowd field), present exactly when `rules.crowdFeedback` is: it is written right after `guests`, is not in `RESTORE_ORDER` (that would add a key to every save) and is restored explicitly after the guests; migration 12 to 13 is the identity (and drops a hand-edited `crowd` or `rules.crowdFeedback`, which a schema-12 build ignored). A bump rather than an optional key because an older build ignores unknown top-level keys and would silently drop the field; with 13 it reports `too-new` and keeps the save. See Crowd flow and neighborhoods (Phase 14). **Schema 14 (Phase 21)** adds four optional keys, each written only when it carries something, so every park without restricted land is byte-identical at 14: `world.land` (`{ parcelSize, owned }`, the ascending owned parcels of an estate), `rules.landCostMultiplier` (with the Phase 25 keys, only when != 1, last of them), `management.categoryTotals.land` (once a parcel has been bought; restore accepts 12 or 13 keys) and `scenario.latestMetrics.ownedParcels` (on restricted land). The saved map may be 32 to 64 cells a side in whole parcels (`isLegalMapSize`), and `maxSavedProps` is one per cell of the largest map (4,096). Migration 13 to 14 is the identity (it drops a hand-edited `world.land`, `rules.landCostMultiplier` or `latestMetrics.ownedParcels`, which a schema-13 build ignored); `ParkSaveV14` / `ParkRulesetStateV14`, the older names are aliases. See Land (Phase 21). **Schema 15 (Phase 29)** gives every guest record four fields (`nausea`, `warmth`, `souvenirs`, `activity`) and the three guest states `walkingToBench`, `resting` and `pausing`, and adds two optional keys written only when used: a litter pile's `sick: true` and `management.categoryTotals.souvenirSales` (restore accepts it like `land`). Migration 14 to 15 sets every saved guest to 0 / 50 / 0 / null (`ParkSaveV15`, an alias of the V14 shape with the wider guest record). **Phase 30, no bump:** a guest's optional `thoughtObjectId` (the building its complaint is about) is written only while not null, like a litter pile's `sick`, so a park with no live complaint is byte-identical at 15; restore reads absent or null as null, refuses anything but a non-negative integer, and keeps an id that names a demolished object (readers check the world). `checkSessionConsistency` also requires a resting or bench-bound guest's standing destination to be a bench.

**Determinism proof.** `src/game/save/determinism.test.ts` runs, per fixture park and per save
point, a reference run that is never saved against a twin that is serialized mid-run, JSON
round-tripped, restored into a fresh session and continued; it compares the hash of the whole state
every 50 ticks and at the end, every step's event stream, and public-API observables (cell
occupancy, placement checks, route order and distances, unlocks, next ids, the attributes of the
next spawned guests). `coverage.test.ts` makes a new simulation field fail until it is classified as
serialized, derived, config or transient. Known limit: `Math.hypot` is not guaranteed bit-identical
across JavaScript engines, so the proof is same-engine and hashes must not be compared across
engines. Persisted notification text in `management/parkStall.ts` uses `toLocaleString()`, so the
text, and any hash that includes it, can differ between locales; the tests run in one locale.

**Policy and limits of step 1.**
- *Seeded runs changed once.* `PathNetwork.connectedCells` now returns its component in a canonical
  (y, x) order instead of an order that depended on which cell was queried first. That history
  dependence would have made a restored run diverge from a never-saved one, so it was removed, but
  it changes every seeded run (wandering goals, entrance tie-breaks): a deliberate behaviour change.
  Re-check `BALANCE_NOTES.md` and scenario tuning against the new order.
- *Validation is per owner, and restore is not atomic across owners.* Each owner validates its own
  state before it changes anything; `ParkSession.restoreState` restores owner by owner, and the
  world notifies its listeners before the others have restored, so a caller must re-sync
  subscribers afterwards. `fromState`, which builds a fresh session, has no such window and is the
  load path. The snapshot undo in step 3 has to handle this.
- *Ranges.* `src/game/save/ranges.ts` bounds every saved number (counters, seconds, money, prices)
  far outside any healthy park, because a finite but absurd value such as 1e300 can hang the first
  step (an unbounded `while (timer >= interval)`) or hand out colliding ids. The bounds are
  deliberately generous, and each one is a promise to old saves.
- *Integrity is not authenticity.* The envelope carries `stateHash`, which detects damage and
  truncation, not editing: a player can edit cash, rules, locked ids, research ids (without
  prerequisite checks), the run state or scenario progress. Nothing outside the park itself (profile
  unlocks, run rewards, achievements) may trust a save without re-verifying (`rewardEligible`, `runRewardEligible`).
- *Saving.* `serialize()` throws `SaveError('unsynced')` unless `ParkSession.syncWithWorld()` has
  run for every edit, so an unloadable save is never written. `createParkSave` (which hashes) takes
  about 30 ms at 1,000 guests and belongs off the frame; `serialize()` alone is about 3 ms.
- *Size and content drift.* A 1,000-guest save is 0.7 to 1.0 MB of JSON depending on the park, 93%
  of it guests (routes alone 18%). `sessionFromSave` returns `{ session, save, contentDrift }`; what to do about a catalog change
  between save and load (scenery scores throw `content-mismatch` today) is a step 2 decision.

**Storage, autosave and loading (step 2).** All of it lives in `src/app/saves` and is driven by
`GameApp`; the simulation knows nothing about it.
- *Store.* `SaveStore` is a list of slots keyed by a closed set of ids, `autosave`, `autosave-previous`
  (Phase 31) and `manual-1` to `manual-10`. A build from before Phase 31 does not know `autosave-previous` and
  lists that record as an unreadable "Unknown slot" orphan, which it can only delete. IndexedDB database `parksmith-saves` has two object stores: `slots` holds metadata
  (name, scenario, park time, saved-at, schema version, guests, cash, rating, size, a `revision`) and
  `payloads` the save itself, and one read-write transaction writes both, so the list never describes
  a payload that failed to land. `list()` reads only the metadata. The payload is a structured-cloned
  plain object, never a JSON string. When IndexedDB is missing, blocked, over quota or refused (private
  mode), `createSaveStore` falls back to a memory store with the reason, and `retry()` re-opens
  IndexedDB and migrates the in-memory slots into it without overwriting anything.
- *Autosave.* `SaveManager` saves every 120 s of real time while the park has changed (at least 20 s
  apart), 15 s after a park starts (not immediately, which would overwrite the previous autosave in
  the same frame), at a scenario result, and best-effort when the tab is hidden. It captures from the
  ticker at a step boundary (`serialize()` is about 3 ms), then a module Web Worker (`saveWorker.ts`)
  hashes (`createParkSave`, 40-90 ms) and writes through its own IndexedDB connection, so the main
  thread only runs the capture and one `postMessage`. Without Workers an idle-time writer does the
  same work in one slice. Saves are single-flight and coalesced. `Ctrl+S` quick-saves from the world
  context only, and always prevents the browser's own save dialog.
- *Two autosave generations (Phase 31).* Every autosave write rotates: in ONE read-write transaction the store
  moves the record in `autosave` (meta and payload, re-keyed, the target's revision advanced) to
  `autosave-previous`, replacing what was there, and then puts the new save (`StoreWriteOptions.rotateTo`, set for
  every autosave by `persistJob.ts` `writeOptionsFor`, so the worker and the idle writer both rotate; the rules are
  `planRotation` / `rotatedRecord` in `memorySaveStore.ts`, shared by both stores). A failed put, a quota abort or a
  refused write leaves both generations as they were. Nothing rotates out of an empty slot or out of a record the
  store calls unreadable. The writer rotates a record only when it is known good: either the write expects the
  revision this tab itself wrote or loaded, or the record passes the Phase 30 integrity check first
  (`mustVerifyBeforeWrite`: the first autosave of a page session, and any write without an expectation); a record
  that fails is refused, marked unreadable and quarantined to a manual slot, so the save that follows finds the slot
  empty and the good previous generation stays. Every reader that means "the autosave" goes through
  `autosaveGenerations.ts`: `resumableAutosave` (the current generation when readable, else the previous one) and
  `continuableSlots` (at most one generation) feed Continue, the start screen's preview, `latestSave`,
  `latestRunSlot` and crash recovery. The previous generation is read-only (load and delete only; never a manual or
  quick-save target, no rename). Deleting the readable autosave deletes both generations; deleting an unreadable one
  keeps the previous as the fallback (`slotsToDelete`).
- *Two tabs.* Every slot has a `revision`. Autosave sends the revision this tab last wrote or loaded
  and conflicts if another tab has written since; a conflict suspends autosave in that tab behind a
  banner, and manual saves compare revisions too, so two tabs cannot silently overwrite each other. A
  `BroadcastChannel` refreshes the lists.
- *Unreadable saves are never discarded.* A record that is corrupt, damaged, from a newer schema or
  without a migration is listed with its reason, can only be deleted by the player, and is never
  overwritten: an unreadable autosave is first moved to a free manual slot ("Unreadable autosave: …").
  The one exception is the rolling `autosave-previous` slot: a rotation replaces whatever it holds, because
  it only ever holds an older copy of a park the current autosave has moved past.
- *Failure.* Persistence trouble is handled as `ProfileManager` handles storage: the park keeps running
  in memory, a banner says persistence is unavailable (with the code, for example storage full) and
  offers Retry, and nothing crashes.
- *Preview.* The start screen builds a park from a slot without installing it (`SaveManager.loadPreview`, then `adoptPreview` when the player continues); see Menus.
- *Loading.* The player picks a slot in the Save / Load dialog (confirmation when the live park has
  unsaved changes). The load path is imported lazily (`app/saves/loadSave.ts`, which alone reaches `sessionFromSave`
  and the migration chain, so they are its chunk since Phase 34), migrates and validates,
  and only then does `GameApp` swap sessions as `startScenario` does (`setSession`, listeners, input
  context, `clock.resetAccumulator()`, speed), restore the clock and the view from the envelope, settle a
  run stage that ended without its run hearing of it (Phase 23), and refresh management and the UI before the
  first paint. A failed load leaves the live park untouched.
- *Interrupted-session recovery (step 3).* A tab that runs a park holds an exclusive Web Lock `parksmith-session-lock:<id>` and a localStorage marker `parksmith-session:<id>` (`src/app/saves/recoveryMonitor.ts`). The lock is taken first and the marker second; `pagehide` removes the marker first and releases the lock second, so a marker whose lock is free can only mean a death without cleanup (a crash, a kill, power loss). A normal close or reload is therefore never an interruption, and a second live tab is skipped because its lock is held. Without Web Locks the monitor falls back to heartbeat staleness (45 s visible, 30 min hidden); without localStorage it does nothing. The monitor's id is also the SaveManager's `tabId`, so an offer is made only when the autosave was written by the interrupted tab itself. Since Phase 31 the detection gets both generations: when the current autosave is unreadable or was quarantined and the previous one was written by the interrupted tab, the previous generation is offered (`RecoveryOffer.autosave.slotId`, the prompt says the last autosave could not be read), and Resume and "Not now" act on that slot. GameApp holds autosave in its constructor and `RecoveryController.start()` runs once after `saves.init()`: with an offer the autosave stays held (park-start, interval, scenario-result and hide saves are all suspended) until the player resolves it. Resume loads the autosave through the normal load flow; "Not now" moves it, never deletes it, to a free manual slot named "Recovered autosave" (`keepAutosaveAsRecovered`, like the unreadable-autosave quarantine) and then releases autosave. Escape does not decide. Verified in headless Chromium with `Page.crash`: offer, Resume (state hash equal to the autosave's, 1,000 guests), Not now, reload and tab close (no prompt), two tabs (no prompt while the first lives, a prompt after it crashed). Limits: a browser-discarded tab looks like a crash and is offered; the offer never reads the payload, so an autosave that turns out unreadable is flagged only on Resume.
- *Known limits.* Closing a tab cannot be awaited: the worker write after `pagehide` landed in about
  one of four tests, so an unsaved change can be lost (a `beforeunload` prompt appears while edits
  are unsaved, but not in developer mode). The 8 ms main-thread budget for a capture holds at 1x CPU
  but not at 6x throttle (capture 14-25 ms plus a 20-32 ms clone, in separate tasks); no long task was
  attributable to a save at 1x, but 50-163 ms tasks remain possible at 6x. Two autosave generations exist since
  Phase 31 (above), so a bad autosave write costs at most one generation. The first-autosave integrity check covers every checksummed schema since Phase 30 (the hash
  is over the plain state at the schema it was written at, as `migrateSave` checks it). The worker URL assumes
  the app is served from `/`.

## Game modes and profile (Phase 22)

**Mode.** `GameMode = 'sandbox' | 'scenario' | 'run'` (`src/game/modes/types.ts`) is typed in the session (`ParkSession.mode`, constructor option, invariant: Sandbox if and only if no scenario definition, a `RangeError` at construction and `SaveError('invalid-state')` on restore) and in the save (state and header). `scenario` is a park started from the Scenario browser (`startPark({ mode: 'scenario', ... })`; `startScenario(id, cards)` is the same); `run` is **The Map** (Phase 23, see The Map (runs)): a stage of a run, started only through the run commands, never through `startPark`. Recolour cost derives from the mode (`colourCostModeOf`: run -> `map`; still 0 everywhere). **History:** in Phase 22 the menu entry opened the Park Tour as an interim and parks started there had mode `run`; Phase 23 retired that (schema 11 migrates such a save to a Scenario park).

**Save schema 10.** State v10 is v9 plus two keys written last, after `map`: `mode` and `grant` (`ParkGrantState`: the profile-gated catalog ids this park may build and the permanent bonus ids compiled into its rules, both canonical-ordered and unique); the envelope header gains `mode` (so slot lists read it without the state). `SAVE_MIGRATIONS[8]` (9 to 10) drops any hand-edited `mode`/`grant`, then sets mode by `scenarioId` (null -> sandbox, otherwise scenario; **an old Park Tour save reads as Scenario**; until Phase 23 GameApp also kept restoring its tour node, and since then the node is ignored) and an empty grant; `SAVE_CONTENT_VERSION` stays 2. Restore validation rejects (never trusts): an unknown mode, a mode that disagrees with `scenarioId`, a malformed or over-long grant, duplicates, wrong order, a non-gated id in the unlocks (`invalid-state`), unknown building or bonus ids (`content-mismatch`), a bonus not allowed in the mode, bonus-only ruleset keys out of range, and more active cards than the slots plus the bonus slot. The ruleset is used as saved, never recompiled. Frozen fixtures `src/game/save/fixtures/park-v9-*.json` (sandbox on the meadow, sandbox on a generated map, scenario, tour) were captured from the v9 code before `state.ts` was touched and play on their pre-change hashes. Slot metadata (`SaveSlotMeta.mode`, optional) is written from the header; a record without it, or with a hostile value (dropped by `parseSlotMeta`), reads as `legacyModeOf(scenarioId)` (`slotMode` in `app/saves/mapMeta.ts`).

**Layer order and the bonus layer.** `compileParkRules(scenario, cards, biome, bonus)`: base -> biome -> scenario -> **profile bonuses** -> cards -> safety clamps. The layer (`profile/bonuses.ts`, `compileBonusLayer`) is small, bounded and listed: Nest egg (+$500 starting cash), Research grant (15 starting research points), Builder's discount (construction x0.97), Spare card slot (+1 slot in Scenario and The Map), Word of mouth (arrivals x0.97 interval), Trusted crew (staff wages x0.95). Per-bonus and total clamps (`BONUS_CLAMPS`): cash <= min($1,000, 10% of the starting cash), research points <= 30, one extra slot, every factor in [0.95, 1.05] and per rule the product in [0.95, 1/0.95], upside-only, at most 8 bonuses; unknown, duplicate or out-of-mode ids are ignored. A neutral layer inserts nothing (the arithmetic is exactly the old chain), so a park without bonuses has a byte-identical ruleset. `startingResearchPoints?` and `extraCardSlots?` are optional ruleset keys written only when non-zero; cards can never touch them. Bonuses are never lost and never consumed; the way to play without them is the profile switch **Use permanent bonuses** per mode (defaults: on for Scenario and The Map, off for Sandbox, which keeps the First Day pacing of BALANCE_NOTES). No scenario requires a bonus, an unlock or a specific card (`noRequirement.test.ts`; each new scenario is proven winnable by a scripted bot with no card, unlock or bonus).

**Grant snapshot policy.** A park takes a snapshot of the profile when it **starts** (`ProfileManager.parkGrant(mode)`: every unlock, and the bonuses only when the mode's switch is on) and saves it; loading never reads the live profile. So an unlock applies to parks started after it, determinism and self-contained saves win over retroactivity, and the result text says so.

**Gated catalog entries.** `BuildDefinition.profileGate` marks entries built only when the park's grant holds them: Tiki Tumbler (Boardwalk Breeze), Cactus Cooler (Canyon Caravan), Cocoa Chalet (Frost Fair), Lantern Maple (Harvest Festival). They have no research project; in a park whose grant lacks them the build-access policy refuses them (`ParkSession.buildLockOf` -> `{ kind: 'profile', text }`) and the HUD shows LOCKED with the condition; in a park that holds them they are buildable from the start (the research tree is untouched, and the Phase 23 plan is that in a real run they become one cheap research project each). Their colours are existing catalog colours, so the voxel palette stays at 162 materials with unchanged texture bytes. Placement refusal text comes from `buildLockRefusal` (`app/placementFeedback.ts`): research keeps its words, a profile lock names the scenario that grants the entry, a scenario lock names the rule. Voxel art goes through the registry (`genericRide`, `kiosk`, and a real `lanternMaple` blueprint); classic art has a bespoke Tiki Tumbler, generic shop art and a maple branch in `classicObjectArt.ts`.

**Profile v2** (`src/game/profile/`, key `parksmith-profile`, owned by one `ProfileManager` with injected storage; the Park Tour's `TourManager` view was deleted in Phase 23, so there is exactly one writer and one reader). Content: cleared scenarios with records (clears, attempts, best clear seconds, best progress, how first cleared), unlocked buildings, earned bonuses, the per-mode switches, mode statistics (parks started, wins, losses), discovered cards, the legacy Park Tour slice (route, owned cards, epoch: read, validated and merged, never written by gameplay since Phase 23), the run statistics slice (Phase 23) and one one-time notice. Corruption-safe like the settings store: a missing key on writable storage is a fresh profile written at once (and a first run, so Phase 13 is unchanged); v1 is migrated and the original text copied once to `parksmith-profile-v1-backup`; every successful write also copies the v2 text to `parksmith-profile-v2-shadow`, and any v1 or garbage read later (a stale pre-Phase-22 tab reads v2 as unreadable and writes a fresh v1 over the key) is merged with that shadow, and a v1 arriving through the `storage` event is merged and written back at once, so an old tab can never erase scenario records, unlocks or bonuses; garbage is copied to `parksmith-profile-corrupt-backup` and replaced; a **newer** version is read-only (a fresh in-memory profile that is never written, `persistence: 'read-only'`); throwing, full or blocked storage never blocks a start (`'unavailable'`, in-memory). Every field is validated per entry (unknown ids dropped, counters clamped, hostile keys ignored). Every write is read-merge-write with a monotonic `mergeProfiles` (unions, max, min best time, the higher tour epoch wins), and a `storage` event calls `applyExternal`, so two tabs never erase each other's progress and a win in one shows in the other's Collection without a reload. GameApp publishes the snapshot to the UI store only when its revision moves (a start, a result, a switch, another tab), never per frame; a test pins zero profile publishes over 120 steady frames.

**Park Tour conversion (decision, Phase 22; the Tour itself was retired in Phase 23).** Converted, not retired: a v1 profile's route, discovered cards and flags are kept verbatim, and every completed tour node counts as a clear of its scenario (`firstClearVia: 'tour-conversion'`, best time unknown), which grants that scenario's rewards retroactively and opens the scenarios that depend on it. A one-time notice on the start menu tells the player what carried over (`Got it` / `Open Collection`). Frozen fixtures `src/game/profile/__fixtures__/profile-v1-*.json` pin the conversion.

**Results and rewards (`GameApp.handleScenarioEvents`).** A result is recorded in the profile by `recordScenarioResult`: rewards are **per scenario, once** (the first clear in Scenario mode or on The Map; a tour clear still advances the route), later clears only improve the record. `rewardEligible(session)` recompiles the ruleset a park started in this game would have and compares it with the one the park plays under: a hand-edited save shows its result and grants nothing. The result carries `ScenarioRewardResult` (new unlocks, bonuses, scenarios now available, new best, eligibility) in the store as `scenarioRewards`. The card draft comes from the profile collection (Scenario mode only; a run stage drafts nothing, its offers replace the draft). Retry keeps scenario, seed, cards and **mode**; the grant is read again like any new park.

**GameApp flows.** `startPark(request)` is the one entry for a new Sandbox or Scenario park (`ParkStartRequest`, in `gameBridge.ts`); `startScenario`, `menuNewPark`, `startSandboxMap` and the restart go through it; runs go through `startRun` / `startRunStage`. Menu commands: `menuOpenTheMap`, `menuStartScenario`, `openParksChooser`, `setUseBonuses`, `dismissProfileNotice`, `menuLoadSlot`. The store carries `sessionMode`, `parkTitle` (Phase 33: the top bar's park name, `parkTitleOf` in `ui/modeLabels.ts`: the scenario or Map level name, else the Sandbox map's name), `activeBonuses` and `profileLocks` (written at a session swap only, mode and grant being fixed for a park's life; `parkTitle` also by the full `syncUi`, so the first park has it) beside `profile` and `scenarioRewards`. The autosave is one slot for every mode (two generations since Phase 31); its metadata and the recovery marker (`gameMode`, optional, marker version still 1, a bad value ignored) carry the mode, the offer text names it (`RecoveryOffer.mode`, the autosave's own mode first), and the kept copy is named `Recovered autosave (Scenario)` (`recoveredSlotName`, `isRecoveredSlotName`).

**Scenarios as data.** `ScenarioDefinition` gained `mapId`, `difficulty`, `unlockedBy` and `rewards` (unlocks and bonuses). The four shipped scenarios keep their rules and map byte for byte (pinned by identity hashes from before the change) and gained rewards and difficulty only. ## The Map (runs) (Phase 23)

**What it is.** The default roguelite mode: a **run** is a fixed route of levels (`GAME_CONFIG.run.levelCount`, 5), each a generated park in a biome, cleared in order with a **deck of cards that are used up**. Level 1 is always Meadow, levels 2 to 5 are distinct biomes. The player starts with 3 cards, is **offered 2 cards before every level and all of them join the deck** (`offerRule: { kind: 'all' }`; `{ kind: 'pick', pick: N }` is data with a tested branch, the UI ships `all`), then **chooses distinct cards from the deck** as the loadout, counted by slot cost (slots 1, 1, 2, 2, 3 plus the grant's Spare card slot; a rare costs 2). Loadout cards are **consumed when the stage starts** (`consumeAt: 'stage-start'`; `'stage-clear'` is data with a tested branch); since Phase 25 an unplayed one-shot goes back to the deck when the stage resolves (`unplayedOneShots`, see Card pool (Phase 25)). Failing a stage ends the run; clearing the last level is victory. No run currency, no shop, no retries (a replay of the same seed is the retry), one fixed route (`levels[]` is an array; branching would add `nextLevelIndices` and a format bump). All numbers are PROVISIONAL (BALANCE_NOTES). Everything pure is in `src/game/run/` (builder A); the app side is `GameApp` (run lifecycle, hold, persistence), `app/runSlots.ts`, `app/saves/runMeta.ts`; the screens are `src/ui/Run*`.

**Run state (`RunStateV2` since Phase 25, `run/types.ts`).** Plain data, seeded, hash-covered: `version` (`RUN_FORMAT_VERSION`, 2: format 1 lacked the plan key `unplayedOneShots` and the per-level `playedCardIds` and `unpaidDebt`), `planVersion` (`RUN_PLAN_VERSION`, bumped whenever `planRun` output changes for any seed; digests in `plan.test.ts` pin it; 2 after the Phase 23 review, 3 for the Phase 25 pool and keyed draw, 4 for the Phase 25 retune), `seed`, `difficulty` (relaxed | standard | tough), `consumeAt`, `offerRule`, `unplayedOneShots` (`'return'` or `'consume'`, from `GAME_CONFIG.run` at run start), `grant` (the profile's gift **snapshotted once at run start**, mode `run`: a mid-run profile change cannot alter a run), `levels[]` (biome, the accepted generator recipe, `parkSeed`, objective family and `ObjectiveDefinition`, deadline in days (per difficulty since plan version 4: `GAME_CONFIG.run.difficulties[d].deadlineDays`, the `levels[]` rows no longer hold one), start cash, structured `conditionIds`, base slots, the offer), `starterDeck`, `levelIndex`, `parkLevelIndex` (the level the session's park belongs to), `phase` (offer | loadout | stage | won | lost), `deck` (a multiset in canonical order), `usedPile`, `loadout`, `offersSeen`, `history` (one result per finished level; format 2 adds the one-shots played and the debt left, `playedCardIds` and `unpaidDebt`). Same seed and difficulty give the same levels, maps, objectives, conditions, starter deck and offers on any profile (the profile changes only the grant). RNG: the run has its own streams hashed from `(seed, stream, level)` (`run/rng.ts`), never the guest RNG and never a clock; `planRun` is cross-process tested. Levels use the Phase 24 generator with recipes fixed at run start and an acceptance test (cleared area, a clear entrance corridor; 16 attempts, then 16 low-density dry ones); objectives come from the existing families (visitors, profit, crowd, spirits) scaled by the level table and the difficulty (plan version 2: crowd, a park-size goal, only on levels 1-2; spirits holds that lengthen with the level and with `spiritsSecondsScale`; level 5 draws visitors or profit, so the level, not the family, sets the curve); conditions (`run/content.ts`) compose by multiplication into the stage's scenario rules, with conflict protection (no Bin strike with spirits or crowd, no Wet spell in the desert).

**Transitions (pure, `run/deck.ts`).** `createRun`, `acceptOffer` (offer -> loadout), `validateLoadout` / `startStage` (loadout -> stage, builds the state a NEW session is made from), `resolveStage` (stage -> next offer | won | lost), `abandonRun` (any open phase -> lost). Terminal phases refuse everything. `isRunTransition(prev, next)` is the one guard a live session accepts (`ParkSession.advanceRun`): only acceptOffer, resolveStage and abandonRun results with an unchanged plan and park level. Profile rewards (`run/rewards.ts`): `runOutcomeOf` (won or lost, levels cleared, every card that joined the deck) and `runRewardEligible` (the planned part of the run must be exactly what this build plans for its seed: a hand-edited run plays but never earns).

**Stage.** A stage is a `ParkSession` in mode `run` on `generateMap(level.recipe)` with `stageDefinitionOf(run, i, entrance)` (scenario id `the-map-stage`, name `Level 3 · Desert Canyon`, the level objective and deadline, the starting cash `levelStartingCashOf(run, i)` (the level's cash minus the previous level's `unpaidDebt`, never below 0), the conditions' merged copy, `cardSlots`, no unlock and no reward draft). The compiled ruleset is the existing chain: base -> biome -> scenario (level cash plus conditions) -> **bonuses (the run's grant snapshot, mode `run`)** -> cards (the loadout) -> clamps. The session takes the run as an option (required exactly in mode `run`), exposes `run` and `advanceRun`, and serializes it as the **last key** of the state (only in mode `run`: Sandbox and Scenario states are byte-identical to schema 10). `fromState` rebuilds the definition from the run, so a save cannot disagree with its run (loadout, grant, seed, recipe, and the scenario status against the run phase are all checked).

**Save schema 10 -> 11.** `ParkSaveV11 = ParkSaveV10 & { run?: RunStateV1 }`, `run` present exactly when `mode === 'run'`. Frozen v10 fixtures (`src/game/save/fixtures/park-v10-*.json`, captured from the v10 code before `state.ts` was touched; sandbox on the meadow and on a generated map, scenario, scenario in a biome, and the interim Map's `park-v10-run-tour.json`) play on their old hashes. The migration drops any hand-edited `run`, turns a v10 `run`-mode save (the Park Tour interim) into a **Scenario** park (its grant is kept; every bonus that applies in `run` also applies in `scenario`, a test proves the tables agree) and changes nothing else. Hostile run state is **refused, never normalised** (Phase 12 policy; `run/validate.ts` checks shape, ids, indices, history, card conservation as multisets, copy cap, then the session cross-checks): invalid-state, or content-mismatch for an unknown id. A run saved by another `GENERATOR_VERSION` cannot rebuild its map: loading it fails with a message, and a stage that cannot be built ends the run as abandoned, counting no loss.

**Save schema 11 -> 12 (Phase 25).** `ParkSaveV12` adds `plays` (the one-shot ledger, `CardPlaysState`), present exactly in mode `run` and written after `grant`, before `run` (`run` stays last), and the run becomes format 2. `SAVE_MIGRATIONS` 11 -> 12 is a frozen literal: it drops any hand-edited `plays`; a run save gets an empty ledger, `run.version` 2, `unplayedOneShots: 'return'` and `playedCardIds: []`, `unpaidDebt: 0` on every history entry; Sandbox and Scenario states are byte-identical across the bump. `SAVE_CONTENT_VERSION` stays 2. Six frozen v11 fixtures (`src/game/save/fixtures/park-v11-*.json`: Sandbox Meadow, a Scenario with cards and a grant, a biome Scenario, a run at a stage, the same run's backdrop, a won run) were captured on the v11 code before `state.ts` changed; `v11Fixtures.test.ts` pins their migration and their replay hashes. A run started under an older plan version loads and plays but finishes unrewarded (`runRewardEligible`); the Continue card says so from the slot header's `RunSummary.planVersion` (optional, written by `runSummaryOf` since Phase 25).

**The app lifecycle (`GameApp`, the run commands).** The UI calls the run commands through `runBridge` (`src/ui/runBridge.ts`, the `RunCommands` interface that `GameApp` implements and registers on mount: `startRun`, `continueRun`, `openRunMap`, `closeRunMap`, `acceptRunOffer`, `startRunStage`, `continueAfterStage`, `abandonRun`, `runEndAction`, `resolveLeaveRun`, `resolveMapOffer`; `gameBridge.menuOpenTheMap` stays for the menu entry); the app owns the run and when the run overlay opens, the screens own the sub-view inside a phase (`useUiStore`: `run` (a `runSnapshotOf` snapshot, rewritten only when the run changes), `runBonusIds`, `runView`, `runLoadoutSelection`, `runRewards`, `leaveRunPrompt`).
- `startRun(seed, difficulty)`: validates the seed (`isMapSeed`) and the difficulty (Tough needs a Standard or Tough victory in the profile), may raise "Leave the run?", then `createRun` with the profile grant, builds level 1's map and swaps in a **frozen backdrop** session (level 1's park, no cards, paused), counts `runs.started`, arms an autosave and opens the run map.
- **Hold.** Between two stages (phases offer, loadout, won, lost) the park on screen is a frozen backdrop (`runHold()`, derived from the run): `setSpeed` refuses anything but pause, world input is refused (`menuBlocksWorld`), Ctrl+Z says "Undo works inside a level", the save host is not "running", and the undo ring takes no entries.
- `acceptRunOffer` -> `acceptOffer` then `session.advanceRun`; `startRunStage(ids)` -> `startStage` (validates; consumes) -> `buildStage` -> a NEW `ParkSession` (a new-park swap clears the undo ring) at speed 1, `recordParkStarted('run')`, autosave armed. A `content-mismatch` from `buildStage` ends the run as abandoned.
- **Result.** Scenario events in a run stage never reach `recordScenarioResult` and draft nothing: `settleRunStage` -> `resolveStage` -> `advanceRun` -> speed 0, **undo ring cleared**, autosave armed, and the stage-result screen (`runView: 'stage-result'`), or at a terminal phase the end screen with the profile's answer (`recordRunResult`, below). The development hook `__parksmithDev.forceStageOutcome` (`forceStageOutcomeForDevelopment`) latches a result the way a real one does; the next step hands it to the app.
- `abandonRun` (a loss at the level reached, park seconds recorded inside a stage), `continueAfterStage`, `runEndAction('same-seed' | 'new-run' | 'main-menu')` ("Try this seed again" is a fresh run with the same levels; 'main-menu' also serves the run map's own Main menu: between stages it writes the autosave (`SaveManager.autosaveNow`) and leaves, inside a stage it uses the pause menu's quit flow). Escape in the run layers goes to the UI's `escapeRunLayer` (offer and loadout to the map, the map of a stage to the park, the hub between stages to the pause menu; a stage result and the end screens are decisions and are never dismissed).
- **Leaving an unfinished run** (a new run, a new park, a Scenario, a Load) is asked first (`leaveRunPrompt`, `raiseLeaveRun`): the autosave is the only slot (its previous generation is pushed out by the next autosave), so Save first opens Save / Load and keeps the question, Leave goes on, Cancel keeps the run. A Load picked in the Save / Load dialog closes the dialog before asking (the question is on top and answerable) and returns the failure code `deferred`, which the dialog and the menu show nothing for. **On the start screen** no run is live, but a new park still takes the autosave slot: the run at stake is the unfinished run either autosave generation holds (`autosavedRunAtStake` in `app/runSlots.ts`, the current generation first; loading the autosave itself or another save of the same seed and difficulty asks nothing), and the prompt names it (`LeaveRunPrompt.saved`) with Cancel (focused) and Leave only, since there is nothing live to save. The setup panel's note says the same: a run only the autosave keeps is replaced (Start run asks first); a run in its own slot stays.
- **Persistence.** `capturePark` adds `run: runSummaryOf(run)` (seed, difficulty, level n/N, biome, phase, levels cleared) to the slot metadata (`SaveSlotMeta.run`, dropped by `parseSlotMeta` when hostile via `app/saves/runMeta.ts`) and to the recovery offer (`RecoveryOffer.autosave.run`); every run boundary calls `runChanged()` (bumps the dirty revision and arms a safe-point autosave, the 20 s minimum gap still applies). `continueRun` loads the newest readable run save whose run has not ended (`latestRunSlot`); the ordinary Continue and crash recovery take the same load path. **Reconcile on load** (`adoptRunPark`): a stage whose scenario already ended while the run never heard of it (impossible for the app to write, possible in a hand-made file) is settled at once, but never rewarded: `ParkSession.fromState` marks a session whose scenario had already ended (`resultFromSave`, provenance kept outside the instance: not saved, hashed or part of the session graph) and `rewardEligible` refuses it, so a result only a save claims pays nothing (as in Scenario mode, where only live events record); then the right screen opens (stage: the paused park; offer and loadout: the run map; terminal: the end screen, and the profile record is idempotent so nothing is counted twice). A loaded stage starts paused like every loaded park.
- **Undo, recovery and two tabs.** The deck changes once, at `startStage`, before the stage session exists, so every undo image taken inside a stage carries the same run: a rewind restores the run byte for byte (`runHash` is equal before and after every rewind, tested). The ring is empty at every stage boundary (a new session, or the clear in the result handler), so no undo can bring back a consumed card, an accepted offer or a stage result. Recovery and the two-tab revision logic are unchanged: the run is inside the park save. Known limits: manual saves of an older moment allow save-scumming (an "ironman" option is a candidate); a tab on an older build drops the profile's `runs` slice (a pinned expected-fail test).

**Profile (run statistics, `profile/ProfileManager.ts`).** An optional `runs` slice of profile v2 (no version bump): `started`, `victories`, `losses` and `bestLevel` per difficulty, and the last 32 recorded run keys. `recordRunResult(input, eligible)` is idempotent per key: the app's key is `seed-difficulty-runHash(final run)`, so a reload of the same finished run counts nothing twice while "Try this seed again" is a new attempt that can improve the best level (the pure `runKeyOf` identifies the planned run, not the attempt, and is used only for eligibility proofs). A loss updates the loss counter and the best level; a victory also **discovers every card of the run's deck** and opens Tough for the first Standard or Tough victory: discovered cards and unlocks only, never raw power (no bonus, no cash, no building). `stats.run.parksStarted` counts stages started; wins and losses count runs.

**Park Tour retirement.** `TourManager`, the tour map and nodes in `ScenarioHud`, `resetTour`, the tour branch of the reward draft and the `tourStorage` option are deleted. Kept read-only for migration safety: `game/tour/{types,content}.ts` (the legacy ids), the profile's `tour` slice and `ui.mapSeen` (validated and merged, never written by gameplay), the conversion notice, and `ParkSaveAppState.tourNodeId` (validated, written null, ignored on load). The four hand-made tour parks live on as the scenarios Sunny Start, Penny Lane, Garden Gala and Starlight Finale in the Scenario browser; an old tour save reads as a Scenario park. There must be no dead UI: grep gates for `tour-node`, `TourMap` and `resetTour` in `src/ui` and `src/app` pass (a unit test pins them).

**Known limits.** One autosave slot, with one previous generation since Phase 31 (the leave-run prompt is what keeps a long run from being replaced silently); no run currency, shops or retries; manual-save scumming; a run made by an older map generator version cannot continue; the card pool and its limits are in Card pool (Phase 25); crowd is only an opening family (a three-ride park fills it on any level; a late crowd goal needs a bigger park, a Phase 25 lever).

## Card pool (Phase 25)

**Table, types, derived id.** The 48 cards are rows of `PULSE_CARD_TABLE` (`src/game/cards/table.ts`, data only, `as const satisfies readonly PulseCardRow[]`); `PulseCardId` is derived from it (`cards/types.ts`), so a card id the table does not hold is a compile error. Table order is canonical order (starter deck, offers, deck, Collection): the six shipped cards first with their ids and numbers unchanged (so no Scenario park loses `rewardEligible`), then the 42 Phase 25 cards. `content.ts` builds `PULSE_CARDS` / `CARD_BY_ID` with generated copy (`copy.ts`: `stageCardLines`, `oneShotLines`; `RULE_COPY` moved from `src/ui` to `cards/ruleCopy.ts`, typed per rule so a missing line is a compile error) and the slot cost; `slotCostOf`, `rarityOf`, `kindOf`, `slotCostTotal`. Adding a card is a row; every card test reads every row.

**Kinds.** `stage` (37): multipliers over `CARD_MODIFIABLE_RULES`, compiled once at session construction in the existing chain (base -> biome -> scenario -> bonuses -> cards -> clamps). `one-shot` (11): `modifiers: {}` (so the compile and `rewardEligible` need no branch), an `OneShotEffect` (`loan`, `research`, `repair` broken or all, `sweep`, `forecast`, `surge`, `cheer`) and an authored vector. A one-shot never touches the ruleset, the calendar, the weather chain's day kinds or the run.

**Rarity.** `GAME_CONFIG.run.rarity`: common / uncommon / rare = offer weight 6 / 3 / 2, first level an offer may hold it 1 / 2 / 3, slot cost 1 / 1 / 2, starter decks commons only, Scenario draft weight 6 / 3 / 2. Rarity is frequency and slot cost only: it is not an effect axis and never enters the compile; `rarity.static.test.ts` allows reading `rarity`, `slotCost` and `tags` only under `src/game/cards`, `src/game/run` and `src/ui`. Per-rarity magnitude bounds are a test (common factors in [0.6, 1.5] with two modifiers, uncommon [0.5, 1.6] with two or three, rare [0.6, 1.5] with exactly four: "two trades in one card", which the second slot pays for). The copy cap stays a flat 3.

**Effect vector and dominance (`cards/vector.ts`).** `effectVectorOf(card)`: a stage card's vector is derived, `ln(f)` for a higher-is-better rule and `-ln(f)` for a lower-is-better one (`MULTIPLIER_DIRECTION`; the compile multiplies, so log space adds); a one-shot's is authored in fixed units (cash in $1,000s, research in 10 RP, visitors in 10 guests, spirits in 10 points, booleans as +1, `queues` -1) and cross-checked against its effect numbers by a test. Positive is good for the player on every axis. `dominates(a, b)`: `>=` on every axis of either and `>` on one. `dominance.test.ts` asserts no ordered pair of the 48 dominates; the direction test gives every card an up and a down axis.

**The seven new rule keys.** Card-modifiable multipliers, base 1, compiled clamp [0.25, 4], restore range 0.01..100, listed in `OPTIONAL_RULE_KEYS` (`scenarios/rules.ts`): written in a save only when not 1 (`toPlainRuleset`), read as 1 when absent, so every save without such a card is byte-identical and every frozen fixture replays to its hash (`bitIdentity.test.ts`); at 1 every consumer computes exactly the old float. Consumers:

| key | dir | consumer |
|---|---|---|
| `weatherEffectMultiplier` | lower | `WeatherSimulation.effectiveIntensity`: rain, storm and hot intensity x m; `sunny` is exempt (its effect is a bonus) |
| `nightArrivalMultiplier` | higher | `WeatherSimulation.refresh`: the arrival rate x m from 21:30 to 05:00 |
| `dayLengthMultiplier` | higher | the scenario/run calendar: `scenarioDayLengthSeconds` = round(720 x m) (`save/consistency.ts`, shared by the session and the consistency law); the deadline in seconds never moves |
| `crowdCapacityMultiplier` | higher | `GuestSimulation.calculateOrganicGuestPotential`: the organic guest potential x m |
| `litterImpactMultiplier` | lower | `OperationsSimulation`: the litter penalty and the guests' cleanliness penalty x m (how much litter bothers, not how much there is) |
| `breakdownRateMultiplier` | lower | `RideSimulation.scaledBreakdownProbability`: failure probability x m, capped at 0.95 only when m is not 1 |
| `sceneryAppealMultiplier` | higher | `ScenerySimulation.collectSourceDescriptors`: each source's appeal x m before its signature, so a restore under the same rules rebuilds the same signature |

Opening hours were not added: closing the gate has no upside in this simulation (guests go home, arrivals stop, payroll does not shrink), so night arrivals and day length carry that family.

**One-shot path.** `cards/effects.ts`: `canPlay(effect, host)` (the hint: "The level is over", "No ride is broken", "Every ride is in top shape", "The park is clean", "The park is full", "No guests yet", "Not enough cash ($600)") and `applyOneShot(effect, host, name)` over a structural `OneShotHost` (no import of `session/`). The owner primitives are `rides.repairBroken` / `rides.serviceAll`, `operations.sweepLitter` / `emptyBins`, `weather.rewriteForecast` (writes the slots after the current one, never a day's `kind`), `guests.adjustHappiness`, `guests.spawnGuests` and `progression.grantResearchPoints`. All money goes through `world.postTransaction` (never `world.addMoney`, which bumps `world.version`); every card's transaction labels go through `classifyTransaction` in `copy.test.ts` and land in their declared category. A play runs between steps and leaves `world.version` alone.
- **Ledger.** `plays` (`CardPlaysState`: `played` {cardId, tick} in play order, `pending` {cardId, dueTick, amount, label, category} ascending) is owned by `cards/CardPlays.ts` and exists **exactly in mode `run`** (a session field, `ParkSession.plays`, null otherwise). It is not in `RESTORE_ORDER` (that would add a key to every Sandbox and Scenario save); like `run` it is restored explicitly after `scenario` and hashed through `serialize()`. `ParkSession.step` runs `plays.step` right after `world.advanceTick()` and only while the run is in phase `stage`, applying due costs with `postTransaction`.
- **`ParkSession.playCard(id)`** answers `{ ok: true, summary }` or `{ ok: false, reason: 'not-a-run' | 'unknown' | 'not-in-loadout' | 'not-one-shot' | 'already-played' | 'not-playable', hint? }`. The ruleset, the active cards and the run never change. `cardsSnapshot()` gives the UI `ActiveCardSnapshot` (kind, rarity, slot cost, `playState` stage / ready / played, `playable`, `hint`, `pending`).
- **App and undo stamp.** `RunCommands.playCard` (`runBridge.playCard`) -> `GameApp.playCard`: refused while swapping, destroyed, with no run, or between stages (`runHold()`: "One-shot cards are played during a level"); else `undo.begin('card')`, `session.playCard`, refusal -> `undo.abandon()` and a toast, success -> `noteCardPlay()`, commit, toast `Played <Name> · <summary>`. A play does not move `world.version`, and `SnapshotUndo.commit` keeps an entry only when the stamp moved, so `noteCardPlay` adds a `cardPlays` counter to the undo stamp (`world.version + (colourEdits + cardPlays) * 2**32`) and bumps `settingsRevision` (the save layer sees an unsaved change). Undo is a full park rewind: the card comes back ready, its cash and scheduled cost rewind, and the run is unchanged (it never changes inside a stage). New `UndoGestureKind` `'card'`.
- **Settlement.** `resolveStage` and `abandonRun` take `playedCardIds` and `unpaidDebt` (the app passes `stageLedgerOf(session, run)` from `settleRunStage`, `adoptRunPark` and an abandon inside a stage; defaults `[]` and 0). The history entry records both. Under `'return'` the stage's unplayed one-shots leave the used pile and go back to the deck (sorted); played ones stay used. `isRunTransition` replays the transition with the entry's plays and debt, so the guard is still "byte-equal to exactly one transition". A backdrop's `plays` must agree with its history entry (the ledger's restore laws get the entry as `settled`), and `advanceRun` refuses a result whose plays or debt differ from the ledger.
- **Debt.** A pending cost when the stage resolves is recorded as `unpaidDebt` and comes off the next level's starting cash (`levelStartingCashOf`, never below 0): a backdrop never steps, so without it a late loan would never be repaid. A pure function of the run, so a restore and `rewardEligible` agree. Debt after the last level is forgiven; the result and end screens show "Unpaid at the end: $X".
- **Validator laws** (`run/validate.ts`, `CardPlays.readCardPlays`; refused, never normalised): run `version` must be 2; `unplayedOneShots` one of the two; a history entry's `playedCardIds` distinct one-shots of its `cardIds` in loadout order (unknown id: content-mismatch), `unpaidDebt` an integer in 0..`MAXIMUM_SAVED_AMOUNT` and 0 when nothing was played; history and running loadouts within the slots by slot cost; the used pile per entry exactly what settlement leaves (stage-start: the loadout minus returned one-shots; stage-clear: on success stage cards and played ones, otherwise played only); conservation `deck + usedPile = starter + accepted offers` unchanged in form (a return is a move). Ledger: at most 5 played, distinct, one-shots of the loadout, ticks in 0..`world.tick`; at most 8 pending, each for a played card, due in `world.tick + 1 .. + 1,000,000`, amount negative and finite, label at most 80 characters, ascending.

**Keyed weighted draw (`run/rng.ts`).** `cardKey32(id)` (FNV-1a over UTF-16 code units) and `keyedWeightedDraw(base, candidates, n, accept)`: a card of integer weight w gets w keys `hash32(base, cardKey32(id), r)`; all keys are sorted (ties by id, then r) and walked, a card is taken the first time one of its keys comes up and `accept` passes. The first pick has probability exactly w / sum(w) using integer hashing and comparisons only (no engine-dependent float). Bases: offers `runHash32(seed, 'offer', level)`, starter `runHash32(seed, 'starter')`, the Scenario draft `hash32(seed, 0x25c0_0001, 0)`. **Stability means:** a card's keys depend only on (seed, stream, level, its own id), so adding a card later changes an old seed's offers only where the new card's own key wins a place (tested with a fake card); it does not freeze old offers, and any pool change is still a plan-version bump. `shuffled` stays for biomes and conditions.

**Offers, starter deck, draft.** `offerWeightOf`: 0 at the copy cap (3), before the rarity's first level, or when the card is dead in every biome still ahead; else the rarity weight. Offers are distinct and never hold both halves of an `OPPOSING_CARD_PAIRS` pair (12 pairs, each sharing an axis with opposite signs, tested); the starter deck draws commons only under the same rule. `draftRewardChoices` (Scenario) draws stage cards not owned with the draft weights and takes the three from different families while three remain.

**Card x biome rule (`cards/interaction.ts`).** An axis is dead in a biome when its effect cannot happen there; today only `wetWeatherMultiplier`, when the biome's stationary rain + storm share is below `GAME_CONFIG.run.deadWetShare` (0.10; Desert Canyon 0.047, the next lowest Meadow 0.206). A card is dead in a biome when every upside axis is dead there (`weak` exists as a state, unused). `deadCardIdsIn(biome)` feeds the plan's offer weights and the offer notes; `interaction.test.ts` prints the 48 x 6 table and pins the dead set (Dry Spell and Farmer's Almanac in the Desert Canyon), every card live in Meadow and in at least five biomes, tags agreeing with axes, and no downside axis dead anywhere.

**One-shots are The Map only** (an owner decision, defaulted 2026-10-13): Scenario loadouts and drafts use stage cards, and Scenario saves carry no `plays`.

**UI.** One shared `CardTile` (`src/ui/CardTile.tsx`, with `CardBadges`, `CardFacts`, `CardNotes`) in the offer, loadout, deck and used drawers, dashboard, Collection (grouped by family) and the Scenario loadout and draft; badge words in `runCopy.ts` (text, never colour alone). ## Biomes and maps (Phase 24, steps 1 and 2)

A park is played on a **map** in a **biome**. Both are data (`src/game/biomes/`, `src/game/maps/`), pure and versioned; the default, **Meadow Garden** (today's 32x32 lawn with the gate at the bottom, `(15, 31)`), is bit-identical to the park before this phase: a new sandbox, the dev park, every scenario and every older save hash and play exactly as they did (pinned in `session/defaultIdentity.review.test.ts` from a baseline captured before any change, and in the renderers' identity tests). Step 1 ships the data, seven hand-authored maps, both renderers, the simulation around obstacles, the generalised entrance, the weather mix and the Sandbox picker. **Step 2 (built, see Map generator below)** adds the procedural generator with its validators and seed fuzzing, map previews, the recipe in the save (schema 9) and the picker's Generate choice; the previews for the scenario list and The Map are exported (`mapPreviewOf`, `ui/MapPreview.tsx`) but those screens are Phase 22/23. **Phase 21 (built) lifted the size**: maps are 32 to 64 cells a side in whole parcels and may start with an owned area (see Land (Phase 21)); the seven maps of this phase stay 32 x 32 and wholly owned. **Phase 16** moved the theme vocabulary to `src/game/types.ts`; the biome's `sceneryThemes` drives only the build card's local-style chip, and every prop's `appeal` is still data only (see Content, themes and research scale).

**Data.** A `BiomeDefinition` has the ground palette (base `.`, alt `,` and water `~` as an even/odd colour pair each, soil, paving and curb that keep the candy path look, the classic grid and path-dot colours), a five-colour swatch strip for the picker, the **weather mix** (a column weight per weather kind that scales `GAME_CONFIG.weather.transitions` exactly like `wetWeatherMultiplier`, then renormalises; Meadow is all 1 and `x * 1 === x`, so its rows are bit-identical), a **temperature** (-1 cold to +1 hot; 0 skips the climate term), the **sandbox defaults** (day length preset and time-of-day lock, applied once to a NEW sandbox on that map; the player's switches win afterwards: only Autumn Forest differs from the live clock, relaxed days and a dusk look), two small **rule multipliers** (`hungerRateMultiplier`, `thirstRateMultiplier`, the biome layer of the ruleset: base, biome, scenario, cards, clamps; clamped 0.8 to 1.25, not card-modifiable in step 1, serialised only when not 1), the scenery theme hook and the prop legend. `PROP_KINDS` are 30 kinds, 3 to 6 per biome (trees, palms, cacti, boulders, snow drifts, logs, walls ...), each with a footprint (1x1, 2x1 or 2x2), a clearing price or `null` (permanent), a colour pair, a height class and `appeal: 0`. A `MapDefinition` (format version 1) is ASCII: `height` rows of `width` characters, `.` `,` `~` for ground, one `E` for the gate on the border (not a corner; its facing is the inward direction of that border), prop letters per the biome legend (`T t b R s` 1x1, `L` a 2x1 log pair, `X` a 2x2 block, `#` a permanent 1x1) and a seed; `startingObjects` (path stubs, a pre-built ride) are supported for scenarios but no shipped sandbox map uses them (a pre-laid path would complete First Day's first step for the player). `validateMapDefinition` (a test runs it over every map) guarantees a legal gate, the First Day apron (six lanes, twelve deep from the gate) free of props and water, at least 160 cells reachable from the gate without spending anything, at least 480 after clearing every clearable prop, at most 320 props and 40 prop cells in any 8x8 chunk (the voxel box budget). The seven maps:

| map | biome | gate | character |
|---|---|---|---|
| Meadow Garden | Meadow | south edge | the empty lawn (today) |
| Brookside Meadow | Meadow | south edge | a pond and brook, oak groves to buy through |
| Seaside Cove | Seaside | west edge | beach and sea, a palm line to clear for a seafront |
| Red Rock Canyon | Desert Canyon | north edge | a corridor between permanent walls, boulders choking the side passes |
| Frosted Hollow | Winter | south edge | an island of open snow inside a ring of pines, thin ice |
| Emerald Ruins | Jungle | east edge | a river with one land bridge, ruins on the north bank |
| Maple Ridge | Autumn Forest | south edge | dry-stone paddocks, every plot needs clearing, the walls never move |

**Loading.** `layoutOfMap(definition)` / `layoutOfMapId` build an immutable `MapLayout` once (ground bytes, entrance, props at start, a `groundKey` that names the land for renderer caches); `layoutFromState(saved)` builds one from a save. `new ParkSession(scenario, cards, { mapId | map | layout })`: a saved `map` wins over a ready `layout` over a `mapId` over the scenario's own `mapId` (default Meadow). A new sandbox takes the map's seed (Meadow: the old sandbox seed), the biome's sandbox clock defaults and the biome's rule layer before the weather is built; map starting objects are stamped like scenario setup. `GameWorld` takes the layout as a third constructor argument and exposes `map`, `width`, `height`, `entrance`, `entranceFacing`, `biome`, `groundAt`, `propAt`, `obstacleAt`, `isObstructed`, `props` and the transient `propRevision`.

**Props are a map layer, not placed objects.** They are not in `BUILD_CATALOG` (that would shift every plot tint and material id), consume no object id, and no owner that iterates `world.objects` has to learn to skip them: the estate overview, inspectors, paint and the scenery code never see them. A prop's cells are *obstructed*: `canPlacePath`, `canPlaceObject` and the coaster check refuse them (object placement reports the typed reason `'obstacle'`), as they refuse water, and guests therefore path around them with no pathfinding change (they only ever walk on path tiles). **Clearing** is the bulldozer: a clearable prop is removed for its `clearCost` times the park's construction multiplier (rounded), booked as a `land-clearing` ledger row that management reports under Construction (a new management category would have changed every save's `categoryTotals`), and it does not count as a demolition and refunds nothing. A permanent kind or too little cash refuses with a typed result (`permanent`, `funds`) and changes nothing. A snapshot undo restores the prop and the cash with no extra code. **Scenery appeal of props is 0 in step 1, declared**: natural appeal would need prop sources in the saved scenery state (a save-shape change for no Meadow benefit) and would turn clearing into a hidden appeal loss; Phase 16 wires `appeal` together with the theme affinity. **Water** is a ground kind: never buildable, never clearable, flush with the ground (no terrain height).

**The entrance is a map property.** `world.entrance` and `world.entranceFacing` are the only source: arrivals, departures, staff spawn, the connectivity floods, the First Day hint ring and both cameras read them. The only literal left is migration 7 to 8's frozen Meadow state (`save/migrate.ts` since Phase 34, commented), and a static test greps `src/{game,app,rendering}` for the old literals. `entranceFrame(entrance)` expresses a route as `(lateral, depth)` from the gate so a route, a test or the step-2 generator is written once (`onboarding/routeInFrame.ts` is the First Day route in that frame; the pacing test runs it on Meadow unchanged and on Red Rock Canyon). **Camera framing** is one shared pure rule, `src/rendering/entranceFraming.ts`: when the gate lies on the view's bottom edge (Meadow in view 0) the legacy framing applies relative to it (the cell 11 rows in front of the gate at 18 percent of the screen height, bit-identical to before); in every other view, and for any gate on another edge, the midpoint between the gate and the map centre is centred, so both stay on screen. The classic `focusEntrance` and the voxel camera call it; the menu sweep centres on `world.width / 2, world.height / 2` and is re-centred on every session swap (`CameraSweep.setCentre`). **The First Day path hint** names the screen direction the park runs from the live gate: GameApp publishes `world.entranceFacing` as the store's `gateFacing`, and the First Day card turns it into the view the player sees (`ui/firstDayModel.ts` `gateInwardOnScreen`, one of four isometric diagonals); `onboarding/content.ts` `layPathHint` words it. The Meadow gate in view 0 keeps the shipped `drag at least 6 tiles up from the gate` character for character; Red Rock Canyon's north gate reads `down and to the left` (`ui/firstDayGate.test.ts` checks every map and view against the projection).

**Weather and climate.** The mix enters `transitionRow` / `drawDay` / `stationaryDistribution` as an optional argument; the `WeatherSimulation` takes the biome's mix and temperature as config that is NOT saved (the drawn days are the saved future, so a later retune of a biome never rewrites a park's forecast; the biome id is saved in `map`). Same seed plus same biome gives the same weather; a different biome with the same seed differs only through its weights; day 1 stays sunny in every biome (First Day safety); Winter never draws `hot`. The **cold effect** is the heat effect generalised (`weather/climate.ts`, `GAME_CONFIG.weather.climate`): after the weather effects, and also with the weather switched off (climate belongs to the place), temperature above 0 adds cold-treat utility (5 points at +1) and takes away warm-food utility (3), and below 0 adds warm-food utility (8 at -1) and takes away cold-treat utility (6). Scale check: a full rain day is warm +7 / cold -5, so Winter is a permanent rainy-day appetite for warm food and Autumn Forest a third of it. No new `ParkConditions` field (the determinism observables spread that object). Thirst and hunger growth per biome go through the two rule multipliers (Desert thirst 1.12, Winter hunger 1.08 and thirst 0.9, ...). All of these are provisional demand numbers (BALANCE_NOTES.md).

**Rendering, classic (simple on purpose).** `drawTerrain` colours each cell from the biome by ground kind (an even and an odd diamond per kind; Meadow draws exactly the lawn it always did); the cache is keyed by the view class AND the map's `groundKey`, so a snapshot-undo swap or a Meadow to Meadow restart keeps its Graphics and a different map or biome redraws once. Paths use the biome's paving, curb and dot colours. The page backdrop behind the map is Meadow's own colour, a light tone of the ground elsewhere. `classicPropArt.ts` draws each prop kind as a few vector shapes (a crown on a trunk, a boulder, a capsule cactus, three snowballs, an iso block for walls and ruins, a rounded log along the view axis), ONE pooled `Graphics` per prop, created on sync, destroyed with its context when the prop is cleared (`propRevision` diff, so a steady frame and a sync with no change touch nothing), repositioned and re-sorted on a view turn and redrawn only for a 2x1 prop whose axis flips. Props are see-through candidates like objects (the same fader, the bulldozer's own target never fades). Nothing runs per frame.

**Rendering, voxel.** The voxel terrain takes its ground words from the biome (data in the palette rows and box words: no new shader, uniform or texture layout), the props are static chunk content compiled through the blueprint compiler, and the gate model is compiled at the quarter turn that matches an east or west gate. The palette grows from 131 to 162 of 256 materials (31 plain materials appended after the colour swatches, so every older material id is unchanged).

**Voxel numbers (labelled: these are the voxel renderer's measurements, recorded in `src/rendering/voxel/contracts/budgets.ts` and its tests as of this step, not classic figures).** Per prop kind at both quarter turns, a 1x1 prop is 3 to 113 boxes (the palm is the most expensive), a 2x1 log 37 to 108 and a 2x2 21 to 32, under `BOX_BUDGET.prop` 120, `propLong` 160 and `propLarge` 320. A shipped prop map as it starts holds about 7,870 static boxes (budget 9,100), its heaviest chunk about 1,416 (Seaside Cove; budget 1,650), clearing one prop rebuilds one chunk in about 0.27 ms median in Node (budget 3 ms), and the worst park built on a prop map is about 61,400 boxes (budget 70,700). The bulldoze ghost over a prop reuses the prop's cached flat model (the same 3 to 113 / 37 to 108 / 21 to 32 boxes as its chunk copy, uploaded once per hovered prop, never per frame), so it needs no budget of its own. The palette count is 162 of 256. Classic has no such budget: its props are one pooled `Graphics` each and a steady frame draws nothing.

**Hover, clear and ghost texts.** One module, `app/placementFeedback.ts`, words the refusals for the readout and the toast: an object ghost or a path over an obstacle says `Blocked by Red boulder · clear it for $180`, `Blocked by Canyon wall (it cannot be cleared)` or `Blocked by water`. The bulldozer's hover shows the headline `Clear Red boulder · $180` (the store's `previewTitle`) or `Canyon wall cannot be cleared` (invalid); a click toasts `Cleared Red boulder · -$180` (several: `Cleared 3 obstacles · -$210`; mixed with demolitions: `Demolished 4 tiles · $12 refunded · $140 clearing`); a refusal toasts the shortfall or the permanent text once per prop per drag and takes no undo snapshot. A drag over props is one undo entry (`Red boulder cleared`, `2 obstacles cleared`). **The in-world bulldoze preview** tells the three cases apart as well: both renderers take the diamond fill from one helper, `rendering/previewFill.ts`, which draws a clear that will happen in the demolition red (`0xff5f70`, also every object, path and empty-cell bulldoze preview, as before) and a refused one (a permanent prop, or a price the park cannot pay: GameApp passes `valid = false` only then) in slate (`0x8c97ad`); the cursor readout still says which refusal it is. In voxel the bulldozer over a prop also gets a ghost like a placed object (`ghost.ts` `resolveBulldozeProp`: the prop's cached flat model in place, tinted `GHOST_TINT_BULLDOZE` or the slate `GHOST_TINT_BULLDOZE_REFUSED`), so the see-through cutaway learns the prop's height and keeps the target drawn (before, a prop had no ghost, the cut key fell to its own front corner and the boulder the player was about to pay for was cut out of the picture).

**Save, schema 7 to 8.** `ParkSaveV8` adds a top-level `map` key (written LAST): the map id, the biome id, the size, the entrance with its facing, the ground rows and the REMAINING props with their positions (cleared obstacles are simply absent). ### Map generator (Phase 24, step 2)

**What it is.** `generateMap(recipe)` (`src/game/maps/generator/`) is a PURE function of a `MapRecipe` = `{ generatorVersion, biomeId, seed, density: low | normal | high, water }` (32x32 only; sizes wait for Phase 21). It returns `{ recipe, definition, layout, stats }`: an ordinary `MapDefinition` (rows plus the new optional `ground` rows) that `validateMapDefinition` accepts, built into the same immutable `MapLayout` a hand-made map uses (`layoutOfMap(definition, recipe)`; the id is `gen-<biome>-<seed>-<density letter><w|d>`, the name `Generated · seed N`). Hand-made maps are data and are never regenerated: nothing in the generator touches Meadow or any shipped map. Desert Canyon has no water option (`biomeWaterOption`); the recipe forces `water: false` there and a recipe that says otherwise is refused.

**Determinism.** Integer only: no `Math.random`, no clock, no floats, never the guest or weather RNG (the park seed of a generated sandbox is `recipe.seed`). Every random decision is a positional hash of `(salt, tag, a, b)` with the salt from `(seed, biome)`, so results do not depend on evaluation order; value noise and fbm use an exact integer smoothstep table (`noise.ts`). Pinned by golden hashes (3 seeds per biome plus Seaside low / high / dry and Meadow dry, `generator.golden.test.ts`), a corpus digest, a 1,000-run repeat test and a cross-process test that runs the generator in separate Node processes and in another order. The single pins are typical maps that reach no cap and run no repair, so the golden test also pins one digest over the 166 recipes of `generator/goldenCorpus.ts`: 108 sample maps plus 58 maps where a generator constant binds (found by changing each of `minimumOpenArea`, `maxGeneratedProps`, `chunkPropWeightCap`, `mapPropWeightCap` and `maxCarves` by one step over 4,000 recipes); a change of `GAME_CONFIG.maps.generator` that changes output therefore fails the golden test too (`generator.determinism.review.test.ts`, golden VERSION policy). `GENERATOR_VERSION` is bumped whenever any output changes, with new pins in the same change; the golden test fails on an accidental change, and a recipe from another version is refused by `generateMap` (`RangeError`). Version history: 1, the first generator; **2**, repair R2 also joins land stranded behind permanent props and water (of the 22 single pins only `autumn-forest:1` changed). A saved v1 recipe still restores (the stored map wins); it only cannot be regenerated by this build.

**Pipeline** (one pass plus a bounded repair, no retry loop): gate (on a border, off the corners, facing inward, on base ground; the Seaside sea is never on the gate side), reserved apron and halo (no props in the apron, no water in the halo, so water never touches the First Day apron), biome ground (water feature, alt patches, two integer smoothing passes, water capped at 40 percent), decision features per biome (walls, ring forest, palm line, pier, islets, a single land bridge), rule-based prop placement by noise with blue-noise spacing and per-kind rules, then repair, emit and a final `validateMapDefinition` (a failure throws `MapGeneratorBug`; the fuzz test shows it never happens). Repair guarantees an open (free) area of at least 400 cells and a cleared area of at least 640 connected to the gate: at most 24 corridor carves each, then at most one flatten of the core band, each step removing props or turning water into land, so it terminates and can never break a cap; the fallback flatten fired on 0 of 1,500 maps in every biome. R2 also joins land that no clearing could ever reach (cut off by permanent props and water only), within the same 24 carves, even when the 640 target is already met: before this, an Autumn Forest stone-wall line meeting the stream walled off up to 263 cells (181 of 500 seeds stranded some land); now every generated map strands 0 cells (`stats.stranded`, asserted by the fuzz test; the hand-made maps strand 0, Frosted Hollow 1). The caps (`GAME_CONFIG.maps.generator`): at most 300 props, 40 prop cells per 8x8 chunk (the validator's), and a prop box-weight per chunk (1,400) and per map (8,600) from `PROP_BOX_WEIGHT`, which holds upper bounds of each kind's voxel box count, so a generated map is inside the chunk and map box budgets by construction.

**Voxel numbers (labelled: these are the voxel renderer's measurements, recorded in `src/rendering/voxel/contracts/budgets.ts` and pinned by `scene/scene.generated.test.ts`; they are not classic figures).** The generator's `PROP_BOX_WEIGHT` values are game-side upper bounds of each kind's voxel box count, asserted against the compiled models. Over 500 seeds per biome at normal and high density, the heaviest prop chunk weighs 1,424 (Seaside, high, seed 70; 1,433 boxes in the real scene with its terrain and gate), and chunk overhead (terrain, gate) is at most 126 boxes, so a generated chunk stays within 1,400 + 126 <= `PROP_MAP_BOX_BUDGET.heaviestChunk` (1,650); the heaviest prop total is 8,312 plus at most 238 overhead, within `PROP_MAP_BOX_BUDGET.total` (9,100). For comparison the shipped maps measure 7,870 static boxes at most (Frosted Hollow) and a heaviest chunk of 1,003 (the refreshed Seaside Cove). The tide rock and the boardwalk pier are at most 40 boxes each.

**Tests.** `generator.test.ts` (rules per biome, entrance, water, density order), `generator.fuzz.test.ts` (500 seeds x 6 biomes x 3 densities: validator, connectivity, areas, no stranded land, entrance rules, chunk and map caps, no NaN, water rules, `buildFirstDayRoute` succeeds on a sample), `generator.repair.test.ts` (hostile drafts: the step counts are bounded and the measure never grows; stranded strips are joined; Autumn Forest 391 and seeds 0..199 strand nothing), `generator.golden.test.ts` (single pins and the corpus digest), `generator.crossprocess.test.ts`, `generator.perf.test.ts` (under 20 ms per map in Node), `generator.session.test.ts` (a generated layout drives a real `ParkSession`; the First Day route builds on every biome, density and facing), plus the 1,000-guest performance test on the heaviest generated map and `pacingMaps.test.ts` on generated seeds.

**Previews.** `maps/preview.ts` is pure (no WebGL, no DOM, no floats, no randomness): `renderMapPreview(layout, { cellPx: 4 | 2 })` makes a 128x128 (or 64x64) RGBA top-down image, north up, from the biome's ground colours and the prop kinds' colours, with a pink gate marker; a prop colour closer than an RGB distance of 72 to the ground under it is drawn in a contrasting ink (half or three quarters toward slate, else toward white), so snow drifts and snowmen on snow and red boulders on red ground show (`preview.test.ts`: every prop of every shipped map and of 3 seeds per biome changes at least 2 pixels by 60 or more); `previewHash` is an FNV-1a of the pixels (pinned for hand-made and generated maps); `mapPreviewOf(layout)` caches by ground key and prop list (LRU of 64; a hit returns the same object); `mapFactsOf` gives the gate edge, obstacle and water counts. It costs under 5 ms. `ui/MapPreview.tsx` draws an image with `putImageData` (nothing is drawn where there is no 2D context) and `previewDataUrl` gives a PNG data URL for `<img>` users; Phase 22/23 (scenario list, The Map) call these. Previews are for the picker now.

**The recipe in the save (schema 8 to 9).** `MapState.recipe` (last key inside `map`) is `null` for a hand-made map and the recipe for a generated one; the save still holds the full ground rows and the remaining props, so the stored state wins: restore validates the recipe (`readRecipe`: shape, uint32 seed, density, water only where the biome has it, the map's biome and `generatedMapId(recipe)` must match) and NEVER regenerates, so a later generator change cannot alter a park in progress and a recipe from a newer generator version is informational. **The Generate choice in the picker.** Each biome's map list ends with *Generate a map*, a third radio in the same group (End reaches it; changing biome while it is selected keeps Generate). ## Content, themes and research scale (Phase 16)

**Append only, nothing read live moves.** Phase 16 appends 12 entries to `BUILD_CATALOG` (after the Phase 22 gated four,

`ResearchProjectId` union. No existing stat, price, scenery appeal or radius, project link or milestone changed: those
are read live by saved parks (a changed scenery appeal or radius would even refuse the load, `content-mismatch`), and

**Theme vocabulary.** `SCENERY_THEME_IDS` and `SceneryThemeId` (garden, carnival, seaside, adventure, futuristic) moved

**Two optional ruleset keys, base layer.** `themeAffinity` (absent = 0) and `researchCostScale` (absent = 1)
(`PHASE16_RULE_KEYS`, `themeAffinityOf`, `researchCostScaleOf` in `scenarios/rules.ts`). `compileParkRules` reads them
from `GAME_CONFIG.scenery.themeAffinity.share` and `GAME_CONFIG.research.costScale` at compile time (not into the frozen

[`costScaleBounds` 1, 20], rounds to 0.001 and writes them only when non-neutral, as the LAST keys of the ruleset (after
the bonus keys). They are compiled for every new park in every mode; they are not card-modifiable, a scenario override
of them is ignored, and no bonus sets them. Tests set them through the session's `rules` option.

**Persistence.** Save schema stays **12**: the keys follow the Phase 25 precedent for optional multipliers.
`ParkSession` writes them last (`phase16KeysOf` in `toPlainRuleset`), so a park under neutral values serialises
byte-identically to before. Restore accepts an absent key (neutral), refuses a non-finite value or one outside [0, 0.5]
or [1, 20] (`invalid-state`), and drops an explicit neutral value. `SAVE_CONTENT_VERSION` is **3**: a v2 save loads with
"saved under an older balance" and keeps neither key, so it plays as it did (no theme affinity, research at scale 1);
an older build that loads a v3 save reports "a newer balance" and then refuses any object whose id it lacks
(`invalid-state`). `profile/eligibility.ts` leaves the two keys out of the ruleset comparison on both sides, so a

**Theme affinity, a derived scenery value.** `ScenerySimulation.rebuildDerivedSnapshot` adds, per themed destination
(a reachable ride or stall), `bonus = min(maximumBonus 10, matching x themeAffinity)`, where `matching` is the
footprint mean of the appeal field of same-theme sources only (sources in object-id order, appeal after
`sceneryAppealMultiplier`, the same radius falloff as appeal), rounded to 0.01; the destination's score is
`min(100, footprint average + bonus)` and feeds choice, satisfaction and the rating exactly as before. Only a non-zero

## Land (Phase 21)

One big map divided into square **parcels** (`GAME_CONFIG.land.parcelSize` = 8, the voxel static chunk); only owned
parcels can be built on and land is never sold back. Code: `src/game/land/parcels.ts` (pure geometry, the size rule
`isLegalMapSize`: 32 to 64 a side in whole parcels, the price) and `LandOwnership.ts` (the owned set and
`checkOwnedParcels`), owned by `GameWorld.land`.

**Restricted or not.** A map whose `ownedArea` is null (every 32 x 32 map, every save before schema 14) is
*unrestricted*: `LandOwnership` holds no array, owns every cell, offers nothing and is not saved, so the ownership checks
added to `canPlacePath`, `canPlaceCoasterPiece`, `canPlace`, `footprintConflict` and `checkClear` are no-ops and every old
park is bit-identical. An estate's `MapDefinition.ownedArea` (a parcel-aligned rectangle holding the gate, validated) or a
scenario's `ownedArea` override seeds a restricted set. Owned land only grows by buying a parcel that shares an edge with
it, so the set is always one edge-connected area holding the gate's parcel; restore enforces exactly that shape, the parcel
size, and that every path, object and coaster piece stands on owned land. A restored layout carries no `ownedArea`: the
save's `world.land` is the truth (absent = wholly owned).

**Buying.** `checkParcelPurchase(parcel)` returns the price or a typed refusal (`unrestricted`, `outside`, `owned`,
`not-adjacent`, `funds`); `buyParcel` charges it as a `land-purchase` transaction (management category `land`, saved only
once used), bumps `version` (every cache sees new land) and the transient `landRevision` (renderers). Price (pure,
`parcelPrice`): `round10((basePrice + perOwnedParcel x owned) x max(farFloor, 1 + nearPremium - perStep x d) x
landCostMultiplier)`, `d` the Chebyshev parcel distance to the gate's parcel. `landCostMultiplier` is a card-modifiable,
optional ruleset key (scenario override, bonus Land surveyor); the world gets it as config at construction.

**Placement and words.** The typed build reason `unowned` (a footprint touching unowned land; blocked beats unowned beats
obstacle), `ClearCheck`/`BulldozeResult` `unowned`, and one phrasing for every surface (`unownedLandMessage`,
`landHoverTitle`, `landRefusalText` in `app/placementFeedback.ts`). The **Land tool** (`ToolMode` `land`, key L, the
toolbar button only while `UiState.land` is non-null) previews the whole parcel and buys on click as one undo entry; the
pointer readout names unowned land. Since Phase 33 the Land button's tooltip and the Overview's Land KPI (shown only while
`UiState.land` is non-null) both read `describeLand` (`src/ui/landModel.ts`), so they cannot disagree.

**Rendering.** Voxel: `VoxelOverlays` has a land layer at the bottom (index 0; the hints moved to index 4): one dim quad
per unowned parcel (an axis-aligned square of cells is one screen diamond; 3/8 for sale now, 5/8 beyond), the fence
(`strokeOutline` round the owned cells, 2 texels) and a sign per parcel for sale, redrawn only when the world, its
`landRevision` or the view changes. The camera's plot (`setPlotBounds(w, h, x0, y0, maxMargin)`) is the owned land with the clamp
margin capped at one parcel, re-read on a land change; the entrance framing's "heart" is `world.heart`, the middle of the owned land (the map centre
when unrestricted, so every classic framing is unchanged). Map previews of a map larger than 32 x 32 render at 2 px a cell
and dim the land for sale under the props. The classic renderer (legacy) only gets the refusals, readouts and framing.

**Scale.** The voxel renderer, the crowd field, the scenery field and the path distance fields already read
`world.width/height`; `depthRangeFor(64, 64)` and 64 chunks fit their budgets (the map-wide box budgets are per 32 x 32 of
area). Map caps tuned on 32 x 32 (`maxProps`, `minimumClearedArea`) scale with the area (`areaScaledCap`); the open area is
measured inside the starting owned area. The generator makes classic 32 x 32 maps and, with `MapRecipe.size: 64`, estates: `SIZE`/`CELLS` in `generator/draft.ts` are live bindings `generateMap` sets for one synchronous run (`setDraftSize`, restored in a `finally`), `areaCap` scales the prop, weight and water caps, and `estateOwnedArea` gives the starting land (four parcels along the gate's edge, three deep).

white with an ink shadow, coloured by `tint`), anchored like the badges (object footprint centre and top, a guest's head,
or a ground point) and re-anchored on a view turn. A frame moves whole texels and eighths of alpha; reduced motion holds
them still. Its `version` joins the overlay sum, so the overlay target re-renders only while an effect changes.

**Cash pill** (`ui/cashPillModel.ts`, `useAnimatedCash` in Hud.tsx): a rAF tween only while the number moves, and a
delta chip for a change of $25 or more; the accessible label is the real cash.

**Audio** (`src/audio/`): `AudioEngine` over an injected `AudioContextLike` (Node tests use a fake; no Web Audio = silent)
with master -> five buses (music, ambience, rides, guests, ui), gains `(v / 100)^2` from the six settings. `unlock()` runs
on the first pointerdown or keydown (capture listeners, removed after): it creates the context, synthesises every cue and
the three loops (`synth.ts`, deterministic, 22,050 Hz, nothing fetched or decoded) and starts the loops silent.

(`RendererPort.readViewInfo?`, zoom fraction and the visible world rectangle, read at 4 Hz) and computes the crowd and
machinery beds from the guests and running rides in view and the zoom. A hidden page suspends the context.

## Crowd flow and neighborhoods (Phase 14)

Readability and a small, threshold-gated feedback on top of the existing path network and guest records: no collision,
no steering, no rerouting, no new entity type. Code in `src/game/crowd/` (simulation and derivations),
`src/app/crowdNotice.ts` (Pulse tracker), `src/ui/neighborhoodModel.ts` + `NeighborhoodsTab.tsx` (copy and tab) and the
voxel overlay. Numbers and evidence: BALANCE_NOTES.md "Phase 14".

**The field.** `CrowdSimulation` (`ParkSession.crowd`, every park has one) holds one `Uint32Array(width x height)` of
pressure. `GuestSimulation.walk` calls `noteEntry(cell)` (+`entryUnits` 1,024, clamped at 2^31 - 1) at the moment a
walking guest steps onto `route[routeIndex]` (the `distance <= movement` branch), so only guests already walking a route
(entering, wandering, walking to a ride or shop, leaving) generate it. `ParkSession.step` runs `crowd.beginTick()`
(every cell `p -= ceil(p / 320)`: a 32 s time constant that reaches exactly 0) right after `weather.step` and before
`guests.step`; factors read the live value, entries earlier in the same tick included, which a restored run reproduces
because saves happen only between steps. Integers only, no RNG draw, no float state, simulation time only. Guests a
minute = `p x 600 / (1024 x 320)` (`crowd/bands.ts` `flowPerMinute`). A removed path tile keeps its value and decays.

**Derived shape and bands.** `crowd/pathShape.ts` computes, per `pathVersion` (cache per world, `invalidatePathShape` on
restore), lane width = clamp(path tiles in the 3x3 block / 3, 1, 3), degree, components (ascending cell order) and
articulation points (iterative Tarjan). `bands.ts`: flow per lane = flow / lane width; `bandOf` quiet < 80, normal < 270,
busy < 450, severe (`GAME_CONFIG.crowd.bands`); `withHysteresis` (display only) rises at once and drops while the flow is
below 85 % of the band's lower edge; `isBottleneck` = severe AND (lane width 1 OR articulation). Load = flow per lane /
`laneCapacityPerMinute` 400.

**Feedback, new parks only.** The ruleset key `crowdFeedback` (`PHASE14_RULE_KEYS`, `crowdFeedbackOf`: absent = 0 = off)
is compiled for every new park in every mode from `GAME_CONFIG.crowd.feedback` (1) at compile time, clamped to
[0, `maximumFeedback` 1], rounded to 0.001 and written LAST (after the Phase 16 keys) only when non-zero
(`crowdFeedbackKeys`, `CROWD_FEEDBACK_COMPILED`); it is not card-modifiable, a scenario override is ignored, no bonus sets
it. `GuestSimulation.setCrowd(reader)` takes the session's field (a standalone `GuestSimulation` keeps the frozen
`NEUTRAL_CROWD_READER`). Movement onto a tile is multiplied by `speedFactorAt(target)` = `crowdSpeedFactor(load, s)`:
the literal `1` at load <= 1, when off or off the network, else `1 - s x min(0.4, 0.4 x (load - 1))` (floor 0.6). In
`updateNeeds` a MOVING guest (walk state with route steps left) on a severe tile loses `0.2 x s` happiness a second and,
if entering or wandering, thinks `CROWDED_THOUGHT` "It's so crowded here." (after the need thoughts, before "What a lovely
spot."); `INSIGHT_TEXT` maps it to "guests find the paths too crowded". Below load 1 the factor is an exact multiply by 1
and the happiness branch never runs, so such a park is bit-identical to one without the key (asserted in
`save/crowdDeterminism.test.ts`). With the rule off the field still runs: it is display only, outside the save and the
hash, and a test floods it mid-run to prove nothing reads it back.

**Persistence.** Schema 13, content 4 (see Persistence). `crowd` = `{ version: 1, pressure: [cell, value][] }`, sparse,
strictly ascending, values 1..2^31 - 1 (`MAXIMUM_CROWD_PRESSURE` in `ranges.ts`; `readCrowdState` in `consistency.ts`).
The presence law (`crowd` exists exactly when `rules.crowdFeedback` is non-zero) is checked three times: the envelope
(`corrupt`), `checkCrowdLaw` at the end of `checkSessionConsistency` and `restoreState` (`invalid-state`). Ruleset
restore: absent = off, an explicit 0 is dropped, a finite value in (0, 1] is kept, anything else is refused. Restore
puts the field back after the guests, then invalidates the path shape, the neighborhoods, the coverage and the display
memory. `profile/eligibility.ts` ignores `crowdFeedback` on both sides, so a Scenario or run park saved before Phase 14
stays reward-eligible. A park saved before Phase 14 (content 3 or older) loads with "saved under an older balance" and
never gains feedback. Undo goes through `serialize()`, so a feedback park rewinds its field; for a rule-off park
`GameApp.restoreSnapshot` calls `next.crowd.adoptDisplay(live.crowd)` (presentation only, like `adoptSettings`), so the
heatmap does not blank. Loading a rule-off park starts with an empty field that warms up in about 30 s.

**Frozen v13 fixtures** live in `src/game/save/fixtures/v13/` (`park-v13-sandbox-crowded.json`, a dev park at 487
guests with slowed, severe and bottleneck tiles over five neighborhoods; `park-v13-scenario.json`;
`park-v13-run-stage.json`; `v13Fixtures.test.ts`): a subfolder because `phase14Rules.test.ts` and `phase16Rules.test.ts`
sweep `fixtures/*.json` and assert that no fixture there carries `crowdFeedback` (or the Phase 16 keys), which is the
proof that the v1 to v12 fixtures never gain a rule. Never regenerate them; a config change that moves their 600-tick
pin is re-pinned with attribution.

**Neighborhoods** (`crowd/neighborhoods.ts`, pure, `neighborhoodsOf(world)` cached per world version, never saved, never
player-authored). (1) Rides with at least one adjacent path tile, in ascending id, join the cluster whose leader (its
first ride) is nearest within Chebyshev 6 cells and shares a path component, looked up in 8x8 grid buckets; otherwise
they lead a new cluster. (2) Territory: a layered multi-source BFS over path tiles from every cluster's access tiles plus
the gate (key 0, at most 4 steps); a tile goes to the nearest source, ties to the lower key. Paths whose component has no
ride belong to no neighborhood; a cluster whose every access tile is an older cluster's folds into it. (3) Members:
services, bins and benches by their lowest-index access tile with a territory, scenery by the nearest territory tile;
the rest are "unreached". (4) Identity: key = leader id; order gate first, then key. (5) Name (`crowd/names.ts`):
`hash32(biome + 1, anchor.x, anchor.y)` picks one of the biome's eight words and one of eight suffixes; a collision steps
the hash in key order, so an older neighborhood keeps its name; the gate is the biome's first word + "Gate". The gate
neighborhood exists only while at least one cluster does. (6) Sector: the territory centroid in a 3x3 split of the map,
world compass. Stability (tested over six real parks): non-ride buildings, litter, staff and guests never change the
list or any territory; a path tile changes the list only when it joins or splits components; a new ride never renames an
older neighborhood; removing a leader re-clusters its followers.

**Metrics and the view.** `aggregateNeighborhoods` (`crowd/metrics.ts`): one pass over guests, one over buildings
(rides and services are read from their runtimes and revenues, never recomputed). `coverageOf` (`crowd/coverage.ts`):
one multi-source BFS per service kind from OPEN services with path access, cached per path version and the open-service
signature; a tile is covered within `reachSteps` 16. `ParkSession.crowdView()` returns a `CrowdView` memoised per
(tick, world version, path version), a pure read (scenery is read only while synced); it carries `walkingByKey`,
`unreached` and `openServices` beside the neighborhoods. `crowdHeatmap(previous)` lists every path tile with its
displayed band and returns `previous` itself when no displayed band moved; revisions come from a process-wide counter,
so a new session never reuses a revision a renderer already drew. `crowdHoverAt(cell)` feeds the cursor readout. The
displayed bands of all three come from one hysteresis memory per session (`CrowdDisplay`), refreshed at most once per tick
or path change, never saved. `determinismHarness.ts` ignores the derived `shapes` and `crowdDisplay` in its live-graph
walk; crowd data is not in `management.snapshot()`, ride snapshots or `BuildingSnapshot`, so `observe()` needed no shim.

**Park Pulse.** `app/crowdNotice.ts` is the twin of `capacityNotice.ts`: a pure tracker driven by the session tick (a
paused park freezes it), reset to `INITIAL_CROWD_NOTICE` on every session swap and never saved, because a Management
notification would be saved state. A condition turns on after `holdSeconds` 10 (bottleneck; crowded = 25 % of its tiles
busy or worse; no food / drink / toilet within reach while one is open elsewhere and the neighborhood has >= 5 guests) or
`slowHoldSeconds` 20 (unhappy: mean below 50 with >= 10 guests; litter: >= 5 items) and off after `releaseSeconds` 20
without it. The HUD shows at most one line (priority bottleneck > crowded > coverage > unhappy > litter) beside the
capacity line; the tab lists every line, grouped by kind with at most three names ("... and 2 other neighborhoods").
Copy is `ui/neighborhoodModel.ts`; a test bans advice words from every line.

**App wiring.** On the 250 ms UI cadence `GameApp.publishCrowd()` runs `crowdView()` -> `stepCrowdNotice` ->
`buildCrowdUi` (rows only while the dashboard is open on Neighborhoods) -> the store only when `crowdUiEqual` says it
changed -> `setCrowdHeatmap` only when `crowdHeatmap(previous)` returned a new object, so a steady or paused park pushes
nothing. The hover line (pointer tool, heatmap on) also refreshes on every pointer move. `setCrowdHeatmapVisible` and
`setSceneryInfluenceVisible` are idempotent and exclusive both ways. `crowdHeatmapSupported` is published in
`attachRenderer` (mount and the GPU fallback); a classic renderer keeps the store off and a press toasts "The crowd
heatmap is drawn by the voxel renderer.". `focusNeighborhood(key)` focuses the worst tile when it is busy or worse, else
the territory tile nearest the centroid, with `focusCell(cell, 'ease')`, and turns the heatmap on when the live view has
a bottleneck there. Every session swap resets the tracker, drops the heatmap memo and pushes the new park's view (or
null) at once. `gameBridge.setCrowdHeatmapVisible` and `focusNeighborhood` are required commands.

**Configuration.** Everything is in `GAME_CONFIG.crowd`: `feedback` 1, `maximumFeedback` 1, `entryUnits` 1,024,
`decayDivisor` 320, `laneCapacityPerMinute` 400, `bands` 80 / 270 / 450, `hysteresis` 0.85, `speedPenaltyPerLoad` 0.4,
`minimumSpeedFactor` 0.6, `severeHappinessPerSecond` 0.2, `neighborhood` (`leaderRadius` 6, `bucketSize` 8, `gateSteps`
4, `reachSteps` 16) and `pulse` (holds, release and thresholds above). A changed `feedback` reaches new parks only.

## Custom coasters

Coaster design is pure data and pure functions: a layout is an ordered closed loop of track pieces (cell + height + optional special), validated per coaster type (height limits, allowed specials) and converted to a deterministic ride profile in `src/game/coaster/design.ts` with no world or rendering dependencies. A marble-physics speed sweep assigns each piece a travel time — chain lift up (or, on a free climb, a fixed-point momentum climb, see Lift hills), acceleration down drops, drag on flats, loop scrub, launch boosts — which yields duration, top speed, and the timing the renderer uses to move the train. Ground cells under track at clearance height stay open for walkways, and bulldozing removes the walkway before the track above it. The world stores built coasters beside placed objects, occupies every track cell, and answers two queries the rest of the game uses for all rides: `objectFootprint` (a coaster's whole track, a normal object's rectangle) and `rideProfile` (custom stats win over catalog stats). RideSimulation, guests, scenery, and management read profiles and footprints through those two calls, so a coaster behaves like any other ride — queues, cycles, tickets, wear, breakdowns, rating — without duplicated logic. Bulldozing any track cell removes the whole ride and refunds from the actually paid cost.

**Families (Phase 39).** `CoasterTypeDefinition.family` (`steel`, `wild-mouse`, `wooden`) picks the build rules in
`validateCoasterLayout` (a wild mouse turns only on the flat), the ride-model weights in
`GAME_CONFIG.coaster.families` (the `steel` row is the pre-family numbers, so every older coaster derives exactly what
it did) and the art: `TYPE_LOOK` per type, lattice bents (`emitCrossBrace`) for `wooden`, and a car kind per family
(`kindOf`: `mouse`, `timber`). New types are appended to the catalog and the research tree, so the determinism
harness's appended-content filters keep every pin.

**Crossings (Phase 38).** A layout may visit a cell again when the two pieces are at least
`GAME_CONFIG.coaster.trackClearanceLevels` (2) apart and neither is exclusive (`isExclusiveCoasterPiece`: a station
piece, a loop or boost, or the piece after a loop, which its ring overhangs); `validateCoasterLayout` raises
`overlapping` (same height), `crossing-too-close` or `crossing-not-allowed`. In the world, `occupancy` holds only the
ground occupant (entrance, non-coaster objects) and `trackLayers` every coaster piece per cell, lowest first, both
derived and rebuilt at restore (no schema change). `coasterPieceConflict` / `canPlaceCoasterPiece` check a piece
against paths (`pathClearanceHeight`), ground objects (a definition's `clearanceLevels`: track at `clearanceLevels + 1`
or higher may pass over it; absent = never) and other track; `canPlace` / `checkObjectBuild` check an object against
the track above it the same way. `objectAt` answers the ground occupant first, else the top-most track (so the
bulldozer takes a bench before the track over it, and the upper track before the lower); `objectsAt` lists every
object top first, and a repeated click on such a cell steps the selection down. The voxel track drops the support bent
of a piece with something under it (`hasSomethingUnder`, or a lower piece of its own layout); its neighbours carry it.
A crossing adds `coaster.crossing.excitement` (2) per crossing, up to 3; a layout without one takes the old
expressions. The classic renderer draws crossings without that support rule (it is frozen).

## Coaster centre line

Phase 27 step 1. A coaster's look comes from one pure curve, `src/game/coaster/centreLine.ts` (no Pixi, DOM, world or gameplay imports; `centreLine.test.ts` has its tests). `createCentreLine(pieces)` turns a layout into position and tangent per arc length (`sampleCentreLine`, allocation-free; `resampleCentreLine` for hot loops), and the voxel track, both trains, the designer ghost and the draft preview all read it, so the train rides exactly the rail that is drawn. **It is visual only**: ride stats, cycle time, cost, ratings, queue and dispatch, breakdowns and saves come from `design.ts` and `RideSimulation` and never see it (`gameplayInvariance.test.ts` pins them to golden values captured before the curve existed).

*Plan.* Every piece owns exactly its own tile. The line enters through the midpoint of the edge toward the previous piece and leaves through the midpoint of the edge toward the next, always perpendicular to the edge, so tangents match exactly at every join and a zig-zag of single-tile turns cannot collide (each arc stays inside its tile). A straight piece is a straight line one tile long; a turn is a quarter circle of radius half a tile (16 of 32 voxels, `CENTRE_LINE_CORNER_RADIUS`) around the tile corner it turns toward, π/4 of a tile long. A malformed layout (gaps, a U-turn) still yields a finite line.

*Height.* Height is a function of ground distance along the plan line: a monotone cubic Hermite spline (Fritsch-Carlson tangents) through the piece heights at the tile centres. A steady climb or fall keeps a steady slope, crests and dips have slope exactly zero so they are rounded curves, flats stay flat (the station never tilts), and it never overshoots, so a path under level 2 track keeps its clearance. Position and slope are continuous everywhere, tile edges included.

*Loops.* A loop special on a straight piece inserts a vertical ring of radius half a tile in the plane of travel on that piece's exit edge, once around, forward and up first and upside down over the top; its circumference adds to the arc length. A loop on a turn is ignored (the track content ignores it too). Since step 2 the ring is rotated by the track's pitch at its base so it enters and leaves along the ramp's own tangent (see Coaster structure).

*Units.* x, y in tiles in cell space, z in height levels, arc length in tiles; `COASTER_LEVEL_TILES` (13/32) converts a level to tiles, and a renderer scales: the voxel renderer by 32 voxels a tile and 13 (+5 for the rail top) a level, the classic renderer through its isometric projection with 13 px a level. Nothing depends on screen orientation, only on cell directions, so map rotation (Phase 26) needs no change here.

*Timing.* `coasterHeadIndex` (cell based, unchanged) says how far through the cycle the train is as a fractional piece index. `centreLineIndexToDistance` maps it onto arc length linearly inside each segment from piece centre to piece centre, monotonically, so the train is at every piece centre at exactly the second it always was and the lap time is unchanged; only the speed along the way follows the geometry (a corner is 0.79 of a straight tile). Cars sit 0.62 tiles of arc behind the head (`COASTER_CAR_SPACING_UNITS`) and interpolate through `stepFraction` exactly as before; at a cycle end the head wraps to the parked position (it stops up to 0.05 s of travel short because the stats round the cycle to 0.1 s, as before).

*Voxel track.* `content/coaster.ts` `pieceBoxes` lays the 32 x 32 columns of the piece's tile: a column is track when its centre is within 4 voxels of the centre line, its rail top is `round(13 z + 5)` plus the banking lift, and equal-top columns of each layer are merged into boxes by the existing greedy rectangle merge. A corner is therefore a staircase quarter circle of radius 16 plus or minus 4 and risers are one voxel, two where a steep climb meets a corner. What the layers are (two rails on ties over a spine, the chain, the brake, the supports, the station) is under Coaster structure below. The chunk path is unchanged: pieces are filed under their tile's chunk, a coaster change rebuilds those chunks once, and a steady frame rebuilds nothing. A piece's boxes depend on its neighbours up to two pieces away (the spline), which the chunk invalidation already covers because it marks every piece's chunk. `centreLineFor(pieces)` caches the line per array and re-checks the layout (cells, heights, specials and the `freeClimb` lift flag) on every call, so the draft's edited arrays, including a closed draft whose lift is toggled in place, are never stale. The station platform and canopy keep the far side and a turning station end drops the part of the platform inside the arc (`STATION_ARC_CLEARANCE`).

*Box cost.* Step 1 measured a flat straight piece at 3 to 6 boxes, a flat corner about 45 to 50, a corner that climbs about 80 and a crest corner up to 125; the dev park coaster was 444, the longest allowed layout (64 pieces, 44 corners, hills 0 to 4: `longestLayout()` in `testLayouts.ts`) 5,525. The step-2 structure costs are measured under Coaster structure and written into `BOX_BUDGET` (per piece kind, `COASTER_PIECE_BOX_ALLOWANCE` holds every fixture to them) and `COASTER_BOX_BUDGET` (whole coasters); the worst case stays under a quarter of the 30,000 developer-park budget.

*Draft and ghost.* A draft that can close (three pieces or more, the last beside the first) is shaped as the ring it will be built as. An open draft is shaped as `openLayoutRing`: a scratch piece behind the first and one ahead of the last, straight on and level, so neither end bends toward a neighbour that does not exist; only the real pieces are drawn. The voxel `CoasterDraft` and the classic preview both build that same ring, so they show the same curve, and the built coaster is the same boxes as its closed draft. Blocked cells and the closing hint are overlay and classic marks drawn on cells and are unchanged.

*Classic.* `WorldRenderer.drawCoasterTrack` strokes the structure `src/rendering/classicCoaster.ts` builds (see Coaster structure) once per construction, and loop rings are the projected vertical circle the train rides (previously a screen-space circle). A frame only moves the pre-built cars by transform: `syncCoasterTrains` uses scalars and one reused sample, no closures or arrays, and a test (`coasterClassic.test.ts`) requires zero drawing calls and no new displays over 10,000 steady frames with a running coaster, and the same screen spot as the voxel train (the classic car sits 1 px higher).

### Coaster structure

Phase 27 step 2. The structure of a coaster, in both renderers, is built from one cross-section frame per arc length (`sampleCentreLineFrame`, allocation-free): the tangent T, the plan left of travel N = (−dirY, dirX, 0) (on a loop ring the ring's axis, so the cross-section stays perpendicular to the ring plane all the way round), B = T × N (up on flat track, toward the centre on a ring), both rolled about T by the banking. **Banking** is `centreLineRollInPiece` / `centreLineRollAt`: exactly 0 on straights, rings and the station, and inside a corner `−turn · CENTRE_LINE_BANK_MAX · sin²(π · along / tileLength)`, a raised cosine over the corner's own arc (0 at both edges, C1 everywhere, 26° at the apex) signed so the outer rail rises; two same-sign corners dip to zero at their shared edge (accepted: a cross-tile blend would couple pieces across chunks). Roll never moves the centre line, so the train's position and timing are identical with or without it; step 3's cars read the roll of their own centre from `centreLineRollAt`. The rails sit at ±`CENTRE_LINE_HALF_GAUGE` (3/32 tile) along the rolled N, and `centreLineBankLift(across, roll) = across · tan(roll)` is the one formula both renderers quantise banking through. **Round loops**: a ring is a true circle of radius half a tile in the vertical plane along the tangent, rotated by the track's pitch α at its base (`ringEntryPitch`, stored on the line): ring(θ) = M + R sin θ F′ + R (1 − cos θ) U′ with F′ = cos α F + sin α Z and U′ = −sin α F + cos α Z, so it enters and leaves with the ramp's own tangent (the step-1 review's 27° kink on a ramped loop is gone); on a flat run (α = 0) it is the step-1 ring exactly, and the arc length is still 2πR so timing is unchanged. **Chain**: `line.chained[i]` says whether the segment from piece i's centre to piece i + 1's centre carries the lift chain; `centreLineChainedSegments` hard-codes the step-1 rule (every climbing segment, the test `coasterSpeedProfile` uses for lift speed) and `centreLineChainedHalf` maps it onto a piece's entry and exit halves, so step 4 (chain-or-free hills) swaps one helper for the piece's data and nothing else changes. Ties are laid by arc length on both renderers from `centreLineTieCount` / `centreLineTieAlong` (one every 4 voxels: 8 a straight, 7 a corner, 25 round a ring), and a piece's support bent stands at `centreLineSupportDistance` (7 voxels past its entry edge) with legs ±`CENTRE_LINE_SUPPORT_HALF_SPAN` (8 voxels) along the rolled normal, so on a corner the legs sit beside the arc and a banked corner's outer leg is taller. Nothing is placed from screen directions; the one camera-dependent choice is which side of the track the station platform takes (the far side, away from the camera: `classicFarSide` in the classic renderer, the voxel station's −x / −y rule). Under map rotation (Phase 26) the classic renderer re-evaluates `classicFarSide` per view; the voxel station is static world geometry and keeps its world side, so in view 2 the platform and canopy stand on the camera side of the track (a real 3D station seen from its platform, not a fault).

*Voxel structure* (`content/coaster.ts`, tests `coaster.test.ts`, `coaster.fuzz.test.ts`, `coasterBudget.test.ts`). The step-1 column layout stays: `pieceBoxes` walks the 32 × 32 columns of the piece's tile, projects each onto the piece's line (`projectOntoTile`) and keeps those within 4 voxels of it; each gets one rail-top `top = max(5, round(13 z + 5 + s · tan(roll)))` where `s` is the signed across in voxels toward the frame's N (a rail column uses its rail's centre, ±3, so a rail never steps across itself; the clamp keeps a ground-level corner's inner rail out of the ground, so at level 0 only the outer rail moves). Per column, three layers merged into boxes by the greedy rectangle merge on equal tops: the **lower layer** [top − 4, top − 2), the spine where |s| < 1 (on a station piece a STONE bed over the whole width: the station track stands in a paved pit), and a column whose spine bottom is at the path top (level 0) reaches one voxel further down on to the grass at `GROUND_TOP_Z`, because a coaster cell gets no paving or plot slab from the static world (`emitCoaster` files piece boxes only) and the game never lets a path share a cell with track under `pathClearanceHeight`, so the bed of ground-level track never floats (the split adds no boxes: the merge never joins columns of different tops); the **tie layer** [top − 2, top − 1) on columns [4k, 4k + 2) of the line with |s| < 3 (radial bars on a corner; the rails' outer column overhangs the tie by a voxel the camera cannot see, which costs a quarter fewer boxes on corners than 8-wide ties); the **top layer** [top − 1, top): the two rails at |s| ∈ [2, 4), and between them by priority the boost chevrons (BULB), the brake pad (CONCRETE, |s| < 2, along 6 to 26 of the last piece) and the chain (FENCE_RAIL dashes, |s| < 1, 4 on 4 off, on chained halves). **Supports**, one bent per piece of level ≥ 1 (never on the station, which is level 0, and none under a ring): the frame at `centreLineSupportDistance` places two 2 × 2 legs 8 voxels either side of the line on its plan normal (radially on a corner; the bank's tilt moves a rail by a voxel, not where a leg stands), each on a 4 × 4 STONE footing that stands on the grass at `GROUND_TOP_Z` and rises `SUPPORT_FOOTING_HEIGHT` (1) over the path top (`SUPPORT_FOOTING_Z` / `SUPPORT_FOOTING_TOP`; on a path tile under level-2+ track its lowest voxel is inside the paving, and the legs stand on `SUPPORT_FOOTING_TOP` either way), rising to the beam top zb = the lowest track bottom over the bent's strip (the spine bottom), so the beam [zb − 2, zb) meets the spine from below and nothing reaches into the track (tested per box: every support box ends at or under the track over it). Between the legs: a rung at z 23 when zb ≥ 27 (level 2 and up: the first member that may cross the along-track walkway corridor, above a 20-voxel guest), then one diagonal brace per 12-voxel bay (four 4-high steps that share a face) and a rung between bays; level 1 is legs and beam, level 2 adds the rung, level 3 a diagonal, level 4 two diagonals and a mid rung, and nothing floats (every support box touches a leg, the beam, a rung or the ground, tested per piece and through the real scene: the box under every footing of `hillDipLayout` on an empty park ends where the footing starts, which the step-2 review found false while footings started at the path top). The bent is rasterised per tile column from the frame's normal and tangent, so a corner's bent is a rotated staircase of columns, not a screen-aligned box. Walkway rule: on a piece of level ≥ 2 a leg whose footing would touch a corridor (3 voxels either side of the four lines from the tile centre to its edge midpoints, or the 4-voxel disc at the centre) is moved 2 voxels along the tile axis away from that corridor, up to four times, or dropped if that leaves the tile (the step-1 corridor test keeps passing on every fixture, random layout and random circuit). **Loop ring**: the rotated circle of the centre line (centre M + 16 · (−sin α, cos α) in (along, up)), rasterised in its (along, up) plane in three passes: rails in the annulus [16, 18) at |across| ∈ [2, 4), ties as 1.5-voxel radial bars every 4 voxels of ring arc at |across| < 2, the spine in [18, 20) at |across| < 1; voxels at or under the straight track's rail top are left to the straight track. **Station**: the step-1 platform (from the grass up to the rail top, for the same reason as the footings), accent edge, striped canopy, valance, bulbs and post, plus a queue gate (two 2 × 2 × 9 accent posts with a bar) at the entry end of piece 0 and a dispatch light (a 2 × 2 × 10 steel post with a 2 × 2 × 2 bulb) at the exit end of the last station piece, each only where the platform reaches that end; a turning first piece that the last piece's loop ring reaches over (the ring enters perpendicular to the station and reaches up to 28 voxels into the tile at canopy height) keeps its platform only. The brake fin is a 2 × 2 × 5 FENCE_POST beside the outer rail at along 28 of a straight last piece. **Colour by type** (`coasterLook`, the table the classic renderer shares): rails in the type's accent (0xffd166 yellow, 0x61e7d3 cyan, 0xf5f06c lemon), ties WOOD / the type colour (purple 0x7048c9, teal 0x1b7f79), spine TRACK / PANTS_DARK / INK, supports TIMBER / STEEL / STEEL_LIGHT; chain FENCE_RAIL, brake CONCRETE and FENCE_POST, footings STONE, bulbs BULB. Every material is an existing fixed material or a catalog colour: the palette stays at 122 of 256 slots, 0 added. **Measured box costs** (`counts` probe, written into `BOX_BUDGET` and `COASTER_BOX_BUDGET` with about 15 % headroom): a flat straight piece 11 at level 0 and 17 at level 2, a straight ramp 59 to 84, a straight crest 28 to 61, a flat corner 66 to 69 at level 0 and about 91 at level 2, a corner that climbs or falls 99 to 136, a crest corner 98 to 133, a loop piece 176 to 182, a station piece 18 to 96, a boost 23. Layouts, step 1 → step 2: the 16-piece dev park coaster 444 → 735, the 24-piece oval 433 → 798, the 32-piece zig-zag 1,128 → 1,634, the 32-piece hill-and-dip 954 → 1,505, the loop oval 693 → 1,140 and the longest allowed layout (64 pieces, 44 corners) 5,525 → 6,500 (6,547 with its train, 1,802 in its heaviest chunk; building all 64 pieces takes about 5 ms, the one frame that rebuilds its 5 chunks about 25 ms on the software path, and the scene test's 7,000-box ceiling still holds). Three 64-piece coasters on an otherwise empty map (two of the longest side by side and a 64-piece rectangle under them; a third serpentine does not fit 32 × 32) are 17,320 boxes with their trains, inside the 30,000 developer-park budget. Frame cost on the software rasteriser with the longest coaster running (`frametime.mjs`, 1280 × 800, 8 s, not representative of a GPU: SwiftShader rasterisation of about 920 ms of gpu-process CPU per frame dominates and hides the draw cost): the page's own frame callbacks take 0.71 ms mean / 1.0 ms p95 (step 1: 0.75 / 1.1), 15 draws a frame in both, so the structure costs nothing measurable on the CPU side and its real-GPU cost (about 1,000 more boxes on the worst-case coaster, 300 on a normal one) is still unmeasured.

*Classic structure* (`src/rendering/classicCoaster.ts`, pure, tested without Pixi in `classicCoaster.test.ts`; `WorldRenderer.drawCoasterTrack` strokes it). `buildClassicTrack(line, first, last, options)` returns plain screen-px arrays: the spine (the centre line sampled 4 times a straight piece, 8 a corner, 32 a ring), the left and right rails (the same samples offset ±3/32 tile along the rolled normal, projected with 32 px per tile of height, so banking shows as the outer rail rising about 1.3 px at a corner's apex and a ring's rails are the ring offset by its constant axis), ties as short strokes every 4 voxels of arc reaching 4.5/32 tile either side (8 a straight, 7 a corner, 25 a ring, centred on the line), supports, chain dashes, the brake, the station and boost chevrons. Supports: one bent per raised non-station piece (never under a ring) at the support distance: two legs from the ground to the bed 4 px under the rail line at P ± 8/32 N′ with per-leg heights, a beam at the lower of the two bed bottoms, footings as small ellipses, and bracing by height (a rung at 18 px when the bed is 22 px or higher, then one diagonal per 12 px bay, alternating, with a rung at every bay boundary: level 1 a beam only, level 2 one rung, level 3 a rung and a diagonal, level 4 four members). A leg keeps 4/32 tile from the two axis lines through its tile centre (the corridors a walkway under track at level 2+ runs along, 3 voxels plus the leg); when it is inside one it is pushed 2 voxels further out, twice, and dropped if that leaves the tile. The chain is static dashes (4 on, 4 off voxels of arc, phased by arc length so a dash never splits at a tile edge) along the centre line on chained halves, in the fence-rail grey. The brake is a light-steel strip over the middle 20/32 of the last piece (the run into the station) plus a fin post on its far side; the designer has no brake pieces (`design.ts` knows `loop | boost` only), so that is the only braking detail. The station (the first `stationLength` pieces at level 0) gets, on the far side: a stone platform 5/32 to 15/32 tile from the line with an edge in the type colour, a canopy in the type colour 22 px up with a valance in the rail colour, one post per piece, a gate (two posts and a bar, rail colour) at the entry end of piece 0 and a dispatch light (a post with a bulb) at the exit end of the last station piece; a station end that turns off toward the far side keeps only the 10/32 of platform clear of its arc, like the voxel station. Colour by type: rails in the type's accent, ties in its colour, a matching dark spine and support tone (comet-trail yellow rails on wood and timber, star-chaser cyan on purple and steel, skyline-serpent lemon on teal and dark steel); the draft is drawn from the type it belongs to (`drawCoasterDraft` takes the definition id, falling back to the catalog coaster with that colour). Draw order inside the one Graphics per coaster: supports, platform, spine, ties, rails, chain, brake, chevrons, then the canopy, posts, gate and light. The draft is drawn into one pooled Graphics (cleared and reused on every layout change, parked out of the layer when empty, destroyed with the renderer), the built coaster into one Graphics at construction, and nothing of the structure is touched per frame (`coasterClassic.test.ts`: the renderer strokes exactly the geometry's points, draws each coaster once per construction and never on a sync, zero drawing calls and no display churn over 10,000 frames, the pooled draft is never replaced, and a session swap releases the track displays). Leftover: the classic chain does not animate (static dashes; the voxel plan is a transform slot per chained straight piece driven from the ride's cycle clock, frozen when paused and under reduced motion).

### Coaster trains

Phase 27 step 3. Cars are placed by arc length exactly as before (spacing 0.62 tile, timing from `coasterTrain.ts`); only what a car looks like and how it leans changed. Visual only: no gameplay number, save field or hash is involved.

*Shared car frame* (`src/rendering/coasterCarFrame.ts`, pure, no Pixi or voxel imports, allocation-free). Both renderers place a car with `coasterCarFrame` / `resampleCoasterCarFrame`: the two bogie points sit 3 voxels of arc ahead of and behind the car's centre, the pivot is the midpoint of the chord between them (off the line by the sagitta only, under half a voxel) and the forward axis is that chord; the up axis is the banked cross-section's B′ at the centre (`resampleCentreLineFrame`) made orthogonal to it. Yaw, pitch and roll come out of one orthonormal basis, so a car leans into a turn and rides upside down round a loop without a special case, and nothing assumes a fixed heading (Phase 26). The same file owns the rider seats: `coasterCarSeats` spreads the type's train capacity over its cars, front cars taking the remainder (comet 3 3 3 3, star chaser 2 2 2 2 2, serpent 2 2 1 1 1 1), and `coasterLoadedCars` names the cars, front first, whose first seat is taken by the current head count while the ride is `running` (0 otherwise, and 0 for a running train with nobody aboard). A full train therefore shows exactly its capacity and a partial one at most one car's seats minus one over the real count (2 on the comet, 1 on the others). Riders are boxes and dots, never guests: nothing in the simulation reads them, and riding guests stay hidden as figures (`figures.ts`).

*Classic* (`src/rendering/classicTrain.ts`, built once per coaster by `createClassicTrain`, moved by `WorldRenderer.syncCoasterTrains`, tests in `coasterClassic.test.ts`). Each car is a pooled `Container` of three parts drawn once: wheels (two bogies peeking out under the hull), the hull (darker underside, accent stripe; the lead car is longer and has a nose cone, a headlight and a fin) and an `upper` container (two seat backs, two lap bars, and a `riders` child with one colourful dot per seat of that car). Three styles by coaster type (`classicTrainStyle`): comet-trail short blunt orange/amber cars with a round nose, star-chaser purple with a pointed nose and a cyan stripe, skyline-serpent slim teal with a long sharp nose and a yellow fin. A frame computes the shared car frame (one reused object) and sets, per car, the position (the projected pivot, on the same screen spot as the voxel car, 1 px higher), the rotation (the screen angle of the forward axis, so slope pitches the car) and `upper.position` from `classicCarLean` (the screen shift of the banked up vector against the unbanked one, at most a few px). Couplings are the pooled stretched segments between the tail of one car and the nose end of the next, so the gap stays closed on corners and crests. Riders show on the cars `coasterLoadedCars` names (`setClassicLoadedCars`: an integer compare per frame, visibility writes only when it changes), the same cars the voxel view fills. Nothing is drawn after construction; the 10,000-frame test requires zero drawing calls, no new displays, and a bulldoze releases every display.

*Voxel* (`content/coaster.ts` `carBlueprint` / `riderBlueprint` / `couplingBlueprint`, placed by `scene/coasterCars.ts`, compiled and uploaded once with the station's chunk by `staticWorld.ts`). A train is rigid parts on transform slots (`contracts/rigid.ts`): per car one car part (`coasterCarSlotKey`, 1000 + car), one rider part (`coasterRiderSlotKey`, 1100 + car) and, per coupling, two half-bars (`coasterCouplingSlotKey(car, half)`, 1200 + 2 · car + half), so 4 · cars − 2 slots: 14, 18 and 22 for comet, star chaser and serpent. A frame writes 7 floats per slot and rebuilds nothing; a parked train writes identical floats and dirties no transform row. Car models share one envelope (x [−5, 5) × y [−4, 4), ten voxels long so neighbouring cars clear each other inside a radius-16 loop): a navy chassis on four running wheels and four guide wheels, a body tub in the coaster's colour with a trim band, an open cockpit with two rows of accent seats and restraints (lap bars on the comet, over-the-shoulder hoops on the star chaser), a lead car with a clear front (comet: rounded nose with headlights and a star; star chaser: a pointed wedge with a fin; serpent: a snake's head, and a tail on its last car). Riders are a separate part per car with one rider per seat (`coasterCarSeats`; torso in a guest shirt colour, face, hair, raised arms on the looping types); a car that should be empty gets the collapse pose (`COLLAPSED_PART_QUATERNION`, zero-area quads) at its pivot rounded to whole voxels, so filling or emptying a train changes rows, never chunks. A coupling is two 8-voxel half-bars, each hinged at one car's hitch (4 voxels from the pivot along the car's axis, 2 above the rail top) and pointing along the hitch-to-hitch chord at the other hitch (`coasterCouplingHalfFrame`): together they close every measured hitch distance (9.4 to 15.6 voxels on the fixtures and 100 random circuits), and since one half never reaches the far hitch, no bar end can poke out under a car where neighbouring cars differ by 90 degrees (a single fixed bar had to tuck its surplus past a hitch along the chord and did). The designer's draft shows the same parked train on transform slots of the shared table, cars and couplings only, no riders; an open draft parks it on its own ring with a three-piece straight lead-in behind the station (`coasterDraft.ts` `trainRing`), because the track's open ring has a single scratch lead-in whose centre line runs backwards and the rear cars of the 5- and 6-car trains reach past piece 0. Numbers (boxes after compiling, `coasterBudget.test.ts` and `budgets.ts`): cars 37 + 3 × 27 = 118, riders 4 × 9, couplings 6 × 2: 166 for the comet; cars 45 + 4 × 32 = 173, riders 5 × 8, couplings 8 × 2: 229 for the star chaser; cars 46 + 4 × 31 + 35 = 205, riders 8 8 4 4 4 4, couplings 10 × 2: 257 for the serpent (before the review fixes 172, 261 and 311: four riders a car and one 16-voxel bar per coupling). The dev-park coaster is 735 boxes of track and 964 with its train, the longest allowed coaster 6,757 with its serpent, the heaviest chunk with a train 1,953, three 64-piece coasters 17,950; palette unchanged at 122 of 256 materials. Frame cost with the longest coaster running on the software GPU (SwiftShader, headless, 1280 × 800): 12 to 13 fps at a median 83 ms interval, rAF callback 0.65 ms, script 1.4 ms per frame, the same as before the train (the software rasteriser dominates; a real GPU is unmeasured). Trains freeze while paused (the head index comes from the simulation's cycle, not wall time), and nothing else on a train animates on its own. Known leftovers: wheels do not spin; the star chaser's raised arms and back-row hoop can touch the next car by under half a voxel inside a loop ring; a star chaser's back-row hoop can graze the ring of a loop whose next piece dips (seed 207, about 1.8 voxels); the two coupling halves overlap in the middle on a tight hitch distance (same material, so invisible).

### Lift hills: chained or free (Phase 27 step 4)

A deliberate gameplay change. An uphill run is either **chained** (the train is pulled at the steady lift speed, `speed.lift`, exactly as every coaster behaved before) or **free** (the train climbs on momentum). The choice is one flag per connected uphill run (a "lift": a maximal run of consecutive climbing segments, `liftRuns` in `src/game/coaster/lift.ts`), stored as `CoasterPiece.freeClimb?: true` on every piece of the run; a chained piece has no key at all, so an old layout has exactly the shape it always had. Validation refuses a flag on a piece that does not start a climbing segment (`lift-flag-not-climbing`) and a run whose pieces disagree (`lift-run-mixed`).

*Speed model* (`src/game/coaster/speedModel.ts`, one sweep around the circuit; `coasterSpeedProfile` / `coasterSpeedTrace` are re-exported from `design.ts`). The chained branches are the old code unchanged (`chainedEquivalence.test.ts` compares a frozen copy of the old profile, stats and cost with `Object.is`, so a chained coaster is bit-identical). The free branch is integer maths: speeds are whole milli-cells per second (`lift.speedScale` 1000), the speed squared falls by `lift.freeClimbLossPerLevel` per level climbed, the exit speed is the exact `integerSquareRoot` of that, and nothing may fall below the creep floor (`lift.creepPermille` of `speed.maximum`, 1.2 cells per second). A segment's travel time uses the mean of entry and exit speed, clamped to the floor, so there is no stall or rollback state in the simulation. The descent uses the existing drop boost, so a free hill after a drop keeps its speed. The sweep feeds the ride duration (a free climb is slower, a free hill after a drop is quicker than a chained one), the train timing in `coasterTrain.ts` (`travelSeconds`), the top speed and the stats; same layout, same profile (a test runs it 1000 times; the determinism harness covers a free layout).

*Rules around it.* The designer warns when a free run slows to the creep floor on one segment (`COASTER_LIFT_SLOW_TEXT`) and refuses it when more than `lift.maxCreepSegments` segments hit the floor (`free-climb-stalls`), computed from the model. The refusal counts per climb, not per run: free runs split only by flat track add up (a flat gives back too little speed to count as a fresh start), and a drop, a chained climb or a boost starts the count again (`analyseLiftRuns`). Free runs give a small bounded bonus to excitement and intensity and cost a little reliability (a train that takes its hills on momentum is harder on wheels and brakes: the chain's upside, so a free hill after a drop is never better on every axis); a chained piece costs `lift.chainCostPerPiece` more (scaled by the ruleset's `chainLiftCostMultiplier`, default 1, plumbed through `coasterBaseCost`; no card uses it yet) and adds a little running cost. The inspector's chain cost line (`describeCoasterLift`) is the ledger's difference against the same layout with every lift free, under the session's chain lift, construction and ride operating multipliers, so it matches what the build and each cycle actually charged. All constants are PROVISIONAL (BALANCE_NOTES.md).

*Rendering.* The chain strip is data-driven: `centreLineChainedSegments` marks a segment chained when it climbs and its piece is not `freeClimb`, and both renderers read `line.chained` through `centreLineChainedHalf`, so no renderer change was needed for the strip itself. Two rendering details matter: the game's `openLayoutRing` (the open draft's ring) drops `freeClimb`, so both renderers build their draft ring with `openDraftRing` (`src/rendering/draftRing.ts`), which copies the flag back; and the voxel draft's change signature (`coasterDraft.ts`) includes the flag (bit 8 of the piece code) so toggling a lift rebuilds the strip. Tests: `content/coasterLift.test.ts` (built pieces and both draft shapes) and a chain case in `classicCoaster.test.ts`.

*Save.* The schema is 5: `SAVE_MIGRATIONS[3]` upgrades schema 4, in which every uphill piece was chained, so the migration only drops any hand-edited `freeClimb` key, adds the `chainLiftCostMultiplier` rule (1) and leaves the saved stats (which already contain the chain) untouched; the frozen v4 fixtures (`park-v4-sandbox-coaster.json`, `park-v4-scenario.json`) were captured from the old code before `state.ts` changed. `World.deserialise` rejects a `freeClimb` that is not `true`, and the layout validation above rejects flags off a climb and mixed runs. A toggle is an ordinary coaster edit, so the undo ring and crash recovery need nothing new.

## Ride visuals

Art that must line up with a plot is measured in grid cells through `src/rendering/isoPlot.ts`, never in screen pixels: a footprint is a rectangle in cell space, which on screen is a slanted parallelogram, so a screen-axis oval built for a 4×2 plot lies diagonally across it and spills onto the neighbours. Long geometry (the coach's circuit, the flume channel, a plot surface) is therefore expressed as cell-space ellipses and parallelograms and rotates with the building. The construction blueprint draws the real building, ghosted and at rest, at the same footprint centre the placed object will use, so what the player lines up is what gets built.

Every non-coaster ride is built by `src/rendering/rideArt.ts`, which owns one builder per catalog id and returns a container plus an `animate` callback (it also takes the object's colour record, see Colour customisation; a recolour redraws that ride's art once). Everything is drawn once at construction and animated by transform, alpha, and visibility alone: **a frame may move geometry but never rebuild it**. Recording a path is cheap, but Pixi re-tessellates and re-uploads a cleared `Graphics` during the render pass — strokes especially — and on a throttled CPU that cost dominates the frame, invisible to any timer around the update loop. So the moving connectors have pre-built forms in `src/rendering/parts.ts`: a unit-length segment stretched between two points by transform (swing chains, roundabout arms, carousel poles, train couplings) and a band set whose slats are positioned and faded to fake a rotating cylinder. Smoke, foam, wake, motion trails, beacons, and the bin fill bars are likewise pre-built and driven by transform and alpha. A test counts every `Graphics` drawing call during a steady-state dev-park frame and requires zero. The renderer feeds each ride a motion state derived from simulation truth, never from wall-clock alone: `motion` eases toward a target set by ride status, `spin` accumulates only motion-weighted time so a machine coasts to a halt and resumes from the same angle, and `progress` comes from `cycleRemainingSeconds` against the ride profile duration, which is what makes the drop tower winch, hang, drop, and rebound in step with the actual cycle. Depth inside a ride is handled locally with `zIndex` from the orbit angle, so vehicles pass behind their own machinery without involving the world sort. Ride plots are drawn from the footprint: tinted tiles, a perimeter fence, and an opening wherever a path touches the plot, which is exactly the access rule guests use.

## Construction undo

Undo rewinds the whole park (Phase 12, step 3). Before the first mutation of every construction gesture (a path drag that will build, one placed object, one coaster layout, a bulldozer drag that will demolish something) GameApp asks `ParkSnapshotUndo` (`src/app/undo/SnapshotUndo.ts`) for a snapshot: a plain-object `ParkSession.serialize()` taken synchronously on the main thread, with no stringify and no worker. Snapshots sit in a ring of at most 20 entries and about 20 MB (`src/app/undo/constants.ts`, estimated from guest count). Capture is skipped for refused gestures (`abandon()` drops a pending one), and a bulldozer drag captures only when it is about to remove something, so the snapshot is never staler than the first removal.

Restore is the load boundary, not `restoreState` in place: GameApp builds a fresh `ParkSession.fromState(entry)` first (so a failure leaves the live park and the ring untouched), then runs the same `swapSession` that `startScenario` and `installLoaded` use. A rewind keeps the armed tool, the selected definition, the rotation, the camera and the speed, and resets what refers to the old world (selection, ghost, drafts, the bulldozer's drag state). Because the whole park is restored, a mis-demolished ride returns with its ticket price, open/closed intent, condition, revenue history and breakdown state, and the Phase 11 withdrawal rules ("somebody used it", "price changed", "another gesture happened") do not exist any more: a snapshot restore is always correct. Cash, guests, research, the scenario clock and the guest RNG rewind together (a ride recolour is the one cosmetic exception, see Colour customisation: it restores colours only); the ring is cleared on every new session, load and recovery resume, and closed (`scenario-ended`) at a scenario result so a rewind can never un-award a Pulse Card the tour profile already stored.

The player is told how far back it goes. The button reads "Undo · rewinds 42 s" (simulated seconds; `rewindLabel.ts`), and a rewind past 60 simulated seconds needs a second press within 4 s ("Confirm rewind 3 min 20 s", amber, with a toast), which works the same for the button and Ctrl+Z. `event.repeat` presses are ignored. A coaster draft with pieces still steps back one track piece first ("Undo track piece"); Ctrl+Z in the middle of a bulldozer drag commits and rewinds the partial drag. After a restore GameApp calls `SaveManager.notifyParkRewound()`, which marks the park unsaved against every slot and bumps the park generation so an autosave in flight for the pre-undo state cannot mark the rewound park clean. The status (`UiState.undoStatus`) is written to the store only when it changes. `ParkSession`, `GameWorld` and `src/game/build` know nothing about undo; the old `ConstructionUndo`, `GameWorld.undoConstruction` and `probeUndoInteraction` are gone, and `syncWorldEquivalence.test.ts` and the voxel `equivalence.test.ts` use a ring snapshot restore as one of their random mutations.

**Demolition outside the bulldozer (Phase 11, PA-015).** The ride and stall inspectors end with Demolish
(`Demolish · refund $N`, the refund published as `UiState.selectedDemolitionRefund` from `World.demolitionRefund`, so
`RideSnapshot` is untouched). It opens a confirmation (`UiState.demolishConfirmId`, cleared on a selection change,
inspector close and session swap; Escape pops it before the inspector), and its Demolish calls
`GameApp.demolishSelected()`: `undo.begin('demolition')`, `World.demolishObject(id)`, one entry named "<Name> demolished",
the bulldozer's routine receipt, then the inspector closes. It is refused while a coaster layout is open, because the
undo restore would discard the layout. `World.demolishObject` is the bulldoze object branch moved into a method, and
`bulldoze(cell)` calls it (`World.demolish.test.ts` pins both paths byte-identical through `serialize()`). In the
bulldozer, a press on a coaster cell with no path on it (where one cell would take out the whole coaster) only arms
that coaster: nothing is removed and no undo entry begins; the footprint is previewed and an alert toast and the hover
readout say "Click again to demolish <Name> (the whole coaster) · refund $N". A second press on the same coaster goes
through the normal `bulldozeTo` path (one undo entry). A press elsewhere, Esc, a right-click cancel, a tool change or a
session swap disarms it, with no timer, and a drag skips coaster cells, so a drag never removes a coaster.

Measured in headless Chromium at 1,000 guests with real pointer input (voxel renderer, software GL): capture median 2.5 ms (max 8.7) at 1x and median 12 ms (max 16) at 6x throttle; the synchronous part of a restore median 7 ms (max 31) at 1x and 40 ms (max 61) at 6x, plus one rebuild frame; no long task from a capture at 1x. Known limit: the restore worst case at 1x can exceed the 30 ms budget by a few milliseconds, and a parked coaster draft is discarded when Ctrl+Z reaches the ring while another tool is armed.

## Colour customisation (Phase 28, steps 1 and 2)

A placed object can be recoloured from curated swatches. Colour is **cosmetic state**: it is world state (it is saved, hashed, undone and drawn) but no simulation owner ever reads it. A park recoloured and the same park not recoloured step identically (the simulation-observable state, hashed per owner over 3,000 steps, is equal; only the world hash differs while a record exists). Step 1 coloured the ten flat rides. **Step 2** colours the rest: the three coasters, the shops and facilities, the bench and bin, the lamp, flowers and fountain, and the entrance gate; adds six named presets, the **Paint tool** (click, Shift, drag, eyedropper), the colour on the build ghost and the placed object, and the cost plumbing. Trees, paths and fences stay fixed (below).

**Data (`src/game/content/colours.ts`, pure content).** `COLOUR_SWATCHES` is 21 candy swatches in three themed rows of seven (Sunny, Berry, Sea), `[index, id, name, rgb, row, tone]`, **append-only because the index is the save value**, and `classicRgb` equals `rgb` for all of them. Twelve are catalog colours (eleven of them flat-ride slot defaults, so "what it was" is pickable for those slots); the other nine were **retuned by the readability test** (below): the catalog Sunflower, Lemon and Apricot grey out at night, Ice greys at dusk, Jade sinks into a plot at night, and Vermilion/Cherry, Bubblegum/Orchid, Indigo/Violet and Harbour/Sky become one colour at dusk or night. Each moved as little as the floors allow and kept its hue; the five that were a slot default moved visibly and were renamed (Buttercup, Citron, Glacier, Azure, Emerald), so a slot whose default is no swatch any more (Sunflower, Lemon, Harbour, Ice, Jade) keeps its old name in `DEFAULT_COLOUR_NAMES` and is reached through the Default chip. `tone` is `candy`, or `neutral` for Cream (the white of canopies and cabins, judged by lightness instead of saturation). Every slot carries `defaultName`, a swatch's name only when that swatch is exactly the default, and `isSlotDefaultSwatch(definition, slot, swatch)` says whether a pick is the default itself. A saved colour is an index, never a free RGB, so every choice stays inside the candy look and inside the 256-material voxel palette. `RIDE_COLOUR_SLOTS` gives each flat ride two or three ordered slots from one vocabulary, `primary` (compile tag 1), `secondary` (2) and `trim` (3), with the UI labels Main, Accent and Trim and a description of what each paints; the order per ride is the save format. Slot defaults are the catalog `color` (primary) and `accent` (secondary); trim exists on aurora-wheel (cream cabins), moonpetal-carousel (brass poles, finial, manes) and harbor-swings (canopy stripes). Everything not in a slot stays fixed: steel, timber, glass, water, ground contact, riders, and every light's glow (the cloud-hopper beacon and the thunder-drum glow keep the catalog yellow in both renderers). A test requires at least two slots per ride and that every slot default is an existing voxel material; the classic and voxel art of a ride use the same slot ids.

**What is colourable, step 2 (`content/colours.ts`).** One vocabulary of five slot ids that are also the preset ROLES: `primary`, `secondary`, `trim` (step 1), `rail` and `support` (coasters). A slot's compile/emit **tag is positional** (its index in the definition's list plus one, `ColourSlotDef.tag`, at most 5 so it fits the three tag bits; for the ten flat rides this equals step 1's numbers, pinned by a test), so the vocabulary can grow without running out of bits. Labels are per definition and fit the 62 px label column. The tables (the order per definition is the save format): **coasters** `comet-trail`, `star-chaser`, `skyline-serpent` have four slots, Train (the train body, nose and stripes and the station canopy; defaults Flame, Amethyst, Lagoon), Seats (seats, restraints and the trim band; Sunflower, Mint, Lemon), Rails (running rails, station valance, platform edge and queue gate; the same three) and Supports (support bents, spine and ties; Timber, Steel, Pale steel); **shops and facilities** (picnic-pocket, fizz-foundry, glacier-scoop, lemon-light, waffle-windmill, snack-sprint, comfort-cabin, comfort-pavilion) have Walls and Roof (the stall has no separate sign slot: its sign-like parts are the roof strip and the ridge icon, which says what it serves and stays fixed); **ribbon-bench** Seat and Back, **tidy-totem** (the bin) Body and Lid, **lollipop-lamp** Post and Cap (the globe and its light stay fixed), **sunburst-flowers** Blooms and Petals (the bed stays green), **ripple-fountain** Basin (stone, water and spray stay fixed); and **the entrance gate** has Arch, Sign and Posts (the lettering and the lantern lights stay fixed). Defaults are the shipped colours; those that are no swatch have names in `DEFAULT_COLOUR_NAMES` (Flame, Amethyst, Tangerine, Custard, Terracotta, Flamingo, Pine and so on). **Fixed on purpose:** trees (a confetti tree is a landmark of the candy look), every light and glow, water and spray, glass, doors, the food icons, riders, wheels, chassis and couplings, the chain, brakes and chevrons, stone platforms and footings, every plot slab and the classic coaster's ground diamonds. **Paths and fences are not colourable (leftover):** a path colour needs new patterned paving materials (a mortar and curb secondary each, the swatches are plain colours), a readability pass with guests and litter on the paving and in the cutaway, and a classic path redraw; a fence colour is ground contact under step 1's rule and would rebuild every ride's chunk. Neither is cheap enough to do well in this phase. `colourKindOf` groups the definitions (ride, coaster, stall, comfort, scenery, gate) and `COLOURABLE_DEFINITION_IDS` lists the 26 catalog ids.

**World state (`src/game/World.ts`).** `PlacedObject.colours?: readonly (number | null)[]`, one entry per slot (a swatch index, or null for the default), frozen and **replaced, never mutated**, so a renderer diffs it by identity. No record means defaults; an all-null record is never stored. `setObjectColours(id, colours)` is strict (the length must equal the slot count and each entry must be null or a swatch index, else a typed refusal and nothing changes), `clearObjectColours(id)` removes the record, `objectColours(id)` reads it. A colour edit is free (no transaction, no cash), does **not** bump `version` or `pathVersion` (bumping `version` would re-sync scenery and guest routes and so touch the simulation), and bumps the transient `appearanceVersion` and notifies listeners once per batch only when the record really changed; a no-op set keeps the record's identity. `GameApp` therefore keeps its own `colourEdits` counter, added to `world.version` for the undo ring's "did the gesture change anything" stamp and to the save layer's change token (so autosave and the unsaved-changes prompt see a recolour). **The gate** is not a placed object: its record is the park-level `GameWorld.gateColours` (aligned with `colourSlotsFor('park-entrance')`; `ENTRANCE_COLOUR_ID` is a pseudo definition id so every colour helper works for it), with `setGateColours` / `clearGateColours` under the same strict, free, `appearanceVersion`-only contract. `recolourBatch(edits)` applies several object and gate edits as one gesture (one listener notification, `appearanceVersion` +1 per changed record, never `version`, no transaction) and reports `changedCount` (the gate counts as one); `applyPresetToPark(presetId)` is the whole-park preset through it.

**Persistence.** Save schema 7 (`SAVE_SCHEMA_VERSION`, `ParkSaveV7`; `ParkSaveV6`, `V5` and `V4` are kept as deprecated aliases). Schema 6 added `PlacedObjectState.colours?: (number | null)[]`, written only for a recoloured object, so an uncoloured park serializes byte for byte as before. **Schema 7 adds two fields:** the park-level `world.gateColours?` (written only when set) and `rules.recolourCostMultiplier` (the compiled ruleset is saved). Presets are derived data (applying one writes ordinary per-object records) and the paint tool, its brush and its panel are UI state, so they add nothing to a save. Migration 5 to 6 changes nothing but the version; migration 6 to 7 adds `recolourCostMultiplier: 1` and drops a hand-edited `gateColours` (a v6 save cannot legitimately carry one); the v5 and v6 fixtures were captured before `state.ts` changed. **Policy: colours are normalised on restore, never a reason to refuse a save.** A colour is cosmetic and cannot desync an owner, and slot lists may grow in later versions, so `normaliseObjectColours` repairs it: an entry that is negative, 21 or above, fractional, huge or not a number becomes the slot default; a wrong length is padded with null or truncated; a record on a definition that is not colourable (a tree) is dropped; an all-default result is no record; the gate's record is normalised through `park-entrance`. NaN and Infinity never reach it: they are `corrupt` for any value in a save, as everywhere else. Colours and the gate record are in the world hash, `coverage.test.ts` and the determinism fixtures (one park with the gate, a stall and a coaster recoloured, one wearing a preset). Crash recovery and the autosave carry the records because they carry the session state.

**Voxel (`src/rendering/voxel`).** Slots are tagged at authoring time, not remapped by material: a blueprint shape's material may carry a tag (`material + 256 x tag`), the voxelizer keeps it in the top three bits of the pattern byte, the greedy merge key includes it (so the partition of a default ride is unchanged: the probe proved identical boxes for all ten rides), and each compiled box carries its tag in field 7, which the scene overwrites with the transform slot at placement. This also keeps a rider's shirt that happens to share a ride's colour out of the slot. `StaticWorld` remembers the record per object; an object whose record identity changed marks only its own chunk(s) dirty (no forget, so transform slots survive) and `emitObject` substitutes the swatch material per tagged box when it pushes the boxes, for the static body and for the rigid parts emitted into that chunk. Swatches are ordinary palette materials appended last with the existing rgb de-duplication: the twelve catalog colours share their materials and the nine retuned swatches cost one plain material each, 131 of 256 (at most +21); every material id and every texture byte of the 122 older materials is unchanged (pinned), so a default ride draws exactly as before; patterns are per box and flags per material, so there is no swatch x pattern product and a recoloured box keeps its pattern and glows no more than before. A per-box override channel was considered and rejected (the box word has one spare bit; a decode in six geometry programs plus fxc guards for a feature whose whole cost is otherwise zero extra materials and one chunk rebuild). No shader changed, no fallback rung was added, a recolour is a data change that rebuilds one chunk once and nothing per frame. The ghost keeps default colours in step 1 (step 2 colours it, see below). **Voxel numbers (step 1).** Dev park (REGISTRY content, 16 chunks, 15,401 boxes, largest chunk 4,574): recolouring any of the ten rides (40 different records each) rebuilds exactly its home chunk once, and the box count of that chunk and of the park is identical before and after every recolour (petal roundabout and carousel 4,574 in their chunk, comet cups 2,373, cloud hopper 2,218, harbor swings and splash rings 1,925, aurora wheel and bumble coach 1,826, gale spinner and thunder drum 1,505); only the material byte of the slot's boxes changes (`staticWorld.colours.test.ts` checks every ride x slot x swatch box for box). Rebuild of that chunk on the CPU in Node, median / p95 over 40 recolours: 0.34 / 0.39 ms for an 1,826-box chunk, 0.59 / 0.67 ms for the thunder drum's, 0.91 / 1.09 ms for the 4,574-box chunk, once per pick; steady frames rebuild nothing (the zero-rebuild test runs with a recoloured, running ride). Palette 131 of 256 materials.

**Readability (`colourContrast.test.ts`).** A CPU twin of the composite: face light (`ambient + key x lambert` for the top, lit side and shaded side), the weather surface hook (cloud shadow multiply, compared under the same sky as the ground next to it; wet ground darkening and saturation lift on ground tops) and `vxGrade`, with the look blended from the real presets and weather modifiers for day, dusk and night under sunny (which has cloud shadows), cloudy, rain and storm: twelve looks. Grounds are both grass shades, paving, curb, the stone and concrete ride decks and every ride's plot tint. Floors, all absolute: a candy swatch keeps saturation >= 0.25 on every face in every look; its top and lit side stay >= 40/255 RGB from every ground by day and dusk and >= 24/255 at night; Cream keeps a luma gap of >= 0.06 (day, dusk) / 0.04 (night) to every ground; every pair of swatches stays >= 28/255 apart by day and dusk and >= 20/255 at night on the same face; in classic a swatch keeps >= 45 % of its saturation and >= 40/255 from the tinted grass and paving. The test pins its calibration (the catalog Sunflower's top face at night is 95,97,84, as measured from real frames) and proves it can fail on exactly what the reviewer measured in real frames (the catalog Sunflower, Lemon and Apricot at night, Sunflower on wet paving, Ice at dusk, Jade on a plot, the collapsing yellow, pink and purple pairs). The old relative floor ("no worse than the least readable colour the game ships") is gone: it let the shipped yellows excuse themselves. The shipped slot defaults are not judged by it (a default may not change in step 1); the catalog Sunflower and Lemon defaults do grey out at night, which is a step 2 / art question, not a swatch.

**Classic (`src/rendering/rideArt.ts`, `WorldRenderer.ts`).** Every builder receives a `RidePaint`: `paint(slot, fallback)` returns the swatch's classic colour when the slot is recoloured and `fallback`, the colour the part always had, otherwise. A ride with no record answers every call with its fallback, so **default art is identical to the art before colours existed**; this is pinned by golden hashes of every ride and rotation (the fingerprint is every transform and every recorded drawing instruction, in an idle and a running pose), taken before slots existed, in `rideArt.colours.test.ts`, and by a headless screenshot diff of the dev park against the Phase 26 production build (a Playwright driver kept with the Phase 28 scratch scripts, not in the repo: three runs of each build, every pixel that changes between runs of one build is excluded as animation, and the other 97 % of the frame, plots, fences, buildings, paths and the static parts of rides, differs in at most one pixel of 1.1 million). Classic maps the slots to its own art by the same ids: primary is the catalog colour (bowls, canopies, car bodies, drum wall), secondary the catalog accent, trim the fixed decorative colours (aurora's cream cabins, the carousel's brass poles, finial and manes, harbor's canopy stripes). A few classic parts of a slot were drawn in their own literal before slots existed and differ from the slot's (voxel) default: the carousel's manes and finial (Trim, cream where voxel is gold) and pennant (Main, cream where voxel is orchid) and the aurora's cabins (Trim, fff3d0 where the default is fff0c8). The defaults of both renderers are pinned, so that difference stays; what is guaranteed is that **the swatch that is a slot's default draws the default art in both renderers** (`ridePaintFor` treats it as the default through `isSlotDefaultSwatch`, and the voxel draws the same palette material), so picking the colour the Default chip names never repaints anything. Some classic literals are tones of the ride's own Main colour (the thunder drum's underside, lit top, plate and booth, the carousel's mauve drum, pale bands and platform, the comet cups' turntable and disc, the gale spinner's base and booth); they follow the slot **only once it is recoloured** through `linkedTone(literal, slotDefault, slotNow)`, which returns the literal exactly at the default, scales the new colour by the same luma ratio for a darker literal and mixes it toward white by the same share for a lighter one. Lights keep their glow; the teal platforms and plates shared by most rides, the steel, the plot tint and the fence stay fixed (ground contact). The renderer keeps the record it drew each ride from; `syncWorld` compares it by identity with the object's (one compare per ride, no display touched when nothing changed) and, for a changed one, **redraws that ride's art once**: the old art and the spare art of the other footprint axis are destroyed with their GPU contexts, the new art is built at the current facing at the same child index, and the cached screen box and art top are refreshed. The old art is the pool, so many recolours neither accumulate displays nor leak contexts (tested over 25 recolours), a steady frame still makes zero drawing calls (tested with a recoloured ride), and a view turn or a session swap (undo of an older gesture, load) builds with the recolour. Cost: one ride's art, a few hundred drawing calls on the one frame of the change, nothing else (`WorldRenderer.colours.test.ts`).

**Classic, step 2 (`classicObjectArt.ts`, `classicPaint.ts`, `classicCoaster.ts`, `classicTrain.ts`, `WorldRenderer.ts`).** The `RidePaint` contract (`paint(slot, fallback)`, `tone`, and the new `isSet`) moved to the Pixi-free `classicPaint.ts` (rideArt re-exports it) so the coaster palette and the train style, which are plain data, can use it. `createObjectArt(definition, colours)` draws stalls, facilities, bench, bin, lamp, flowers and fountain (the trees stay literal) through the same contract, and `drawEntranceArt(group, colours)` the gate; the default art is **pixel-identical** to before: the fingerprints (every transform and every recorded drawing instruction) of every non-flat-ride display of the colour test park at four view rotations, the entrance, the three trains and every build preview were taken before any step-2 change and are pinned in `__fixtures__/classic-step2-baseline.json`, and by a headless screenshot diff of the extended park against the pre-step-2 build (76 screenshots: overview and close-ups of every newly colourable kind and the gate, noon and night, two views, a noise mask built from four baseline takes because sway, spray and smoke move between runs): zero differing pixels outside the mask. A coaster's palette is `classicCoasterPalette(id, color, colours)`: Rails (the type's accent, bright) recolours the rails, the station gate and valance and the platform edge (the new `edge`, the ties' colour by default), Supports the supports, braces, spine and ties (one colour, as in the voxel art), Train the station canopy; the station's ground diamonds (`ground`) are ground contact and stay. The train is `classicTrainSpec(id, colours)`: Train is the hull (the lead car's tone follows through `RidePaint.tone`), Seats the stripe and fin; the seat backs, wheels, couplings and riders stay. A record with nothing set answers the shipped palette or style object itself. `ObjectDisplay` keeps the record it drew from; `syncWorld` compares it by identity (`syncObjectColours`) and redraws a changed object ONCE: a stall or scenery swaps its art container at the same child index (old art destroyed with its GPU contexts, the scenery's animated entry re-pointed, the cached screen box and the see-through refreshed), a coaster clears and redraws its one track Graphics in place (as a view turn does) and drops its train, which the next frame rebuilds once in the new colours, the gate redraws its group once. Steady frames still make zero drawing calls with a recoloured, running coaster, stalls, scenery and the gate; 25 recolours of a stall, a coaster and the gate leak no context and add no display (`WorldRenderer.colours.step2.test.ts`). `drawPreview(..., colours)` and `drawCoasterDraft(..., colours)` build the ghost and the draft in the brush's colours (a view turn redraws them with it; a bulldoze ghost is never tinted). **Paint hover:** `setPaintHover({ cells, tint })` is one pooled Graphics in the preview layer (an outline and, with a tint, a 25 % fill), redrawn only when the cells or the tint change, with its own lifetime (`clearPreview` leaves it), drawn again after a view turn, and it feeds the see-through as a bulldoze target (the target stays intact, what is in front fades); no ghost and no shader. The two renderer-port seams are `RendererPort.drawPreview/drawCoasterDraft(..., colours)`, `setPaintHover?` and `WorldInputHandlers.start(cell, { shift })`.

**Inspector (`src/ui/colourModel.ts`, `ColourSection.tsx`, `colourEdit` in `src/app`).** A **Colours** section sits in the ride inspector (coasters included: four rows) and, since step 2, the stall and facility inspector, right after the ticket price, collapsed by default (a header with one dot per slot, remembered for the session in `colourPanelOpen`). Expanded, it has one row per slot: the label, a **Default** chip (aria-pressed when the slot is at default, named "Main: default, Rose"; the name is the slot's `defaultName`, which is a swatch name only when that swatch is exactly the default, so the chip never names a swatch that draws something else) and the 21 swatches in their themed rows of seven; **Reset to default** (aria-disabled when nothing is customised, the project's convention) clears the ride. The model (`colourSection`; `swatchChoices` is shared with the Paint panel) is pure and is the only place the rules live; the component maps it to markup. Each swatch is a real button named by its colour with `aria-pressed`, selection is shown by a ring **and a check mark whose tone has at least 3:1 against the swatch**, so never by colour alone. Each slot's swatches are one roving group (`data-roving`, one tab stop, the chosen swatch or else the first): Left and Right move by one, Up and Down by a themed row, Home and End to the ends, no wrap, Enter or Space picks; focus stays on the button across the repaint. The header's accessible name is its visible text and then the colours (WCAG 2.5.3), a polite status line says "Colours: Main Teal; Accent default, Sunflower." after a pick. Clicking a swatch repaints the ride itself at once, so the object is the preview: there is nothing to apply. The section is mouse and keyboard operable through ordinary focus. Benches, bins, scenery and the gate have no inspector: the Paint tool and the presets reach them. A pick series on one object is charged once (see Cost). `gameBridge.setSelectedObjectColour(slot, swatch | null)` and `resetSelectedObjectColours()` (step 1's names were generalised to the inspected ride, coaster or stall) reach `GameApp`, which composes the record with `withSlotColour` (refuses what the world would refuse, and stores a pick of the swatch that is the slot's default as null: it is the default, so the ride stays at "Default colours" and a pick of it on a default slot leaves no undo entry), applies it and publishes `selectedColours` to the store (the record's identity, so a component re-renders only when a colour moved). The store field is written by `syncUi`, which every world notification already calls.

**Undo.** A recolour is one new undo gesture kind, `recolour` ("Petal Roundabout recoloured"), captured like the others (snapshot before the edit, outside any batch; the ring keeps it only if the stamp moved, so picking the colour already there leaves no entry). It differs in two ways. First, **it is cosmetic**: undoing it puts only the colours back (`GameApp.restoreColours` applies the entry's recorded colours to the live world in one batch) with no session swap, no rewound clock, no returned cash and no lost guests, so the control reads plain "Undo" with the tooltip "Nothing else changes", never needs the long-rewind second press and reports no rewound seconds. Second, **picks coalesce**: while the newest ring entry is this ride's own recolour, further picks join it, so trying twenty swatches is one Undo and cannot push construction history out of a ring of twenty (any other gesture, or another ride, starts a new entry; only an entry the pick itself opened can be joined, so after a pick whose snapshot failed, which records no entry, the next pick opens its own instead of joining another ride's). Reset is a recolour. Undoing an older, whole-park entry takes the colours of that moment back with it (they are in the snapshot). **Step 2:** a Paint gesture (a click, or a drag over any number of objects), a whole-park preset and a series of inspector picks on one object are each ONE `recolour` entry ("Painted Picnic Pocket", "Painted 6 things", "Seaside colours for the park"). The snapshot is taken lazily right before the first real change (a drag over grass makes none), a Ctrl+Z in the middle of a drag commits the partial entry and the drag goes on in a new one, and the cosmetic undo (`restoreColours`) restores every object the snapshot knew and the entrance gate through one `recolourBatch`. A priced recolour is refunded: the ring entry's charge is kept by the app and its undo posts the same amount back as a `refund` transaction.

**Presets (`content/colourPresets.ts`, pure).** `COLOUR_PRESETS` are six named maps from slot ROLES to swatches, in panel order: Candy (every role at its default: applying it is the reset), Seaside (Azure, Cream, Mint, Glacier, Lagoon), Midnight (Indigo, Buttercup, Violet, Citron, Ink), Autumn (Cherry, Honey, Apricot, Vermilion, Ink), Meadow (Emerald, Bubblegum, Citron, Cream, Teal) and Berry (Rose, Cream, Orchid, Bubblegum, Violet). A preset is derived data: nothing about it is saved. `presetDots` gives the three dots of its chip.

**The Paint tool (`app/paintGesture.ts`, `ui/paintPanelModel.ts`, `PaintPanel.tsx`, `GameApp`).** `tool: 'paint'` is a build-capability tool like the bulldozer (`activeInputContext` gives `build`, no new layer; Esc puts it down and closes its panel; the see-through is armed). It is armed from the dock's **Paint** button, the rebindable key **`C`** (`paintTool`) or **`I`** (`eyedropper`, arms it in pick mode); both are `build-not-designer` keys with `yieldsDefault`, so a player who had bound C or I keeps it and the new action loads unbound. Arming it closes the inspector (the inspector is never open while painting), and inspecting from the Buildings tab puts the tool down. **The rule, one sentence:** a click or a drag paints the **Main** colour of every object under the cursor with the brush swatch (the Paint choice can say Accent or All instead); **Shift, read at pointer down, paints every part** of each object with the swatch; a preset or a picked (copied) brush always paints the whole object; an object that already has the resulting colours is skipped. The brush is one of Default (the shipped colours back), one of the 21 swatches, one of the six presets, or **copied** by the **eyedropper**: the Pick toggle or `I`, then a click copies the target's colours as ROLES (so they paint any other kind: Walls Teal copied from a stall paints a bench's Seat) into a brush named "Colours of Picnic Pocket" and turns pick mode off, making no world change and no undo entry. Alt-click was rejected for the eyedropper because Alt+left-drag already pans the camera and Alt+drag moves windows on many Linux desktops. A drag crosses every cell on the straight path (`lineCells`, shared with the bulldozer); an object is painted once per gesture (a coaster by any piece, the gate by its cell); empty ground and paths do nothing; a tree says "Trees keep their colours" and the fountain "No Accent part". **One undo entry per gesture**, opened lazily before the first real change and committed at pointer up, at a right-click (which also puts the tool down and keeps what was painted) or when the tool changes. **Hover:** on every hover cell change GameApp resolves the target and calls `renderer.setPaintHover({ cells, tint })` (tint is the brush swatch's classic colour, null for default, preset and copied brushes), so the outline works in every view rotation and with the see-through, in both renderers, with no new shader; the cursor readout says what a click would do ("Main to Teal", "Seaside colours", "Already these colours"), follows the Shift key, and a brush change redraws it at once. **The panel** (`.paint-panel`, in the inspector's slot, added to the layout audit's `FLOATING_PANELS`): a header with a close button (= Esc), a polite status line ("Brush: Teal on Main"), the Default chip, the Pick toggle and the 21 swatches as one roving group (the inspector's markup, ring and check mark, one tab stop, arrows move by one and by a row, Home and End, Enter or Space picks), the Main / Accent / All radiogroup (inert, with none checked, for a preset or copied brush), the six presets as a roving group of toggles with three-dot chips, **Apply to whole park** (`aria-disabled` until a preset is the brush: every colourable object and the gate in one world batch and ONE undo entry, one toast "Seaside: 57 things recoloured"; objects already matching are not counted or charged) and a one-line hint. Painting an individual object is a pointer gesture (the documented exception in `FIXED_KEYS`); keyboard players recolour a ride, coaster or stall from the inspector and apply a preset to the whole park from the panel. The dock row holds the button at 1280x720 and UI scale 130 (the layout audit decided, there was no need to move it to the utility rail).

**Colour before placing.** While a colourable build card is armed the brush gives the next building its colours: `placementRecord(definitionId, brush)` (a swatch colours the primary slot only, a preset or copied brush its roles, the default brush nothing, a tree or path nothing). The armed-tool line reads "Picnic Pocket armed - next colour Teal - Esc to put it down" with a **Colour** button that opens the panel's brush parts (`paintPanelOpen`, a panel headed "Next colour" with the card's name, its status line "Next one: Teal", and no target, Apply or Pick) without disarming the card, and the armed dock card shows a small decorative chip (one dot for a swatch, three for a preset; the card's title says "Next colour: Teal"). GameApp hands the record to `drawPreview(..., colours)` and `drawCoasterDraft(..., colours)`; a brush change redraws the ghost under a still cursor. **Ghost identity (voxel):** a new box list identity only when the choice, the model or the rotation changes (below), so a steady hover uploads nothing; a valid voxel ghost in a chosen colour is screened denser and tinted lighter so the colour reads (below). A swatch brush colours the primary slot only, which on a stall is the walls under the roof: the ghost shows exactly what will be placed, and a preset or a copied brush is the way to colour the roof before placing. Placement puts the record on the new object in the same world batch as the build (one renderer sync, one undo entry that removes the whole building) and is free: a recolour fee is for changing what is already there.

**Cost and unlock (data and plumbing only).** Free in the Sandbox, always (a rule in `content/colourCost.ts`, not config). In a Scenario and on The Map `GAME_CONFIG.colours.recolourCostPerObject.{scenario, map}` (both **0**, free until Phase 22's profile unlocks and Phase 25's cards decide) times the park rule `recolourCostMultiplier` (default 1, a `CARD_MODIFIABLE_RULE`, lower is better, clamped like every multiplier, saved in the ruleset; the scenario HUD words it "Recolouring costs 20% less") is charged per object that really changed, once at the end of a gesture as one `construction` transaction "Repainting" (an inspector pick series is charged by the pick that opens it, a preset on the park once for everything it changes); `recolourCharge(mode, objectsChanged, multiplier)` is the one function. Mode is `sandbox` without a scenario definition, `map` in a run stage (mode `run`), else `scenario`. The charge covers only what the gesture's own undo entry holds: Ctrl+Z in the middle of a drag commits and undoes what was painted so far (the ring's rule for any drag), and GameApp then tells the gesture (`PaintGesture.dropUndone`), so the release neither names nor charges those objects (and an undone object is not repainted by the same gesture); a drag cut short by the pause menu, a tool change or a lost pointer-up is settled as the paint gesture (its label and its charge) before the bulldozer's settle commits any pending snapshot. A gesture that would overdraw stops at the object it cannot pay for (what it painted stays) and says so; a preset or an inspector pick the player cannot afford is refused as a whole. Placement is free. No scenario objective, card or progression project references colours or the multiplier (`colourNoRequirement.test.ts`), and with the default 0 no transaction is ever posted. Nothing is locked behind anything: the unlock content is Phase 22's and Phase 25's.

**Voxel, step 2 (`src/rendering/voxel`).** The mechanism is step 1's (tags at authoring time, emit-time substitution of an existing palette material, one chunk rebuild per recolour) with these additions: flat models carry their tags in a parallel array (cars, the gate and the ghost are placed from flats whose field 7 is zeroed), the procedural coaster track resolves its look from a per-tag material table (geometry never depends on it), a coaster recolour marks exactly its own chunk set (the deduplicated chunks of its pieces; the train and riders are rigid parts in the station's chunk, which is in the set) and rebuilds each once, the gate is a park-level record whose change marks the entrance chunk, the ghost is a recoloured copy of the cached flat keyed by (flat identity, record value), and the paint hover and its see-through focus go through the overlay layer. Baseline numbers measured before step 2 (Node, median of 15): rebuilding exactly a coaster's chunk set takes 2.7 to 5.3 ms for the Star Chaser (4 chunks), 2.1 ms for the Comet Trail (2) and 2.8 ms for the Skyline Serpent (2); the palette is 131 of 256 materials and stays so (swatches already exist, no new material, no shader change, no fallback rung). **Voxel numbers (step 2, after; Node, `StaticWorld` sync plus `rebuildDirty`, median / p95 over 31 recolours, the extended colour test park of 16 chunks and 18,465 boxes):** a coaster recolour rebuilds exactly its chunk set, each chunk once: the Star Chaser 4 chunks in 2.65 / 3.13 ms, the Comet Trail 2 in 1.60 / 2.06 ms, the Skyline Serpent 2 in 1.34 / 1.45 ms; the longest serpentine (64 pieces, `longestLayout`, alone on a park) spans 5 chunks (1,436, 607, 1,140, 1,802 and 1,782 boxes) and rebuilds in 4.96 / 5.83 ms, once per pick or gesture, never per frame. A whole-park preset (65 of the 69 objects change) dirties all 16 chunks and costs 6.83 / 8.03 ms including the world edit, the same as a full rebuild of every chunk (6.55 / 7.24 ms): one frame, once per Apply. The box count of every chunk (and so of the park) is identical before and after every coaster recolour and every preset (asserted by the measurement, and per kind x slot x swatch by `staticWorld.colours2.test.ts`; the steady frames by `scene.colours2.test.ts`). Steady frames with a recoloured running coaster rebuild nothing. Palette 131 of 256 materials, unchanged. **Ghost screen:** a VALID build ghost carrying a chosen colour draws at coverage `GHOST_COVERAGE_VALID_COLOURED` (0.8) with `GHOST_TINT_MIX_COLOURED` (0.12) of the valid tint instead of 0.6 and 0.4, so Cherry reads red rather than a muddy tan and Emerald or Teal no longer melt into the green tint; the invalid ghost (0.35, 40 % red), the bulldoze ghost and a ghost in its shipped colours are unchanged (the default ghost crop is pixel-identical to before). The mix is a `GhostState.tintMix` uniform value, written with the coverage on each ghost draw: no shader change, no upload (a validity flip still uploads nothing).

**Left (step 2).** Path and fence colours (new patterned materials, readability with guests and litter, a classic path redraw, an every-chunk rebuild for fences); a lights slot (emissive swatch variants); the Phase 22 and Phase 25 unlock and card content for colours (only the data and plumbing exist: the per-mode cost table and the multiplier, both free by default); shareable profile-level presets and custom user presets; trees and rocks stay fixed by design; a live preview of the recolour on the object under the hover (the hover is an outline and a tint); painting an individual object from the keyboard (a pointer gesture; keyboard players have the inspector and the whole-park preset); per-car colours on a coaster; a park banner (no such object exists); and the shipped Sunflower, Lemon, Timber and Wood and the pale stall accents, which grey or vanish at night (an art question: a default may not change in Phase 28).

## Staffing

Crew size scales with the park rather than sitting at a fixed ceiling: `OperationsSimulation` derives a live per-role hiring cap from the observed crowd (a base allowance plus one place per N guests, clamped), and hiring is refused against that cap instead of a constant. Training is the other half: a role buys whole-crew levels for cash, and each level multiplies work speed and walking speed while raising that role's wage, so a trained crew is an ongoing cost decision rather than free throughput. Both live in the operations simulation and reset with the session; task durations, walking speed, and payroll all read the level through one helper each, so no caller can forget to apply it.

## Estate overview

`ParkSession.buildingsSnapshot()` flattens every placed object into one comparable row — ride, service, bin, and scenery numbers each read from the simulation that owns them, never recomputed — which is what the Buildings tab sorts and what the row click uses to centre the camera and open the matching inspector. Because the rows are derived, the overview cannot drift from an inspector.

Phase 11: the row click moves the camera with `focusCell(centre, 'ease')`, a 250 ms glide in the voxel renderer (a
snap in the classic one and under reduced motion). A ride or stall that no path from the gate reaches (PA-024) is
listed in `UiState.noPathAccessIds` (sorted, a new array only when the content changes), which GameApp builds from
`ManagementSimulation.hasPathAccess(id)`, a read of the management connectivity cache that never changes saved state.
`BuildingSnapshot` is untouched (the determinism observables hash it). Its estate row gets the class `no-access` and
"· no path access"; its inspector a `role="note"` line; the voxel badge layer a static slate badge (rides and
services; priority broken > maintenance > no access). The classic renderer draws no such badge.

Phase 14: the Neighborhoods tab copies the estate row exactly. A neighborhood row is a `<button>` that calls
`gameBridge.focusNeighborhood(key)`, and `GameApp.focusNeighborhood` eases the camera with the same `focusCell(cell,
'ease')` (see Crowd flow and neighborhoods (Phase 14)). Its metrics read the owning simulations, as the estate rows do.

## Developer park

`src/game/session/devPark.ts` stamps a finished park into a fresh sandbox session: a street grid, twelve rides across the intensity range, a validated coaster, every service, decorations, a starting crew, and a working budget. Ride and service plots are declared explicitly and expected to fit exactly — the seeder reports anything skipped, and the tests assert that report is empty and that every ride and service has a path-connected entrance — while decorations fill leftover path-side cells best-effort, so adding a ride can never break the park. ## Settings

Player preferences live in `src/settings/` (pure model: schema, store, motion, UI scale, notification classes) under their own localStorage key, `parksmith-settings`, never in a ParkSave and never in the profile. The model, its migration and the cross-tab sync are described by the doc comments in `schema.ts` and `settingsStore.ts`; this section covers the UI side.

### Panel, UI scale and input layer

- **Panel.** `src/ui/SettingsDialog.tsx` (`SettingsDialogBody`, a lazy chunk since Phase 34 whose open check is `SettingsDialog` in `lazyPanels.tsx`; a loop over `SETTINGS_GROUPS` in `settingsModel.ts`, which derives labels and options from `SETTING_OPTIONS`) is mounted in `App.tsx` outside `.clean-hideable`, so it works in clean view. Controls are native radios (styled as segmented buttons) and checkboxes in labelled fieldsets; every change applies at once through `updateSettings`, there is no Apply button. It is docked right so the park stays visible while a setting changes it, with a transparent catcher behind it so a click or drag cannot build or pan.
- **Opening it.** `openSettings()` / `closeSettings()` in `src/ui/openSettings.ts` (the same seam as `openSaveLoad.ts`) work from non-React code; the gear in the left utility rail and the start and pause menus (see Menus) call it. The `settings` input layer sits above the world layers, the menu and the Parks map and below Save / Load and the recovery prompt, so Escape closes exactly one layer. The panel has `role="dialog"`, moves focus to its heading on open, traps Tab and restores focus on close.
- **UI scale.** `src/ui/settingsDom.ts` writes `--ui-zoom`, `--ui-vw`, `--ui-vh` and `data-motion` on `<html>` (at start, on every settings change, the OS motion preference and window resize). `.ui-layer` uses CSS `zoom`, so the park canvas is never scaled. `effectiveUiScale` caps scaling UP so the HUD always has `UI_LAYOUT_MIN_WIDTH` x `UI_LAYOUT_MIN_HEIGHT` CSS pixels (about 104% at 1280x720); the panel says so when it caps. Inside the UI layer `100vw` / `100vh` are wrong under zoom, so styles use `var(--ui-vw)` / `var(--ui-vh)`, and viewport media queries are container queries on `.ui-layer` (`container: ui / size`), which see the zoomed width. New HUD CSS follows the same rule: no `vw`, `vh` or viewport `@media` inside the UI layer.
- **Reduced motion in CSS.** `:root[data-motion="reduce"]` rules in `styles.css` replace the old `prefers-reduced-motion` blocks, so the setting, not only the device preference, drives them. Scripts read `reducedMotion()` from `src/settings/motion.ts`.
- **Notifications.** UI code shows toasts through `showToast(message, cls)` (`src/ui/showToast.ts`); management pop-ups are filtered by severity in `ManagementNotifications`. The Activity list and the Pulse badge are never filtered.
- **Developer tools.** The panel toggle sits in a collapsed group; `DEVELOPER_MODE` is read once at load, so a change shows "Reload to apply" and a Reload now button.

## Menus

The start screen and the in-game pause menu (Phase 18 step 2) are one layer, `menu`, with two kinds (`UiState.menuKind`: `start` | `pause`). The decisions are pure and live in `src/ui/menuModel.ts` (which save Continue means, what is waiting and why, focus order, what Escape does, the boot decision, the quit question); `src/ui/MainMenu.tsx` renders them and calls `gameBridge`; `GameApp` (the "Start screen, camera sweep and pause menu" block) owns every transition. About / changelog is static data in `src/ui/aboutModel.ts` (the version is the one in `package.json`).

**Boot.** Unless `&menu=0` (`src/app/menuFlag.ts`, read once from the URL, never remembered, `?dev=1` does not change it; outside a browser the default is off so unit tests are not behind a menu), `mount` enters the start screen before the first frame: the clock is stopped, `menuHold` is set, and only a scrim shows until the save list, the recovery decision and the preview read are known. The decision then is `bootMenuDecision`: **a first run (no stored profile AND no saves) skips the menu** and keeps the Phase 13 flow (Phase 23: the Sandbox First Day park, with nothing opening over it; the old auto-opened Park Tour map is gone), because a menu in front of a one-choice start is an extra click; a developer (`?dev=1`) never skips, and a player who has a save but no profile gets the menu. After the first run the menu is always there at boot, leading with Continue when a save exists and with New park when none does.

**Preview, not load.** The park behind the start screen is the newest readable slot (`slotsNewestFirst`, autosave first on a tie; of the two autosave generations only the one `continuableSlots` picks), read through `SaveManager.loadPreview` (the same read, migrate, validate and fresh-session build as a load, with a damaged record flagged unreadable exactly as a load flags it, but nothing installed, no notice, no `lastError`) and put on screen with the same atomic `swapSession(…, 'loaded', …)` a load uses, paused. Up to three tries, newest first, the candidates re-read after each failure (so an autosave that fails here hands over to its previous generation): an unreadable save is named in the menu's notice (`describeUnreadableLatest`) and the next one is shown; with nothing readable the empty starter map shows and the menu is the plain one with its message. While the preview is up nothing of the game is live: `saveHost.hasPark()` is false (`menuHold`), so there is no autosave, no dirty state and no quick save; no recovery marker or lock exists (`recoveryController.parkStarted` is not called); the undo ring is empty; the clock does not run; the world input handlers return at once. A crash-recovery offer outranks the whole menu (see the layer order): while it is open the preview stays on the starter map, Continue, New park, Parks and Load are marked waiting, and answering it (Resume loads through the normal flow and closes the menu; Not now frees the menu, which then previews the newest remaining save, possibly the "Recovered autosave" slot).

**Continue = exactly the parked state.** If the previewed slot is still the newest and its revision is unchanged (the list is refreshed by the manager and by the other-tab channel), Continue adopts the session that is already on screen (`commitPreview`): the same object, so its state hash is the saved `stateHash` (e2e and a unit test compare them), and then starts what the menu held back: `saves.notifyParkStarted()` plus `SaveManager.adoptPreview` (the load bookkeeping: autosave revision, quick-save slot, notice), `recoveryController.parkStarted` (marker and lock) and the autosave schedule. Otherwise it falls back to the normal `loadGame`. Like Load, a continued park starts **paused** (decision: the player sees the park before it moves; a one-line change in `installPreview`/`commitPreview` if running is wanted). New park from the start screen is `startScenario(null)`; it also resets the clock's park time to 0 (before, a new park inherited the previous park's `simulationTimeMs`; a preview carries its save's clock, so this had to be fixed) and puts the camera back at the entrance.

**Camera sweep.** `src/app/cameraSweep.ts` is pure: two incommensurate sines (84 s sideways, 133 s up and down) around the map centre, amplitude eased in over 4 s so position and speed start at zero, at most about 25 screen texels per second, a frame capped at 100 ms. GameApp drives it through ONE new optional port method, `RendererPort.setCameraCentre?(cellX, cellY)` (numbers, allocation-free; the voxel camera's `focusCellXY` and the classic container position), keeping the integer voxel zoom. The park's own time of day and weather presentation run as usual (the park is paused, so machinery, guests and rain stand still: the sweep moves the camera, not the world). It stands still under reduced motion (`reducedMotion()` / `onReducedMotionChange` from `src/settings/motion.ts`, live: turning it on stops the drift mid-sweep) and is not started at all when `window.__voxelFailure` is set (a voxel renderer that fell back to classic, for example on a software GPU without `&voxelAllowSoftware=1`) or the renderer has no `setCameraCentre`. A test pins zero geometry rebuilds for a panning camera in both renderers and that the voxel frame stages no chunk or dynamic row.

**Pause menu.** Escape in the `world` context (nothing armed, no inspector, panel, popover or dialog open) opens it; so does the Menu button (`☰`, top of the left utility rail, so the 1280x720 top bar is untouched). It remembers the clock speed, pauses, and Resume (button or Escape) gives the speed back; Load and New park set their own speeds, so they drop the remembered one. Entries: Resume, Save (quick save, result shown in the card), Load, Settings, Parks, Quit to menu. Parks opens a chooser panel (Sandbox, Scenario, The Map), since Phase 30 after the Quit question below when there are unsaved changes; Escape in its Sandbox picker or Scenario browser goes where their Back button goes (`menuBackTarget`: the chooser, then the list), and the chooser keeps its own focus memory, so focus returns to the entry that opened a panel and never falls to the page. Quit asks first when the manager says there are unsaved changes (`unsavedChanges`, the Load dialog's rule): Save and quit (a quick save that must succeed, otherwise the park is not left and the reason is shown), Quit without saving, Cancel. Leaving releases the recovery marker and lock (`markClean`), stops autosave (`menuHold`) and shows the start screen over the NEW latest park (the save just written, or the previous one after a discard). Escape is ignored while held (`event.repeat`), so one press cannot open and close the menu.

**Layer order** (`inputContext.ts`, top first): textInput, saveLoad, recovery, settings, rewardDraft / scenarioResult, loadout / parkMap, **menu**, clockPopover, management, inspector, coasterDesigner, build, world. Settings, Save / Load and the Parks map (and its loadout) open FROM the menu and therefore sit above it; the recovery prompt sits above the menu (and only below Save / Load, as before). Escape pops exactly one layer and every older Escape behaviour is unchanged (armed tool, then inspector, panel, popover, dialogs); `menu` has no build or view capability, so no tool, camera or speed key acts behind it. The start screen never shows a finished scenario's result overlay (`menuKind === 'start'` hides it and the context skips it); Continue then shows it exactly as a load would. The HUD is hidden behind the start screen and inert (`inert`) behind the pause menu, the clean-view handle is not rendered over either, and the card is `inert` while a layer above it owns the keyboard (focus returns to the entry that opened it).

**Keyboard and accessibility.** Entries are native buttons in a `role="group"`; arrows, Home and End move focus (`moveMenuFocus`), Tab and Shift+Tab wrap inside the card, Enter or Space activate. Continue (or New park with no save) has the focus unless the player has already moved it. An entry that cannot be used yet stays focusable with `aria-disabled` and its reason as the description, so focus never jumps while it waits. The focus ring is a white gap plus an ink ring (coral on the dark primary entry). The card is a `role="dialog"` named by its title. **New park** no longer starts a park directly: it opens the Sandbox map picker in the same card (Phase 24; `newParkModel.ts` and `NewParkPanel.tsx`, see Biomes and maps), whose radio groups use a roving tab stop, so the Tab trap treats only tab stops as its edges.

**Phase 22 menu (modes).** The start screen's entries are Continue (when a save exists), **The Map**, **Scenario**, **Sandbox**, Load, **Collection**, Settings, About. **The Map** (Phase 23, see The Map (runs)) opens its setup panel (`menuPanel: 'the-map'`: Continue run, a seed field, the difficulty, the route preview, Start run), is described `Five generated parks, one deck of cards` and is the default-focused entry when there is no save to continue (`bootMenuDecision` is unchanged: a first run still skips the menu, and lands in the Sandbox First Day park; nothing opens by itself). Scenario opens the browser panel, Sandbox the map picker, Collection the profile screen; the pause menu's Parks button opens the `modes` panel with the same three choices and Collection is its own entry. Continue's description, the Save / Load rows, the autosave row and the crash-recovery offer name the mode. The chooser is also opened from the result overlay (`openParksChooser`: the result closes and the pause menu opens on that panel; a pending reward draft must be answered first). Known limit: starting a park from the pause menu's Parks does not ask about unsaved changes (parity with the old Parks button).

## Keybindings

Every game shortcut lives in ONE registry, `src/settings/keybindings.ts` (pure: no DOM, no store, no import from `src/ui`). `KEY_ACTIONS` lists each rebindable action with id, label, description, group, scope, default key and match rule; `FIXED_KEYS` lists the keys that cannot change (Esc, Ctrl/Cmd+Z, Ctrl/Cmd+S, arrows and Tab/Enter/Space/Home/End inside widgets, pointer gestures). The human-readable list is `KEYBINDINGS.md`, generated from the registry by `renderKeybindingsMarkdown()`; `src/settings/keybindings.doc.test.ts` fails when it is stale (`UPDATE_KEYBINDINGS_DOC=1 npx vitest run src/settings/keybindings.doc.test.ts` regenerates it). To add a shortcut: add a `KeyActionDef`, read it through `resolveKeyAction`/`matchesAction`, regenerate the doc.

- **Scopes.** `view | build | build-not-designer | designer` is a local vocabulary (the registry cannot import `inputContext.ts`). `scopeActiveIn`/`contextsForScope` in `src/ui/inputContext.ts` map it onto `INPUT_CONTEXT_CAPABILITIES`; `inputContext.test.ts` asserts `scopesOverlap` agrees with the real table. Two actions conflict only when their scopes overlap, which is why rotate (R) and the coaster designer's raise (R) coexist.
- **Tokens.** `[shift+](k|c):value`. `k:` = a lowercase ASCII letter matched on `event.key`; `c:` = an `event.code`. Capture stores letters as `k:`, everything else (digits, punctuation, non-Latin keycaps) as `c:`.
- **Layout independence (decision).** Letters match on the character on the keycap, so the labels in the help hint are what works on AZERTY/QWERTZ/Dvorak. Digits and punctuation match on the physical key, because the AZERTY digit row types symbols unshifted; numpad digits count as the digit row. Camera pan is physical (`match: 'code'`) so the WASD cluster survives any layout; the arrows are fixed extra pan keys. Shift matches exactly first; plain letter bindings also fire with Shift held (Shift+G has always toggled the grid). Ctrl/Cmd/Alt never reach a game binding. IME composition and dead keys are ignored.
- **Rules.** One key or none per action. Reserved (refused with a message): Esc, Tab, Enter, Space, Backspace, Delete, arrows, Home/End/PageUp/PageDown/Insert, F-keys, CapsLock/NumLock/ContextMenu, anything with Ctrl/Cmd/Alt, bare modifiers (ignored). Conflicts inside overlapping scopes are refused naming the holder (no auto-swap). Camera keys cannot use Shift.
- **Storage.** Settings schema v2 adds `keybindings` (sparse overrides, `null` = unbound). `MIGRATIONS[1]` adds `{}`; frozen fixtures `src/settings/__fixtures__/settings-v1.json` and `settings-v2-keybindings.json` pin the migration and the per-entry validation (`validateKeybindings` drops unknown ids, bad or reserved tokens and clashing entries, keeps a legitimate swap, and always returns a conflict-free set).
- **Consumers.** `GameApp.handleShortcuts` switches over `resolveKeyAction(...)`; `planPeekKey` uses `matchesAction('peek', ...)` (release ignores modifiers, scope and Shift so a hold never sticks); `worldInput` tracks held keys by `event.code` and asks `settingsPanCodes()` (injectable, like `sensitivity`). All read `getSettings().keybindings` at event time, so a rebind applies at once and follows cross-tab sync.
- **Labels never go stale.** `withKeyHint`, `keyLabel`, `ariaKeyShortcuts`, `helpHintItems` (`src/settings/keyHints.ts`) default to the live settings; components call them with `useKeybindings()` so they re-render on a rebind. `src/ui/keyHints.static.test.ts` fails on a literal "(G)"-style key in a title or aria-label in any `src/ui/*.tsx`.
- **Settings UI.** `KeyboardSettings.tsx` (collapsed `<details>` in the Settings panel) over the pure reducer `keyboardSettingsModel.ts`: press-a-key capture on a window capture-phase listener (swallows the key, Esc cancels only the capture, the dialog's Tab trap stands down via a ref), inline refusal message plus one polite status region, per-row Clear/Reset (Reset is refused when the default now belongs to another action), Reset all, the fixed keys listed. Fully native buttons, so keyboard operable.
- **Phase 11.** `recentreView` (default V, group and scope `view`) moves the camera back to the entrance with a glide;
  it has `yieldsDefault: true`, so a stored player binding on V wins and the action loads unbound
  (`keybindings.recentreMigration.test.ts`, the Phase 26 Q/E pattern). `Delete / Backspace` is a `FIXED_KEYS` row
  (both keys are reserved for text fields, so it cannot be rebound): in the `inspector` input context only, with no
  modifier and no key repeat, it opens the demolish confirmation exactly like the button, focus on Keep it.
- **Tests.** `keybindings.test.ts`, `keybindings.doc.test.ts`, `schema.test.ts`, `settingsStore.test.ts`, `inputContext.test.ts`, `worldInput.test.ts`, `keyboardSettingsModel.test.ts`, `GameApp.keys.test.ts`; real UI: `phase18/e2e-keys.mjs`.

The generated list of every shortcut is in [KEYBINDINGS.md](KEYBINDINGS.md).

## Accessibility

Phase 18 step 3 (keyboard and screen reader). The decisions are pure and tested; the DOM code is thin.

- **Files.** `src/ui/a11yModel.ts` (pure: roving-focus targets, live-region policy, label builders, WCAG contrast; `a11yModel.test.ts`), `src/ui/a11yHooks.ts` (`handleRovingKey`, `useFocusReturn`, `useModalFocus`), `src/ui/a11y.css` (the one focus ring, the structural helpers and the muted-text colours; imported once from `main.tsx`, after `styles.css`, on purpose). `a11yCss.test.ts` reads the stylesheets and fails if the ring tokens lose 3:1, a muted-text override drops under 4.5:1, a11y.css is imported anywhere else, or a `:focus` rule removes the outline without drawing a replacement.
- **One focus ring.** Tokens `--focus-ring` (ink), `--focus-halo` (cream), `--focus-width` (3 px) and `--focus-offset`: an ink outline with a cream gap, which reads on cream paper, on ink and on the green panels (WCAG 1.4.11, 3:1). It is CSS pixels inside the zoomed `.ui-layer`, so it scales with UI scale. Panels that clip (`.pulse-card`, `.management-dashboard`) draw it inward instead, or the panel edge would cut it. The start / pause menu keeps its own white-then-ink band. A new control gets the ring by being a native button, link or input; nothing else is needed.
- **Roving focus.** The build category tabs and the dashboard tabs are real `tablist`s (`role=tab`, `aria-selected`, `aria-controls` only on the selected tab, a `tabpanel` named by its tab); Left/Right/Home/End move focus and select (automatic activation), and exactly one tab is a Tab stop. The build card grid is one Tab stop too (the last card focused, else the armed one, else the first); arrows move through it, Up/Down by a row (the column count is read from the layout, `columnsFromOffsets`), Home/End jump, Enter or Space arms. The category tabs share one flex row with the tool buttons through `display: contents` on the `tablist` wrapper, so the tablist holds only tabs.
- **Focus management.** Save / Load, Settings, the recovery prompt and the menu keep their own traps (they predate this step and are tested). The Parks map, its loadout and the scenario result use `useModalFocus`: focus moves in, Tab wraps, focus goes back to the opener. Non-modal panels (the management dashboard, both inspectors, the clock popover) use `useFocusReturn`: if the panel closes while focus was inside it (Escape), focus goes back to the control that opened it, never to `<body>`; a panel opened by a map click has no opener and nothing happens. The pause menu returns focus to the ☰ button. Price steppers, tab rovers and the card grid keep focus across re-renders (keys are stable, nothing remounts).
- **Live regions** (all mounted while empty, because a region added together with its text is not reliably announced). Toasts: the visible toast is `aria-hidden`; a polite `role=status` and an assertive `role=alert` region carry the words, chosen by the notification class (alerts and refusals interrupt; important and routine wait), each message a new child so the same refusal twice is spoken twice, routine messages rate-limited to one per 1.5 s, repeats dropped (`planToastAnnouncement`). Park Pulse: `PulseAnnouncer` is given only the lines on screen (Phase 30) and says only a line that was NOT there before (a new weather note or guest concern, never a count and never a notification), at most once per 12 s, and nothing on first look (`planPulseAnnouncement`). Management pop-ups: the cards are plain buttons; speech is a separate pair of regions, each notification once and only there (one event, one utterance), critical ones assertive, at most two per update, nothing on first look after a load (`planNotificationAnnouncements`). Price and track-height values are polite `role=status` so a stepper press is heard.
- **Names and roles.** Every icon-only button has an `aria-label` that starts with, or equals, its visible text (WCAG 2.5.3), decorative glyphs are `aria-hidden`, toggles use `aria-pressed`, meters are `role=meter`, charts `role=img` with the latest value, panels are labelled `aside`s or `group`s, dialogs are `aria-modal` and labelled by their heading, shortcut keys come from the registry through `aria-keyshortcuts` and tooltips, and the tooltip is never the only name. Small print was darkened (a generated block in a11y.css, AA on the darkest paper tint).
- **Exception, documented.** Construction gestures (placing, dragging a path, the bulldozer drag, laying coaster track, camera drag and wheel) stay pointer-based. The keyboard can arm any tool, rotate, adjust coaster height, cancel, pan and change speed, and operate everything else; a keyboard-driven cursor is not built.
- **The audit.** `phase18/a11y-audit.mjs` (not in the repo: a backup of it and the other Phase 18 scripts is in `.voxel-handoff/a11y-layout-audits.tar.gz`) drives the real UI through about 40 states and checks, per state, Chromium's accessibility tree (every control named, dialogs, panels, meters), DOM wiring (duplicate ids, `tabindex > 0`, dangling `aria-*`, tablist / tab / tabpanel), a Tab walk (every visible control reachable, focus kept inside a modal, a visible and unclipped ring at 3:1), arrow walks of every roving group, focus return, live regions, and axe-core. `e2e-a11y-keys.mjs` operates the whole HUD with the keyboard only. Not covered here, because it cannot be: real screen readers (NVDA, VoiceOver, TalkBack), a high-contrast mode, and the voxel renderer's canvas, which has no DOM.

### Layout guard (Phase 18 step 3)

No two floating panels may overlap, nothing may leave the screen, and meaningful text may not be cut,
at every supported window size and UI scale. This is enforced by one pure model and one browser audit.

**Supported matrix.** Windows of 1100x690 and larger (1280x720, 1366x768, 1440x800, 1536x864, 1920x1080 are the audited
sizes) at UI scale 85, 100, 115 and 130 %. Scales above 100 % are capped by `effectiveUiScale` so the UI layer never gets
smaller than 1100x690 of its own pixels (`UI_LAYOUT_MIN_*` in `src/settings/uiScale.ts`). 1024x640 is the *stress* size
below the minimum: only the base states (start screen, Settings, Save / Load, the Parks map, pause menu, dock, dashboard
overview, First Day) are required to be clean there; combined states are best effort. Windows narrower than 820 layout
pixels use the older stacked top bar and are not a supported size.

**One place for the numbers.** `src/ui/layoutModel.ts` is pure: the panel registry (`FLOATING_PANELS`: id, selector,
layer), the allow-list (`ALLOWED_OVERLAPS`, every pair with a reason), `rectsOverlap`, `findOverlaps`, `outsideViewport`,
the viewport matrix (`VIEWPORTS`, `supportedMatrix`) and the anchor model (`ANCHORS`, `anchorModel`: where the rail, the
dock and Park Pulse sit at a given layout size). `layoutModel.test.ts` proves the base layout is overlap-free in every
supported cell and reads `styles.css` to fail when an anchor number (pulse width, rail position, dock width and bottom,
`--dock-reserve`, the 720px compaction breakpoint, the grid tracks) drifts from the model.

**Layers.** `hud` panels never overlap each other. `toast` panels (save banner, toast, notifications, save strip) own the
centre band and never overlap HUD panels. A `popover` (the clock settings dropdown) may cover HUD panels and toasts, never a
dialog, because the player opened it and it closes on an outside click or Esc. `dialog` panels (Settings, Save / Load, the
Parks map, the result, the menus, the recovery prompt) may cover HUD and toasts, because a backdrop or click catcher sits
behind them; two dialogs may overlap only where listed (Settings, Save / Load, the Parks map and the recovery prompt opened
over the menu).

**How the CSS keeps it true** (`styles.css`, tokens on `.ui-layer`):

- `--dock-reserve` (232px): bottom edge to the top of the tallest dock plus a gap. The help hint sits on it.
  `--side-floor` (252px): the lowest edge of the side panels (inspector, coaster designer, performance overlay); they scroll
  inside their own box instead of reaching the dock.
- The inspector sits beside Park Pulse (right 300px), never under it: Park Pulse grows with First Day, the Map offer, a
  scenario or research, so nothing is stacked under it.
- The message stack (save banner, toast, notifications) is the only in-flow content of `.ui-layer`, a grid of
  `[--band-l | centre | --band-r]` whose rows stack the three, so they never need hand-tuned offsets. The band narrows by
  `:has()` beside the coaster designer, the inspector and the management dashboard. The grid uses tracks, not padding,
  because padding would shrink the content box that the `@container ui` queries measure.
- Short layouts (container height up to 720px) tighten Park Pulse by about 45px; narrow layouts (width up to 1216px) drop
  the help hint (it is 640px wide and would run under Park Pulse); the clock popover and the coaster designer scroll inside
  a max-height.

**Audit.** `phase18/layout-audit.mjs` (scratch tools, repeatable; needs a dev server with the classic renderer):

    node layout-audit.mjs [--only state,state] [--vp 1280x720,...] [--scale 100,130] [--tier supported] [--shots] [--dump] [--verbose] [--list]

It opens a real dev park per viewport and scale, drives about 50 combined states (top bar chips with the popover, Park Pulse
with First Day and the Map offer, inspectors, the dashboard tabs, every dock category, toasts, notifications and the save
banner stacked, the coaster designer, the performance overlay, a scenario HUD and result, Settings with the keyboard section,
Save / Load, the Parks map and loadout, the start and pause menus) and asserts overlaps, off-screen panels and controls,
controls cut by an `overflow:hidden` ancestor, scrolling of the page, truncated text outside a short allow-list of
intentional ellipses, and that dialogs really stack above the HUD. Every state lists the panels that must be on screen, so a
recipe that silently stopped working fails as `MISSING` instead of passing vacuously. Entrance animations are disabled for
the measurement. Exit code 1 on any finding; `--shots` saves a PNG per failing state.

## Renderers

Terrain, path colours, props and the entrance framing are per map and biome in both renderers (Phase 24, see Biomes and maps).

`src/rendering/RendererPort.ts` is the seam between `GameApp` and whatever draws the world: `mount`, input handlers, the per-frame `update(deltaMs, elapsedMs, stepFraction)`, camera queries and a `RendererPerformance` readout. `GameApp` holds one port and never imports a concrete renderer except through it. `setCameraCentre?(cellX, cellY)` is the one camera call GameApp makes per frame, for the start screen's sweep (see Menus). Two implementations exist. The voxel renderer (`src/rendering/voxel`) is the main renderer and is what every plain URL gets. The classic `WorldRenderer` (Pixi scene graph) is the automatic fallback when the voxel renderer cannot run, and can be chosen with `?renderer=classic`. Both share `src/rendering/worldInput.ts` (picking, drag pan, wheel zoom, placement gestures, so the two cannot disagree about input) and `src/rendering/coasterTrain.ts` (where on the track a train is, including the interpolated remaining cycle time). Fixed-camera voxels are a visual change only: the camera, terrain and simulation are unchanged, so this is not the "Full 3D" (free camera, terrain) listed under not-now in the plan.

**First Day UI.** The step-1 engine is shown in three places, each a pure model plus a thin component or seam. (1) Park Pulse: `src/ui/firstDayModel.ts` turns an `OnboardingSnapshot` into a `FirstDayView` (hidden | step | finished) and keeps the "step done" moment (`nextCelebration`, monotone per `parkEpoch`, so undo and redo never celebrate twice and a new park or load only re-seeds); `FirstDayCard.tsx` renders it as a sibling of the pulse launcher, with real `Skip step` and `Hide hints` buttons that go through `gameBridge.skipOnboardingStep()` / `dismissOnboarding()` to the tracker and republish the snapshot at once. No modal, no focus trap, no key handlers, no new input context. (2) World pointers: `ParkSession.onboardingFocus()` (read-only; `src/game/onboarding/focus.ts` picks the cells per step from a small probe, `ManagementSimulation.connectivity().tip` is the farthest connected path tile) feeds `src/app/hints/hintMarkers.ts`, which holds every off rule (no hints, dismissed, clean view, a context with build and view both off, the price hint while a ride is selected). `GameApp` re-reads the focus at 4 Hz and after each sync and calls `RendererPort.setHintMarkers` only when `hintMarkerKey` changes. The voxel renderer draws a pulsing ring in its overlay target (`overlay/hints.ts`, two prebuilt phases, two overlay renders a second); the classic one draws one Graphics in `hintLayer` and pulses with a single alpha write. Both are static under `prefers-reduced-motion`. (3) First run: `ProfileManager.isFirstRun` (storage works and held no profile) and the profile's `ui` flags (`tourOffered` = the one-time offer was answered; `mapSeen` is legacy and unread). **Phase 23 decision: a brand-new profile lands in the Sandbox First Day park and nothing opens by itself** (the Park Tour map that used to open over it is gone). `src/app/firstRun.ts` decides when the one-time "Ready for The Map?" offer shows (`shouldOfferMap`: sandbox park "stable": Fix a problem done, or every step done or skipped; dismissed hints never offer); the answer (`resolveMapOffer`) is remembered for good and "Open The Map" opens the pause menu on The Map's setup panel. Skip and dismiss are player choices, not park history: they are not undo entries and `adoptDismissals` keeps them across an undo.

**Time of day (Phase 20).** `GameApp.appTicker` hands the renderer ONE number per frame, `RendererPort.setTimeOfDay(phase)` (the effective clock fraction at `tick + stepFraction`, so it is smooth between steps and frozen while paused). Presentation only: nothing flows back. `src/rendering/dayCycle.ts` turns it into weights over the three authored looks (day, dusk, night; keys and ramps are data in `GAME_CONFIG.calendar.lookKeys`, smoothstep between keys, dawn is a derived dusk/night mix). The presets in `lightPresets.ts` are never edited (a test freezes them). Voxel: `voxel/dayLook.ts` blends them into a reusable scratch; `VoxelRenderer` re-blends only when a weight moved, `VoxelGpu.applyLook` writes composite/light uniforms only (no recompile, no geometry, no light-texture upload). `lightPass` is a threshold on the blended strength (0.02, below which the quantised pools cannot reach their first band, so the lamps fade instead of popping); `uPresetBit` is the union of the presets that carry weight; the background fades through a premultiplied `uBackground.a` (`vxBackground`). `LookModifiers` is the hook the step 3 weather look fills (see Weather presentation). Classic: one multiply tint on the camera container (`classicDayTint.ts`), written only when the quantised colour changes.

**Arrival curve, opening hours and weather (Phase 20, step 2).** `GuestSimulation.updateArrivals` drains its spawn countdown at `conditions.arrivalRate` (the curve in `GAME_CONFIG.calendar.arrivalCurve` at the RAW clock hour, times the weather factor; exactly 1 under neutral conditions, so a standalone guest simulation is bit-identical to before). The curve's day-long mean is 1, `calculateOrganicGuestPotential` is not scaled, so the 6-hour night dip lowers the mean population of a small park by about 7 % (measured on the pacing route). `ParkConditions` (`weather/types.ts`) is one object overwritten in place every tick by `WeatherSimulation.step`, called by `ParkSession.step` right after `world.advanceTick` and before `guests.step`; it is derived (a pure function of tick, calendar, weather and rules), never saved, and shared by reference with the guest and ride simulations. Opening hours live in `CalendarState` (`hoursEnabled`, `openHour`, `closeHour`, off by default) and reach the gate through `GameWorld.gateOpen` = the player's `parkOpen` AND `conditions.scheduleOpen` (the six readers of `parkOpen` use `gateOpen`; `parkOpen` stays the manual switch the toggle shows). Weather is saved plain data (`WeatherState`: switches, a uint32 stream state seeded from `mixSeed(session.seed)`, the chain's last kind, `firstDay` and the drawn `days`): days are drawn lazily when a day first comes into view, five draws per day, always keeping yesterday, today and two forecast days, so the forecast IS the saved future and a later change of the chain constants cannot rewrite a park in progress. Day 1 is fixed sunny and slot 0 of every arc is dry, so no rain can fall inside the 15 minute First Day window. A day has four six hour slots (06-12, 12-18, 18-24, 00-06) whose kinds follow the arc of the day's kind. The sandbox severity (low/normal/high) scales intensity only, never which weather comes; weather off keeps the chain advancing and reads as a clear sky. Storm closure of open-air rides is DERIVED (`RideSimulation.isStormClosed` = storm active AND the catalog's `openAir !== false`): the player's `open` is never touched, so the ride reopens by itself when the storm ends, a player-closed ride stays closed (`RideSnapshot.closureReason` is `'player'` or `'storm'`, the player wins), and nothing extra is saved. Covered rides: Moonpetal Carousel, Petal Roundabout, Thunder Drum. The read-only presentation seam is `ParkSession.weatherViewInto(out, tick)` (allocation-free, `WeatherView` with kind, intensity 0..1, previous kind, slot progress, seconds into the slot and a storm flash seed) and `weatherForecast()`; `RendererPort.setWeather?` gets the view once per frame next to `setTimeOfDay` (both renderers implement it in step 3) and `stormFlashAt(flashSeed, secondsIntoSegment)` returns the flash strength and bolt seed as pure data. UI: `src/ui/weatherModel.ts` builds `WeatherUi` (primitives, written to the store at 4 Hz only when its key changed), the chip, the forecast rows and the Park Pulse "Weather:" lines. Scenario parks have fixed weather and hours: the setters refuse and `checkSessionConsistency` rejects a scenario save with weather off, another severity or hours on. Undo rewinds the drawn weather and the stream with the park and keeps the player's switches (`ParkSession.adoptSettings`).

**Weather presentation (Phase 20, step 3).** Presentation reads the typed `WeatherView` and never feeds back: no simulation file knows it exists, and `GameApp` is unchanged (it already calls `setMachineryPaused`, then `setWeather`, then `update` each frame). `src/rendering/weatherLook.ts` is the renderer-neutral core both renderers own an instance of. Per frame: view -> target drivers (`cover, shade, rain, wet, heat, gloom, storm`, a table per kind scaled by intensity) -> drivers slewed on REAL time (so a slot edge, a load, an undo, a sandbox switch or a pin eases instead of popping, also while paused, and the first frame snaps) -> `WeatherEffects` (one reused object of quantised numbers: cloud cover, strength, offset and tint, rain density, slant, two phases and tint, wetness, puddle, ripple, shimmer, flash, gloom and `LookModifiers`). `effects.revision` moves only when a quantised value moved, so a calm, settled or paused frame is detectably unchanged and a renderer writes nothing. A clear sky, weather off, or intensity 0 gives every driver and effect exactly 0 and `active` false (endpoint exactness, tested). Weather off and the sandbox low/normal/high severity already reach the view (`enabled`, scaled `intensity`), so the presentation respects them for free. Time bases: the animation clock (cloud drift, rain fall, shimmer) is real dt, frozen while the game is paused; sim time (`secondsIntoSegment`) only decides WHEN a storm flashes (`stormFlashAt`). Clouds are shadows and gloom, not bodies (a top-down iso view has no sky and visible clouds would need alpha). Colour floors: rain and storm may cool and dim but never grey the candy colours out (cloud tint channels >= 0.78, classic tint channels >= 0.58; the day, dusk and night presets are untouched). **Photosensitivity cap.** Lightning is the only flashing effect. `FlashLimiter` admits at most `MAX_FLASHES_PER_SECOND` = 3 pulse onsets in any one real-time second whatever the game speed (WCAG 2.3.1), a suppressed pulse stays dark until it ends, the level rises at most 12/s and falls at most 6/s (never an instant step), the lift is a soft global exposure change and never a full-white or strobing area (classic lifts at most 60 % toward white), and a paused game and prefers-reduced-motion show no flash. **Reduced motion** (`prefers-reduced-motion: reduce`, the same media query the hint markers use, read once per renderer; Phase 18's settings screen does not exist yet, so the query is the only switch): clouds stand still at a fixed offset, rain becomes a static light texture (density capped at 0.35, off below 0.05), no flash, no shimmer, no ripples; wetness, cloud shadows and gloom stay (they are not motion) and the weather chip and Park Pulse text still explain the weather. **Paused:** drift, rain and shimmer freeze mid-frame like machinery, and the flash target is 0. **Testing flags** (presentation only, the HUD chip, Pulse and the simulation keep the real weather; pin wins over the sandbox weather-off switch): `&weather=sunny|hot|cloudy|rain|storm` with `&wintensity=0..1` (default 0.8), `&wclock=<seconds>` freezes the animation clock for deterministic screenshots, `&wmotion=run` keeps animating while paused, `&wflash=0..1` holds a constant flash level (still 0 under reduced motion), `&voxelWeather=off|rain` limits the voxel pass. **Classic renderer** (`src/rendering/classicWeather.ts`, deliberately simple): a fixed pool of 6 cloud-shadow sprites (one shared soft-ellipse texture, MULTIPLY blend so a shadow only darkens and cools, in the camera container so it is anchored to the park) and 160 rain streak sprites (screen space above the camera), all created once; per frame only property writes, and only when the effects moved (a signature compare), so there is no display-object, Graphics or array churn (a test pins the object count and zero draw calls). Gloom and the flash go through the existing camera tint (`classicTint(weights, gloom, flash)`, same 64-step quantisation, written only when the colour changes). No puddles and no shimmer in classic. **Voxel renderer specifics.** The pass lives in the composite only: no geometry, no new texture and no sampler (0 added samplers). `weatherUniforms.ts` writes 22 uniform floats (`uWxA..uWxD` vec4s plus two vec3 tints; layout in the header of `shaders/compositeWeather.ts`) and writes them only when `effects.revision` moved, so a calm, settled or paused frame writes nothing (tested together with the zero-rebuild frame test with every effect active). The GLSL chunks follow the fxc rules (no loops, arrays, structs or dynamic indexing, integer hashes, each hook called once per main; `compositeFxc.test.ts` and `weatherShaderGuard.test.ts` enforce them) and there is no runtime recompile: the tier is chosen at build. Tiers: `full` (rain, cloud shadows, wet ground and puddles, shimmer), `rain` (the lite composite: rain only, no noise octaves or neighbour reads) and `none` (hooks are pass-throughs). Every effect sits behind one uniform compare, so a clear sky costs one branch per texel. Rain streaks use a FIXED slant (a quarter column per row): an eased slant would re-hash every streak column on each step and pop on every rain-to-storm ramp; the classic layer rotates its streaks instead. Colour: gloom dims exposure and ambient and LIFTS saturation (x1.12 at full gloom), so measured at noon the ground keeps its HSV saturation (sunny 0.390, rain 0.395, storm 0.403 at intensity 1; value 0.80 to 0.73 to 0.70). **Fallback chain:** full composite + weather -> (weather pass fails to compile or run) no-weather -> lite composite + rain -> lite + no weather -> no lights and shadows -> classic renderer; a runtime weather failure falls back to clear weather without losing the voxel renderer and appends `no-weather` to `window.__voxelDegraded`. **Reduced motion is live:** both renderers subscribe to the media query's change event (`watchReducedMotion`, released in `destroy`), so flipping the OS setting stops clouds, rain and flashes on the next frame. **Measured costs** (headless SwiftShader, `tools/frametime.mjs`; frame intervals are dominated by software-GPU noise and cannot separate the cases): page-callback time 1.05 to 1.14 ms in every case (clear, rain, storm, lite storm, weather off), 22 uniform floats, 0 added samplers.

**Crowd heatmap (Phase 14, voxel only).** `RendererPort.setCrowdHeatmap?(view | null)` is OPTIONAL, like `setPaintHover?`: the classic renderer omits it (legacy, so a no-op by omission) and GameApp reads its absence as "unsupported". `VoxelOverlays` draws a `crowdLayer`, the first child of the overlay root, under the scenery heatmap (order: crowd, scenery influence, selection, hints at index 3, draft, preview, paint). One Graphics per redraw: one diamond per path tile, one fill per band (quiet 0x7aa7d9, normal 0x3fbfa0, busy 0xffb347, severe 0xff4f6d at alphas 2/8, 3/8, 5/8, 6/8, the overlay's dither) and an opaque white 1-texel rim on the outer edges of the severe set; 111 tiles without a severe one is 115 calls, then one overlay-target render. The same `revision` again is 0 Graphics calls and no overlay render, so GameApp may push every publish; `null` hides and keeps the drawing; a view turn redraws once with the other layers; a new revision is copied (the caller may reuse its arrays); `setSession` forgets the view, so GameApp pushes the new park's view after every swap. Checked in the browser on all six biomes by day and three at night: the four bands stay distinct; quiet is faint on autumn and desert paving by design.

**Flags** are read once from the URL by `src/app/rendererFlag.ts` and, unlike `?dev=1`, are never remembered in localStorage, so a choice made for debugging cannot stick to a browser. `renderer=classic` selects the classic renderer (anything else gets voxel); `light=day|dusk|night` pins the voxel look to one preset and ignores the clock (an explicit override; without it the look follows the park clock); `time=0.75|18|18:30` pins the LOOK to a time of day (a fraction needs a decimal point, hours are 0..23, so `1` is 01:00; the HUD keeps the real clock); `zoom=N` sets a starting zoom in device px per texel; `voxelAllowSoftware=1` runs on a software rasteriser (SwiftShader, llvmpipe), which is otherwise refused; `voxelGpu=min` is a measurement harness that keeps the CPU work and uploads but clamps draws and targets; `voxelDebug=1` checks the GL error queue after every call and logs the first failing one; `voxelComposite=lite` starts with the degraded composite; the weather testing flags (`weather`, `wintensity`, `wclock`, `wmotion`, `wflash`, `voxelWeather`) are described under Weather presentation above.

**Loading and fallback.** Both renderers are lazy chunks (the voxel one since it shipped, the classic one since Phase 34), so a voxel chunk that fails to load is one more reason to fall back; `GameApp.classic.test.ts` asserts that `?renderer=classic` never loads the voxel module, `GameApp.voxelOnly.test.ts` that a voxel game never loads the classic one, and `bundleSplit.static.test.ts` checks the same in the static import graph. The fallback now downloads the classic chunk at the moment it is needed; if that download fails too, the mount rejects as a failed classic mount always did (the fatal screen). If the voxel renderer cannot run, `GameApp` mounts the classic renderer on the same session and sets `window.__voxelFailure` to the reason. Triggers: missing WebGL2 or required capabilities, a software GPU without `voxelAllowSoftware`, a link or draw-time failure found by the startup validation (`validateGpu` in `boot.ts`), an error thrown mid-game (`onFatalError`), and a context that is lost and does not return. There is an intermediate level: a composite shader that fails to compile or draw (the Windows ANGLE/Direct3D failure "Error compiling dynamic pixel executable" appears at the first draw, not at link) makes the renderer rebuild with the lite composite (no neighbour taps, outlines or light pools) and set `window.__voxelDegraded = 'composite-lite'`. Features whose own programs fail (lights, shadows) are skipped the same way.

**Bundle and chunks (Phase 34).** The entry chunk (`index-*.js`) holds React, the simulation, the app shell and the
always-mounted UI; the build splits off, as lazy chunks, the voxel renderer (`VoxelRenderer-*.js`, about 314 kB), the
classic renderer (`WorldRenderer-*.js`, about 122 kB), Pixi and the rendering code both renderers share
(`worldInput-*.js` about 249 kB, plus `Geometry`, `RenderTargetSystem` and smaller Pixi chunks), the load path with the
migration chain (`loadSave-*.js`, about 10 kB), and three panels that a session may never open: Settings with its
Keyboard section, Save / Load and Paint (`src/ui/lazyPanels.tsx` holds their open checks, a retryable `React.lazy` and
an error boundary that closes the panel with a toast if its chunk cannot be fetched). The save worker is its own bundle.
Rolldown moves modules that the entry shares with a lazy chunk into small common chunks (`parse`, `effects`,
`jsx-runtime`, `vanilla`, `motion` and a few under 3 kB), which the entry imports statically, so the initial load is the
entry plus those (10 files). What may not reach the entry statically is pinned by `src/app/bundleSplit.static.test.ts`
(pixi.js, both renderers, the load path, `migrate.ts`, `fromSave.ts`, the three panel bodies; and neither renderer
reaches the other). Size: `build.chunkSizeWarningLimit` is 1,025 kB (the entry is about 976 kB raw), and
`src/app/bundleBudget.test.ts` (opt-in, `BUNDLE_BUDGET=1`) builds in memory and fails when the entry passes 301,700 B
gzip or the initial load 363,300 B gzip (Phase 34 measurement plus 5 %). Kept in the entry on purpose: the per-owner
restore validation and `consistency.ts` (snapshot undo restores through `ParkSession.fromState`), the start menu's
panels (their focus contract moves focus into the panel when it opens) and the Management dashboard and Map screens
(opened in most sessions).

**Voxel pipeline.** Space is 2:1 isometric voxels, 32 per tile. Everything is axis-aligned boxes drawn by vertex pulling: the vertex shader reads box words from RGBA32F data textures by `gl_VertexID` and no vertex attributes exist. There is one draw per static chunk (16 for the dev park) plus draws for figures, shadow decals, lights, the ghost and the coaster draft. Passes write an MRT G-buffer (material, face, position) and sampled depth into a low-resolution target; the composite pass shades from it (face light, outlines where a neighbour texel is farther, a contact shadow, and light pools at dusk and night); an integer upscale puts it on the canvas, so the picture is pixel-art by construction. Colour comes from a 256-entry palette built from the catalog, with 15 world-anchored patterns (stripes, roof tiles, grass, windows) keyed on world position so they do not swim when the camera pans. Translucency is a Bayer dither, never alpha, which keeps the depth buffer valid. The low-res target is sized to a texel budget (`LOW_RES_TEXEL_BUDGET`, 2.2 M) and zoom is an integer number of device px per texel, chosen per screen. Models are blueprints (parts of a few shapes), compiled to boxes at runtime by `blueprint/compile.ts` (voxelize, hollow, greedy mesh) and cached per rotation; prewarm is time-budgeted per frame. Guests and staff are figures built from keyframed 8-box templates packed per frame (Phase 29: 22 keyframe columns — the walk, standing and 17 poses such as sitting, hunching, being sick, cheering, fanning, shivering, pointing, a camera, stomping, eating and waving — chosen per guest from its state and `activity` and alternated on simulation time; five more guest models carry a souvenir in up to 10 boxes, ranges indexed by `FigureModel`; a resting guest is drawn on its bench seat although the simulation keeps it on the path); rides move by rigid parts with a pivot. Moving things are interpolated by `SimulationClock.stepFraction`, but a step larger than a teleport threshold is never interpolated, and walk frames run on simulation time so a paused park is still.

**Scene and GPU split.** `VoxelScene` (`scene/`) is pure: it turns the session into chunks, figures, lights and dirty data, and talks to a `VoxelGpuSink` interface; it has no WebGL and is unit-tested with a recording sink, including an equivalence test between incremental and from-scratch static worlds. `VoxelGpu` (`gpu/`) is the sink that owns programs, textures and targets and is the only place that touches Pixi's renderer for drawing. `VoxelRenderer` wires them, owns the camera and overlays, and implements the port.

**Performance rules.** Opaque programs contain no `discard` (it disables early depth and hurts tiled GPUs; dither is done by writing nothing to the colour or by pattern, not by discarding). The exceptions are `worldCut` and `worldFront` (see-through, below), which are bound only while the cutaway is active and only for the chunks the hole touches. Nothing in the voxel renderer blends, except the one mix of the see-through front layer over the revealed scene inside the hole's rectangle (shaders/composite.ts, `VX_TRANSLUCENT`): everything else stays crisp, binary and dithered. The composite must stay compilable by fxc, Direct3D's compiler: no loops with texture reads, no arrays of structs, every `texelFetch` clamped, with a fetch budget (`COMPOSITE_FETCH_BUDGET`); `gpu/compositeFxc.test.ts` checks these statically against the shader source, because a browser test on Linux cannot reproduce the failure. The steady state rebuilds nothing static: a test requires zero static-chunk rebuilds per frame with nothing changing, and uploads on a steady frame are one small figures row range and one transforms row.

**Adding a model.** Write a blueprint in `src/rendering/voxel/content/` (part 0 is the `body`; integer pivots; moving parts must not overlap the body at rest, which the compiler does not detect, so add a content test as the existing ones do), register it for its catalog id in `content/registry.ts`, and add its colours to the catalog so the palette picks them up. A model that fails to compile falls back to a placeholder box and is logged, never thrown per frame. The compiler is the only authority on what a model looks like in the game.

**Renderer settings and figure culling (2026-10-14).** The renderer and the voxel composite are player settings
(`renderer`, `graphicsDetail`; Settings > Graphics), read once at start (`rendererFlag.ts` `rendererKindOf`: a URL
`?renderer=` wins; `requestedCompositeVariant` reads `&voxelComposite=` first). A degradation the GPU forces
(`window.__voxelDegraded`) is told once (GameApp `noticeDegradation`). The figure packer writes only the guests and staff
inside the camera's view (the low-res target's texel rectangle mapped to world cells, plus 3 cells); their histories stay,
so interpolation survives leaving and re-entering the view.

## View rotation

Phase 26: the whole map turns in quarter steps (keys Q and E, two buttons by the clean-view handle). It is a camera orientation: the simulation, the determinism hash and the undo ring never see it. Step 1 delivered the orientation model, the shared input mapping, the app state and the classic renderer; step 2 the voxel renderer (its own section below). Both renderers turn.

### Model (`src/rendering/viewRotation.ts`)

`ViewRotation` is 0 to 3; `q + 1` turns the map 90 degrees clockwise on screen about its centre, so the map stays centred. A `ViewFrame` is the rotation plus the WORLD map size it pivots about. The module is pure and allocation-free (every transform writes into an `out`), and every function is the identity for q = 0, so view 0 is bit-identical to the unrotated game. Two spaces: cell-index space (`cellToView`, `cellFromView`: cell centres are integers) and point space (`pointToView`, `pointFromView`: continuous, for the camera, the coaster centre line and cloud shadows). Vectors (`vectorToView`: tangents, frame axes, directions) take the linear part only and z is never touched. A building with world rotation `r` is drawn as `rotationInView(r, q) = (r + q) & 3`, and a footprint rectangle maps to a rectangle (`rectToView`: min corner, sizes swapped on odd turns). `compassAngle(q)` is the screen direction of world north. The build rotation (`R`) keeps its WORLD meaning everywhere; only drawing applies the view.

### Input (`src/rendering/worldInput.ts`)

`bindWorldInput` takes a `viewFrame` getter (read on every event, like the sensitivity). Picking is `pickCell(frame, worldX, worldY) = fromViewCell(frame, worldToCell(...))`, so hover, drag, path drag, bulldoze, the coaster designer, selection and the see-through focus all receive WORLD cells under the pointer in every view. WASD, arrow and drag pan stay in screen space (they move the camera container, not the world). `WorldInput.rehover()` re-picks under a still pointer after a turn (hover only), so the ghost is redrawn. `WorldInput.gestureHeld` (exposed as `RendererPort.gestureHeld`) is true between a tool press and its release or cancel (not while panning); GameApp refuses a turn meanwhile with the toast "Release the mouse button to turn the view", because a drag's last cell was picked in the old orientation and the next move would join it to a cell picked in the new one along a straight world line (bulldozing or paving across the map). A differential fuzz over views x zooms x pointer positions and a "picking in view q equals picking the inverse-rotated point in view 0" test pin this; the 62 existing tests and the fuzz pass unchanged for view 0.

### App state

The rotation lives in the UI store (`viewRotation`) and in the save's `app` block (`app.viewRotation`, optional, validated 0 to 3; a missing value is 0, so the field needed no schema bump), not in the world state: it is outside the world hash and outside the undo ring, undo does not rewind the view, and crash recovery restores it with the rest of the app block. A turn calls `SaveManager.markAppStateChanged()`: an app-state counter, compared with the value the last autosave captured, makes the park dirty for the autosave and the hidden-tab flush (so a turn on a paused park reaches the autosave) but not for `hasUnsavedEdits` or the unsaved-changes flag. The Q and E defaults are marked `yieldsDefault` in the keybinding registry: a stored binding of another action on Q or E (made before Phase 26) wins on load and the rotate action loads unbound, instead of the older binding being dropped. `GameApp` applies it through `RendererPort.supportsViewRotation` and `setViewRotation(rotation, instant?)`. A renderer without support stays at view 0, keeps the saved value untouched and the player gets a toast. Reduced motion, load, new park and a renderer attached mid-park all turn instantly.

### Classic renderer

**Legacy since 2026-10-13.** Frozen by decision: no new features, no new measurements, only the tests that keep it
booting and playable as the automatic fallback (`?renderer=classic`, capability, software-GPU and failure fallbacks).
New world-anchored features are voxel only. Planned removal and the replacement fallback screen are in
IMPLEMENTATION_PLAN.md under "Voxel Renderer".

`WorldRenderer` keeps one mutable `ViewFrame` (`view`) and every placement goes through it:

- `project(x, y)` is the top vertex of a cell in camera pixels in the current view (a reused scratch, no per-frame allocation); `cellSortKey` and `objectSortKey` give the depth keys of points and footprints in VIEW cells (the footprint rect through `rectToView`), so depth sorting is the unrotated algorithm applied to the view. Terrain, paths, plots, fences (a world edge direction turns into a view edge direction), the entrance, objects, guests, staff, litter, bin gauges, ride alerts, the hint ring, the selection outline, the preview diamonds and the ghost all use them.
- Ride art is built with `rotationInView(r, q)`. The art is laid out in footprint cell space (`isoPlot.ts`), so it depends on the footprint axis only: a half turn changes nothing (tested for every ride), and the two builders with a long axis (bumble coach, splash rings) follow the parity. Machinery in the classic art is radially symmetric or a screen-facing billboard; there is no handed art (no entrance, queue end or platform inside the ride sprites). The ride entrance is the gap in the fence where a path touches the plot, which is laid out in view cells and therefore turns with the map. Shops, facilities and scenery are screen-facing billboards and read the same from every side. The entrance gate is a billboard too (its WELCOME text stays upright); it moves with its cell.
- Coasters: `classicCoaster.ts` builds everything from the centre line's plan coordinates and reaches the screen only through `classicTrackX/Y`, `classicOffsetX/Y` and `classicFarSide`; these read the active view (`setClassicView(frame)`, set by the renderer before it builds or places anything; the default is the identity). So rails, ties, supports, chain, brake, stations, the train pose (forward vector) and the bank lean all follow. The station's platform and canopy stay on the side away from the camera: `classicFarSide` turns the direction into view space first (rotation keeps handedness, so the plan-left side is unchanged). A differential test builds a layout in view q and the same layout turned in the world in view 0 and requires every number to match.
- Cloud shadows keep their WORLD anchor: positions are computed in the unrotated field and mapped through the view (`ClassicWeather.setViewMapper`), so the same shadow stays over the same buildings. Rain is screen space and the day tint is the camera multiply, so neither changes. See-through works in view space (the focus rectangle and each object's cached screen box and sort key are view quantities; the world focus still drives change detection).
- A turn (`setViewRotation`) rewrites the view, recomputes the camera so the world point under the middle of the screen stays there, and re-places the scene synchronously while keeping every display object: object containers and the gate are moved and re-sorted (zIndex); plots and fences, coaster track and the path layer are redrawn into their existing Graphics; a ride's machinery depends on the footprint axis only, so it is rebuilt only when the parity flips, and the other axis is then kept detached and swapped back on later quarter turns; the terrain is cached per view class (side swap, checker parity) and swapped in. The moving displays are re-placed and the stored preview, draft, hint ring and selection redrawn. No frame mixes two orientations. Unless instant or reduced motion, one pooled full-screen `Sprite(Texture.WHITE)` tinted to the canvas background (`0x9ed789`) is shown over the already turned picture and fades 0.55 -> 0 with an ease-out over 180 ms, then hides (no snapshot of the old frame). A steady frame still draws nothing in every view (tested). `focusEntrance` keeps its view 0 framing; a turned view centres the midpoint between the gate and the map centre, so the gate is on screen whatever edge it sits on.

Tests: `viewRotation.test.ts`, `worldInput.rotation.test.ts`, `WorldRenderer.viewTurn.test.ts` (kept containers, ride-art swap, terrain cache, veil), `WorldRenderer.rotation.test.ts` (four turns give the identical scene fingerprint, picking agrees with the projection, ghost orientation, zero draw calls per steady frame in all views, ride art audit), `classicCoaster.rotation.test.ts` (the coaster differential). A headless Chromium pixel compare (four turns, same frame outside animated pixels) and the classic screenshot matrix are recorded in the plan.

### Voxel renderer (Phase 26 step 2)

Chosen: a vertex-stage view transform over ONE world data set (design record: `phase26/design-step2.md`), not static chunks rebuilt per orientation and not four lazily built copies. Every box, figure, rigid part, light, litter pile, ghost and draft stays in WORLD voxels, exactly as before; the geometry vertex shaders map world voxels to view voxels with an exact integer 2x2 matrix plus an offset (`uView = (c, s, ox, oy)`, `contracts/view.ts`: `ViewTransform`, `setViewTransform`, `voxelToView`, `voxelFromView`, `vectorToViewVoxel`, `headingInView`, `quarterTurnsOfTransform`, `patternCellShift`), and everything after that point (G-buffer, face codes, outlines, contact shadow, light pass, see-through cut, camera, guard band, integer upscale) runs in view space exactly as in view 0. The matrix entries are -1, 0 or 1 and the offsets multiples of 32, so view 0 is bit-identical. Why: the systems that move every frame (figures, coaster cars, ride parts, lights) are already world data, so they follow the turn with no CPU work and no new upload path; a rebuild per orientation would have made every CPU writer emit view space and cost a cold compile of the half-turn model variants (about 100 ms) on a first turn.

GPU side (`gpu/*`, shaders):

- `common.ts`: `vxViewPoint(p, view)`, `vxViewVector(n, view)` and the inverse `vxWorldXYOfView(u, view)` (no loops, arrays, structs, dynamic indexing or texture reads). `world.ts` (all four variants), `figure.ts` and `lightPass.ts` apply `vxViewPoint` before `vxProject` and `vxDepthKey`, so the depth key `d = u + v + z` is computed per vertex from the VIEW position and stays exact per fragment for any greedy-merged box; the visible face of an axis is chosen in view space (`side` from `dot(axisView, 1)`), which is what the rigid path already did. A figure's heading in view is `(heading + turn) & 3`, the turn decoded from (c, s).
- Patterns stay keyed on the world (or part-local) position; the top-face "one texel per voxel" shift is a flat varying `vCellShift` along VIEW +x (`patternCellShift`), so every view samples the turned world exactly like view 0.
- Composite: the one weather call site turns the reconstructed view point back into world xy, so cloud shadows and puddles (and their drift) stay over the same buildings. Contact shadow, light pools, outlines, rain, shimmer and the overlay are view or screen anchored by design. 0 added fetches; the lite composite has no ground hook and carries no view code (guard-tested).
- `uView` is a member of the existing `frameUniforms` group (and the front layer's copy), written by `ViewUniformSync` only when `ViewTransform.revision` moved: a steady frame in any view costs one integer compare.
- `VoxelGpuOptions.viewTurn` (default true) builds the VX_VIEW sources at startup; `false` gives the pre-rotation sources byte for byte (hash-pinned in `shaders.test.ts`). Nothing compiles on a turn. `warmUp` also draws once with a quarter turn in `uView` and restores it, so a draw-time failure of the view code shows at startup, not on the first Q. `compositeFxc.test.ts`, `shaders.test.ts` and `viewTransform.test.ts` run the fxc rules on every VX_VIEW source and pin the GLSL twins against the TS ones.

Scene side (`scene/*`, `camera.ts`, `VoxelRenderer.ts`):

- `VoxelScene.view` is the one mutable `ViewTransform` (the renderer hands it to the GPU as `frame.view`). `VoxelScene.setView(frame)` re-sorts and re-bounds every chunk that is not waiting for a rebuild and re-sends it with `setChunk` (view texel bounds), once and synchronously, so no frame mixes two orientations. `StaticWorld.orderChunk` is the one sort: descending VIEW depth key of each box's max corner (`u + v + z` from the box's stored WORLD extent), ground last, ties by emission index so every view sorts exactly like a rebuild would. The extents (and the world AABBs of moving sweeps, `ChunkBounds.sweeps`) are kept per chunk so a turn needs no emit pass. The sort only orders draws for early-Z (view 2 would otherwise draw each chunk exactly back to front); the exact per-fragment key comes from the vertex stage. A dirty chunk is built for the current view by the next update; an edit after a turn rebuilds one chunk. Counters: `stats.chunksReordered`, `bytesStaged`.
- Ghost, draft, figures, rigid parts, coaster trains and riders, litter and lights need no scene change: they are world data. The ghost keeps its WORLD rotation (R keeps its world meaning). One exception: queue slots are a SCREEN layout (7 columns 7 texels apart, each row 5 texels lower and nearer the camera), so `queueSlotOffset(index, rotation)` turns the view-space layout back into a world offset and `VoxelScene.setView` hands the rotation to the figure packer (`FigurePacker.setView`); on the next pack only the queued guests' records change (a few rows uploaded once), and the queue reads the same in every view.
- Hollowing (`blueprint/hollow.ts`) already kept every voxel visible from {+-x, +-y, +z}, which covers the four view directions (tested on every catalog model). Content that assumed a fixed camera: the drop tower's lattice now runs round all four mast faces (it left model -y bare). Model backs are real backs (a shop seen from behind shows its back wall, the gate its blank board); nothing is mirrored.
- Camera: all camera texels are view texels. `VoxelCamera.retargetForTurn(from, to)` keeps the ground point under the middle of the screen. The half-viewport (w / 2N) is not dyadic at every zoom (N = 3, 5, odd windows), so the camera keeps a turn chain: while only turns move it, it remembers the origin per view and a turn back restores it bit for bit (Q x 4 and any turn sequence give the identical snapped camera and Bayer phase; a pan, zoom, focus, resize or another map size starts a new chain). `focusEntranceInView` keeps the view 0 framing and uses the classic midpoint rule in turned views. `focusCell` and `setCameraCentre` go through `cellToView`. Picking, `cssToWorld`, the texel budget, the guard band and the integer upscale are unchanged in every view.
- `VoxelRenderer`: `supportsViewRotation` is true unless the pipeline was built without the view code. `setViewRotation` turns the scene, the overlays, hints and badges (`setView`: hint ring, selection, preview diamonds, draft overlay, bin gauges and ride alerts are re-placed in view space, inputs stay WORLD), the camera, snaps the see-through hole (the focus rectangle is converted with `rectToView` after the world-space shaping, so the cutaway maths runs in view cells) and calls `rehover` last. The camera is retargeted from `shownView`, the transform last applied in full, so the runtime rung recentres from the view actually on screen even when a turn failed after the scene took the new view. A turn asked for before or during mount (a save load, a key press during the mount await) is undone when the pipeline then comes up without the view code: scene sort and bounds, `frame.view`, overlays and picking go back to view 0. `instant` is ignored: the voxel renderer always snaps (no alpha; a cross-fade would need two G-buffers), so reduced motion is trivially met.

Decisions:

- Key light: fixed to the SCREEN (lambert from the view-space normal). The visible faces are always view +x, +y and +z, so they get the same 0.416 / 0.714 / 1.0 in every view, the dusk and night presets read the same, and `lightPresets.ts` is unchanged. A world-fixed sun would leave view 2 with two unlit sides under the current light vector. Point lights are world objects and turn with the map. The rotate buttons and the compass are stacked above the clean-view handle (side by side they ran under the build dock at 1280 px) and the rotate row yields while the management dashboard is open, since that panel reaches the bottom-right corner; Q/E keep working there. Consequence (measured in review: the world +x wall of a cabin reads luma 98 in view 0 and 116 in view 1): a given WORLD face changes brightness when the map turns, because the screen-left face is always the brighter one. This is a deliberate trade and awaits the user's sign-off; the alternative (`vxLambert(axisWorld * side)`) would darken whole views and need new presets.
- Dither: every Bayer anchor stays `fragment texel + uCameraTexel`, now a VIEW texel. Inside a view the pattern is fixed to the picture (it never crawls while panning); across a turn the picture changes completely (a snap), and the exact camera recentre gives back the identical pattern when turning back.

Degradation (`no-view-rotation`): a startup failure in a view-turn build that names a program carrying the view code (every geometry program including the see-through's world-cut and front layer, the light pass, and the composite and front composite of a full composite with the full weather tier: `degradePlanFor(error, { viewTurn, compositeView })`), and nothing that no rung could rescue, is retried once with `viewTurn: false` at the same rung: on success `no-view-rotation` is the label and everything else (weather, translucent cutaway, lights) is kept. If that retry fails too, the failure was not (only) the view code's: the old chain is planned from the retry's failure and walked WITH the view code first (rotation kept, e.g. `no-lights` or `no-weather`), then, for a GPU where both break, once more without it (`...+no-view-rotation`). A runtime exception inside a turn puts everything back to view 0 through the same code path, clears the flag, warns once and appends the label. Q and E then toast "Map rotation is not available on this graphics device" (`GameApp` re-reads the flag after the call); the startup "simplified voxel look" toast is not shown for this label alone. The voxel renderer always stays. Both rungs were driven in headless Chromium: shader sources carrying `vxViewPoint` broken by an init script (13 compiles failed, renderer stayed voxel, label set, view 0, toast on E), and a throw injected into `VoxelScene.setView` (one warning, view 0, label, toast).

Measured, Node/V8 (dev park 32x32, registry content): a turn re-sorts and re-sends all 16 chunks (15,220 boxes) in median 2.7 to 3.0 ms (max 8 ms), 624 KiB staged (rows padded; 476 KiB of box data), 0 chunks rebuilt; a one-chunk edit after a turn costs the same as in view 0 (about 0.3 to 1.3 ms by region); a steady frame in every view stages no chunk and rebuilds none (300 guests: at most 64 KiB staged, as in view 0).

### Camera clamp and eased focus (Phase 11, PA-021, voxel only)

`VoxelCamera` keeps the ground point under the viewport centre inside the plot rectangle in VIEW cells
(`setPlotBounds`, fed by `VoxelRenderer` on a session and on every view change, since W and H swap) expanded by
`plotMarginCells`: `max(2, min(halfX, halfY) / TILE_WIDTH − 1)`, capped at `min(halfX / TILE_WIDTH,
halfY / TILE_HEIGHT) − 0.75` so a plot cell stays on a 1100x690 window at the largest zoom (the uncapped formula
fails there). The private `constrain()` runs after pan, zoom, focus and `setViewport`, and returns without touching
the origin when the point is inside, so a camera that stays on the plot is bit-identical with and without it. It
never runs in `retargetForTurn`: a turn keeps a ground point that was inside, and the turn chain stays exact. The
clamp allows the plot to sit behind HUD panels (at 1100x690 panning up leaves it just behind the build dock).

`RendererPort.focusCell(cell, motion?)` and `focusEntrance(motion?)` take an optional `CameraMotion` (`'instant' |
'ease'`, default instant); the classic `WorldRenderer` ignores it and keeps snapping and unclamped. With `'ease'` the
voxel renderer computes the clamped target and glides there with `VoxelCamera.easeTo` over `CAMERA_EASE_MS` (250 ms,
ease-out cubic), advanced by `stepEase(deltaMs)` in `VoxelRenderer.update`. One frame advances it by at most
`CAMERA_EASE_MAX_STEP_MS` (50 ms), so a slow first frame after the click slows the glide instead of using it up.
Pan, drag and wheel input cancel a glide where it is; a turn, resize, sweep frame (`setCameraCentre`) or new focus
completes it. Reduced motion or an unmounted renderer snaps. Only player moves ease (an estate row, the brand button,
the ⌂ button in the "Map view" pill and V); a session swap, load, new park and the start-screen sweep stay instant.
Tests: `camera.clamp.test.ts`, `camera.ease.test.ts`, the PA-021 block of `VoxelRenderer.test.ts`.

## See-through

When you build behind a tall building the build site would be hidden (2:1 isometric: nearer objects cover cells behind them). The see-through cutaway fixes that in both renderers. It is presentation only: picking stays by map cell (`worldInput`), nothing reaches the simulation, and the hint ring, selection highlight and preview overlays are drawn after the world in both renderers, so they are never occluded and get no cut.

**Trigger.** `GameApp` feeds `RendererPort.setSeeThrough?({ armed, peek })` (ONE reused object, called only when a value changes, from `syncInputContext`, the peek key handlers, window blur and a hidden page). `armed` is `tool !== 'pointer'` in an input context with the `build` capability; the cursor cell and footprint are the renderer's own `hoveredCell` and last `drawPreview`, and the fade runs inside the renderer's `update`. Leaving the map ends the hover, which fades the cut out. **Hold X** (x-ray) peeks: it cuts everything near the cursor, also with the pointer tool (so a selected ride behind a building can be seen). `planPeekKey` in `src/ui/inputContext.ts` decides: a press needs the first keydown with no Ctrl/Cmd/Alt in a `build` context (never in a text field, modal or the management panel); ANY keyup of X, a blur, a hidden page or the context losing `build` releases it, so it cannot stick. X collides with no other shortcut.

**Model.** `src/rendering/seeThrough.ts` is pure and shared: `resolveSeeThroughFocus` (footprint bounds, mode `place | bulldoze | cell`, height; peek grows the hovered cell by one cell), `SeeThroughFade` (0 to 1 in 140 ms, 1 to 0 in 220 ms, on real frame time so it also runs while paused; instant under `prefers-reduced-motion`) and `slewTo` (the cut rectangle follows the cursor with tau 70 ms and snaps within 1/512, so an idle frame changes nothing). Constants are in `SEE_THROUGH`.

**Classic renderer.** `src/rendering/classicSeeThrough.ts` (`ClassicSeeThrough`, pure over `{ alpha }` targets, tested without Pixi) fades display objects to `SEE_THROUGH.CLASSIC_ALPHA` (0.3). An object fades when its `zIndex` sorts in front of the focus (peek reaches one cell further back) and its screen box overlaps the focus box grown by the margin (24 px, peek 48 px, a place ghost also reaches 96 px up for its art). The boxes and sort keys are cached on each `ObjectDisplay` when it is created, so the overlap search is a plain loop that runs only when the focus changes (cursor cell, preview footprint, mode, peek, a display added or removed), never per frame. Per frame only the short list of faded objects is touched, and `alpha` is written only when it moved; at fade 0 the alpha is restored to exactly 1 and the pooled entry is released. Bulldoze passes the sort key of the object under the cursor as a floor (`demolitionKey`), so the building being demolished stays opaque while a building in front of a cell behind it fades. Guests, workers and litter keep their own alpha and are not faded. The list is cleared on `setSession` and `destroy`, `removeObjectDisplay` forgets its entry, reduced motion is instant, and a fault in the focus code disables the effect for the session with one `console.warn` instead of breaking the frame. `WorldRenderer.cameraLayers()` is the layer order (selection, hint, coaster draft and preview layers after the construction layer) and a test pins it.

**Voxel renderer, translucent rung (default, `&voxelSeeThrough=alpha`).** The occluding buildings stay visible but faded, `SEE_THROUGH.OCCLUDER_OPACITY` (0.3, tunable, the same constant the classic renderer fades to), and the build site reads clearly through them; the earlier 1-texel screen door read as a mirror or moire pattern. The occluder fragments (exactly those the cut selects, `z >= floorZ`, key at or past `cutKey`, coverage above 0) are discarded from the main G-buffer, so the revealed ground, ghost and rides behind are lit, outlined and contact-shadowed by the unchanged composite, and are drawn instead, by `worldFront` (same source as `worldCut` with the discard turned round, plus 0.05 of key slack so a rounding can duplicate a fragment but never lose one), into a small fixed-capacity front G-buffer (`FRONT_CAPACITY`, 640 x 448, albedo + gdata + depth24plus, created once; about 5.7 MB with its light and lit targets). That target is rendered with the camera moved by the rectangle's origin (`frontFrameUniforms`: `uCameraTexel + origin`, `uLowSize` = the capacity), so the geometry and look code is unchanged. At dusk and night the same `lightPass` program then runs over the front G-buffer (second shader instance on the front depth, gdata and the front frame uniforms, same light list, scissored to the rectangle) into the front light target, so the faded building gets the same light pools as its unfaded part and there is no lit/unlit seam at the rim. Then `compositeFront` (the same composite source in `front` mode: full look, transparent background, the layer's own light pools, no rain, overlay or shimmer) lights it into `frontLit` over the hole's rectangle only (a scissor). In that run `uFront` is bound to the MAIN depth: a texel of the layer is switched off (alpha 0) where the main G-buffer holds something more than `SEE_THROUGH.FRONT_NEARER_SLACK` (0.75 depth keys) nearer, so a guest, litter or the coaster draft standing in front of the faded building is neither tinted nor covered by it (a ring texel with no geometry of its own compares against its nearest neighbour; one extra fetch in the front run only, which stays at 15 of the 16 budgeted fetches). The main composite mixes that over its own result with weight `1 - coverage * (1 - OCCLUDER_OPACITY)` (one extra fetch inside the rectangle, `uSeeC` = origin and size in target texels; the fetch table in composite.ts counts the look's two exclusive branches once, so the budget stays 16). Rain, shimmer, the overlay, hint ring and selection run after the mix. A faded building keeps its face shading and a soft outline (the layer outlines itself in isolation, at the reduced weight; the ring at the layer's artificial rim is suppressed); the ground behind is lit and outlined normally; light pools tint the faded layer like the rest, and figures, decals and the shadows of the occluder are not part of it (guests behind a faded building read through it, guests in front stay crisp because the layer is hidden there). A rectangle that does not fit the capacity, or no cut chunk, makes that frame use the dither rung (`uSeeC.z` = 0). The lite composite never builds the layer: it shows the dither rung. Fallback order (each label in `window.__voxelDegraded`): translucent -> dither (`no-translucent-seethrough`) -> off (`no-seethrough`); a failure naming `voxel-worldFront` or `voxel-compositeFront` drops one rung, a composite failure in a translucent build is retried first on the same weather tier without the mix, a failure naming no program steps down one rung per retry, and a JavaScript exception in the front draw is contained (`onTranslucentFailed`: dither rung for good, one warning). Measured on the software rasteriser: the hole centre weighs 0.297 of the occluder against the revealed scene (target 0.30). Not verified: a real Direct3D 11 compile of the two new programs and of the grown composite, and the cost on a real GPU (1 to 4 chunk draws repeated into a small target, one more light pass over the front target (the light quads are scissored to the rectangle, so the cost scales with lights times rectangle, never above the main light pass) and a lit rectangle of at most about 140k texels; estimated 3 to 8 per cent of the composite's worst case, never measured). Verified on the software rasteriser only: a guest standing on a faded platform stays crisp with the depth switch and is washed without it, and a night lamp pool shows on the faded part.

**Voxel renderer, dither rung (`&voxelSeeThrough=dither`, and the fallback).** One extra opaque program, `worldCut` (`shaders/world.ts`, variant `cut`, compiled with the other programs at startup and drawn once by `gpu.warmUp`). It is the world program plus a short block ahead of any texture read: from the fragment's window depth it reconstructs the depth key (`vxDepthKeyFromTexture`, the same `d = vx + vy + vz` as everywhere) and its height `z = (key - 2 * texelY) / 3`, measures the distance from the fragment's world texel to the hole rectangle, and `discard`s when the soft coverage `strength * (1 - smoothstep(0.4 M, M, distance))` beats the world-anchored Bayer threshold (`DITHER_OFFSET_SEE`, so the edge stays put on the ground while the camera pans, and there is no alpha blending on this rung). Only fragments with `z >= floorZ` (the ground is never cut) and a key at or past `cutKey` (nearer the camera than the build site) are cut; survivors of the soft rim get `VX_GFLAG_NO_OUTLINE` so they do not outline themselves against the revealed geometry. The TypeScript twin of those lines is `seeThroughCoverage` in `gpu/seeThroughView.ts`, which also holds the maths that turns a focus into the uniforms (`seeThroughValuesFor`). Two uniforms carry everything: `uSeeA` (hole centre and half size in world texels) and `uSeeB` (`cutKey`, `floorZ`, margin, strength). `VoxelRenderer.updateSeeThrough` slews them and bumps `seeThrough.revision` only when a value moved, `SeeThroughUniformSync` writes them only on a new revision, so an idle frame writes nothing. `VoxelGpu.drawChunks` binds `worldCut` only while strength is above 0 and only for the chunks (and the litter list) whose bounds touch the hole grown by its margin (`chunkNeedsCut`); every other draw keeps the discard-free program, with the effect off the cut program is never bound, and no geometry is rebuilt or re-uploaded. The cost is early depth rejection lost on those one to four draws while the effect is on. Hole footprint: a place footprint opens as a whole, a path drag or an oversized footprint (more than `SEE_THROUGH.MAX_FOOTPRINT_CELLS`, 6, on an axis) opens around the hovered cell only, because the hole is one rectangle and a bounding box of an L-shaped drag would eat every building beside it.

*Failure and switches.* The cut program is optional. A startup failure that names `voxel-worldCut` (`degradePlanFor`), or that names no program at all (a link error, tried once), rebuilds the pipeline without it (`skipSeeThrough`) and sets `window.__voxelDegraded` to `no-seethrough` (joined with `+` to the other labels); if that rebuild fails too the original error is thrown and the classic renderer takes over. A bug in the presentation code is contained the same way (one `console.warn`, strength 0, same label). `&voxelSeeThrough=alpha|dither|off` chooses the starting look (default `alpha`; `dither` is the earlier look with no label; `off` starts without the effect). The translucent rung's own failure handling is described above; `worldFront` and `compositeFront` get the same static guards as `worldCut` and the composite (`gpu/compositeFxc.test.ts`). `gpu/compositeFxc.test.ts` checks the `worldCut` source statically like the composite (no struct, loop or derivative, no dynamic subscript beyond the Bayer table that `worldOpaque` already has, one discard before any texture read, bounded size over the plain program). Not verified: a real Direct3D 11 compile and the cost of a hole on a real GPU, which no test here can reproduce; a wrong key reconstruction from depth precision would cut the wrong fragments without any error, so it needs a look on a Windows GPU.

## Performance posture

No React work occurs per frame. This section describes the classic renderer; the voxel renderer's rules are under Renderers. Static geometry is rebuilt only after construction changes, while Pixi guest displays are synchronized directly from simulation records. The clock uses a bounded fixed-step accumulator. Guest decisions are staggered naturally by arrivals and state transitions.

That rebuild is incremental as of Phase 11 (PA-006). `syncWorld` keeps a display per object and reconciles against the world instead of tearing the scene down: a placement adds one display, a removal disposes one, and ride bases are only re-drawn when their cached path-edge signature actually changes. A gesture is also batched into a single world change through `GameWorld.batch`, so `version` still advances per mutation — every cache keyed on it stays correct — while listeners fire once at the end. A twelve-tile bulldozer drag therefore costs one scene reconciliation rather than twelve full-park rebuilds. Two tests hold the line: a steady-state test asserting *zero* `Graphics` draw calls per frame with nothing changing, and a construction-frame budget asserting a ceiling per gesture kind. A third test replays random mutation sequences against a freshly constructed renderer and compares scene-graph fingerprints, so the incremental path can never quietly diverge from a full rebuild. Undo is among those mutations, and its steps sync the renderer between the build and the undo: a build and its undo inside one sync window hide exactly the stale-cache bug the test exists to find.

The 1,000-guest pass rests on caching everything that only changes when the world changes: PathNetwork computes distance fields and next-pointers in one BFS per destination and caches connected components, so destination scoring is O(1) lookups and a route array is materialized only for the destination a guest commits to; ManagementSimulation aggregates the guest population in a single pass per step and caches entrance connectivity per world/path version. Measured cost at 1,100 guests is ~0.55 ms per 100 ms tick, guarded by a scale regression test with generous headroom. Phase 14 adds per tick only the field's decay (1,024 integer cells) and an O(1) entry and factor lookup per tile step; path shape (45-57 µs), neighborhoods (0.05-0.37 ms) and coverage are per world or path version, and the view and heatmap (0.07-0.17 ms uncached) per UI publish. Measured against the Wave 0 code at 1,000 guests (best of 5 x 40 ticks, median of three interleaved rounds): +0.03 to +0.07 ms/tick on seven parks, within the ±0.05 ms noise and under 1 % of the 8 ms budget; `performance.test.ts` has a Phase 14 case at the same budget with feedback on and the views every 10th tick. Pooling and viewport culling on the rendering side remain available if the browser frame rate ever demands them.
